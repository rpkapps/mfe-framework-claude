# @company/shell

The test shell: a header and a mount point. It owns the top bar, the registry,
the command palette and the routes above an App's boundary. Everything below
the header belongs to the mounted micro-frontend — the shell adds no padding,
no card and no page title there.

## Running it

```sh
pnpm install                              # from the repo root
pnpm --filter @company/shell dev          # http://localhost:3000
pnpm --filter @company/shell build        # dist/
pnpm --filter @company/shell typecheck
pnpm --filter @company/shell lint
```

The dev server has a history-API fallback, so a deep link into a mounted App
(`/orion-discovery/wells/42`) serves the shell document and the App routes the
rest for itself.

`node scripts/screenshot.mjs [path] [outfile]` captures the running shell at
1400×900; `docs/shell-header.png` is the header as built.

## The registry

`public/registry.json` is an array of generated shell descriptors, fetched at
boot and handed to `createMfeRuntime` raw — the runtime normalizes them,
applies developer overrides and quarantines whatever fails validation:

```json
{
  "id": "orion-discovery",
  "kind": "app",
  "mfe": { "contractMajor": 1 },
  "manifestUrl": "http://localhost:3101/mf-manifest.json",
  "container": "orion_discovery",
  "expose": "./app",
  "title": "Orion Discovery",
  "icon": "ORI"
}
```

In a real deployment this file is generated by each container's build and
published by the shell's deployment. Nobody hand-writes it.

The checked-in file points at dev servers that are not running and deliberately
includes two entries that cannot validate (`legacy-reports` advertises contract
major 2; `no-manifest` has no `manifestUrl`). That is the failure case worth
keeping: the shell boots, the header works, the valid entries stay in the app
finder, the rejected ones are named in the notice strip under the header, and
an unreachable App renders an error surface with a working Retry.

## Developer overrides

The runtime reads `localStorage["company:mfe:overrides"]` **before** any remote
is registered, so an overridden App is pointed at your dev server from its very
first load. To point one App somewhere else:

```js
localStorage.setItem(
  'company:mfe:overrides',
  JSON.stringify({ 'orion-discovery': 'http://localhost:3101/mf-manifest.json' }),
)
```

Then reload — overrides are applied at boot, not per navigation. To clear:

```js
localStorage.removeItem('company:mfe:overrides')
```

While any override is in force the shell shows a strip directly under the
header naming every overridden id and the URL it now resolves to. A forgotten
override pointing at a dead dev server is the failure this makes impossible to
miss, so the indicator is not dismissible.

## Consuming @tecton/react

`@tecton/react` lives in a **separate git checkout** next to this one and is
private, unbuilt and source-TSX. Three things make it work here, and all three
are consequences of that:

1. **`package.json`** depends on it as `link:../../../tecton-ui-1/packages/tecton-react`,
   and declares its peers (`react-aria-components`, `cn`,
   `class-variance-authority`, `lucide-react`, `next-themes`, `sonner`,
   `react-resizable-panels`, `react-aria`) plus what its stylesheet imports
   (`tailwindcss`, `tw-animate-css`, `shadcn`, `@fontsource/*`). pnpm does not
   install a linked package's own dependencies, so the shell has to.
2. **`rspack.config.mjs`** lists this workspace's `node_modules` in
   `resolve.modules` by absolute path, because walking up from the design
   system's real location finds nothing; and it sets `NODE_PATH` for the same
   reason on Tailwind's side, which resolves `@import`s from the stylesheet's
   own directory. The TypeScript rule has no `node_modules` exclusion — this
   build is what transpiles the design system's TSX.
3. **`tsconfig.json`** maps the same specifiers back at this workspace, which
   is the type-level counterpart of the above.

**Caveat.** All of that only works because the checkout sits at a known
relative path. A real deployment publishes `@tecton/react` as a versioned
private package, at which point the `link:` becomes an ordinary version range
and the three resolution workarounds above all disappear. Nothing else about
the shell changes.

Two consequences worth knowing while the link is in place:

- `pnpm typecheck` runs `scripts/typecheck.mjs` rather than `tsc` directly.
  `tsc` cannot exclude a file it was asked to resolve, so consuming unbuilt TSX
  type-checks the design system's source too — under *this* workspace's options
  (`exactOptionalPropertyTypes`, `noUncheckedIndexedAccess`) rather than the
  ones it is written against. Those diagnostics are printed but do not fail the
  check; anything under `apps/shell` does, including errors raised at a shell
  call site for misusing a design-system prop.
- The stylesheet is larger than it needs to be. `globals.css` declares
  `@source` globs for the design system's own repository layout, one of which
  matches its documentation site, so utilities only that site uses are
  generated here too.

Tecton's palette replaces Tailwind's: stock colour utilities (`bg-red-500`,
`text-zinc-400`) generate **no CSS at all**. Use a semantic token
(`bg-destructive-surface`, `text-muted-foreground`) or a Tecton step
(`bg-blue-120 text-blue-830`).

## Federation

The shell is the federation **host**: it consumes remotes and is not itself a
container, so it does not use `mfePlugin()` from `@company/mfe-rspack`. It
declares no static remotes — each is registered at runtime by the framework's
loader, which is handed `registerRemotes` and `loadRemote` from
`@module-federation/runtime` in `src/boot.tsx`, the one file that knows
federation exists.

`react`, `react-dom`, `@tanstack/react-router`, `@tanstack/react-query` and
every `@tecton/react/*` subpath are shared as strict singletons, so a remote
that resolves its own copy is an error rather than a second React or a second
set of React Aria contexts.

## Known issue in the framework

`src/shell/router.tsx` resolves an App through `runtime.loader` before handing
it to `AppHost`. That is a workaround, and its comment says so: the framework's
own loader drops its cached promise when a load fails, so the render that
should surface the error gets a fresh pending promise and suspends again. An
unreachable remote therefore never reaches `AppHost`'s `fallback` and instead
refetches its manifest as fast as the browser allows (measured here at roughly
340 requests per second). Delete the workaround once the loader keeps its
rejection.
