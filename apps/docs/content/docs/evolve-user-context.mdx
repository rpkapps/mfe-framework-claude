---
title: "Evolve an owner's user-context schema"
description: 'Release owner schemas independently while preserving older readers and writers.'
---

Each App or Widget versions its own `userContext.schema`. Readers separately declare the subset they require in `userContext.reads`. Build tooling compiles these declarations into owner contracts and small generated requirements; runtime bundles do not carry Zod or the compiler solely for user context.

## Preserve compatible fields

Add optional fields or fields with deterministic defaults so an existing saved slice still validates. Keep the meaning and type of existing fields stable. Renaming or removing a required field, narrowing an enum, or changing a field's type can break a deployed reader and should be treated as a breaking change.

Object updates merge recursively. An older owner deployment updating a known field preserves fields introduced by a newer deployment. Omission is not deletion. Arrays are complete replacements, and `null` is an explicit clear only where the schema allows it.

Supported declarations include fixed Zod objects, finite JSON primitives, literals, string enums, arrays, nullable and optional properties, deterministic defaults and supported numeric/string/array bounds. Transforms, coercion, arbitrary refinements, dynamic defaults, unions, records and recursion fail compilation.

## Optional owner release checks

Normal generation and deployment need no baseline map or central version configuration. An owner that promises compatibility with a previous release can compare its own contracts in a standalone release check:

```ts shared title="Optional owner release check"
import { compareContracts } from '@company/mfe-build/user-context'

const diagnostics = compareContracts(previousOwnerContract, candidateOwnerContract)
if (diagnostics.length > 0) {
  throw new Error(diagnostics.map(item => `${item.path}: ${item.message}`).join('\n'))
}
```

The owner supplies those two contracts from its release artifacts. This check is separate from the shell, adapters and persistence service; none needs a list of domain contracts, schema revisions or baseline paths. A comparison is optional and does not coordinate other teams' deployments.

## Coordinate readers with owners

Publish the owner's definition and generated registry metadata together. Existing readers can continue using a compatible subset. A new reader requiring unavailable capabilities fails before mounting instead of silently losing data.

The persisted document remains opaque JSON. Adding a field does not require a backend schema change or a new adapter release; defaulting and validation happen in the owning MFE's runtime. Writes from older deployments preserve fields they do not understand. Historical contracts, if retained for optional comparison, stay in the owner's release tooling.
