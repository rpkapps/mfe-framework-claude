---
title: "Evolve an owner's user-context schema"
description: 'Release owner schemas independently while preserving older readers and writers.'
---

Each App or Widget versions its own `userContextSchema`. Readers separately declare the subset they require in `userContextReads`. Build tooling compiles these declarations into owner contracts and small generated requirements; runtime bundles do not carry Zod or the compiler solely for user context.

## Preserve compatible fields

Add optional fields or fields with deterministic defaults so an existing saved slice still validates. Keep the meaning and type of existing fields stable. Renaming or removing a required field, narrowing an enum, or changing a field's type can break a deployed reader and should be treated as a breaking change.

Object updates merge recursively. An older owner deployment updating a known field preserves fields introduced by a newer deployment. Omission is not deletion. Arrays are complete replacements, and `null` is an explicit clear only where the schema allows it.

Supported declarations include fixed Zod objects, finite JSON primitives, literals, string enums, arrays, nullable and optional properties, deterministic defaults and supported numeric/string/array bounds. Transforms, coercion, arbitrary refinements, dynamic defaults, unions, records and recursion fail compilation.

## Check against previous owner releases

When a deployment maintains a support window, pass optional per-owner baselines to build tooling:

```ts shared title="Build options (compatibility baselines)"
userContextBaselines: {
  operations: ['./deployment/operations-v1.json'],
  reports: ['./deployment/reports-v2.json'],
}
```

Each path contains the owner's previously published compiled contract, either as a single-owner manifest or a bare contract. Release CI should source baselines from trusted published artifacts. The checks compare that owner's new schema against its baselines; no global schema package or mandatory global policy file is required.

A first release can build without baselines. Omitting baselines does not establish compatibility with earlier releases; supply the releases your deployment promises to support.

## Coordinate deployments

Publish the owner's new compiled contract with its deployment artifacts. Make a compatible current contract available to the shell and backend before deploying a reader that requires newly added fields. Existing readers can continue using their older subset. A new reader requiring an unavailable capability fails before mount rather than silently dropping data.

The shell and backend need current owner contracts. Historical baselines remain in build and release tooling, outside consumer runtime payloads.
