## What stays neutral

`@company/mfe-core` and `@company/mfe-host` import no React, no router and no Module Federation.
The core holds the `MfeAdapter` interface and the common `RegistryEntry` shape, and names no
framework. The host defines a `ContainerLoader` port and orchestrates loading through it. An
adapter supplies the implementation.

That is what keeps a second adapter cheap. Every shell screen reads the same registry, so no screen
asks which adapter an entry came from.

## How an entry reaches an adapter

An adapter is four things. Its `kind`, and a cheap `detect` that says whether an entry is its own.
Then a strict `parse` that reads the entry or throws. Then an `is` guard that gets a caller back to
its own fields.

`readRegistry` is one pass. Each raw entry is offered to every registered adapter's `detect`, and
exactly one of them must recognise it. If none does, the entry is set aside as unrecognised. If two
or more do, it is set aside as ambiguous, and the reason names them. Order therefore means nothing.
`reactAdapter` is always registered, and `createMfeRuntime({ adapters })` names the rest.

| Adapter                       | Recognises an entry when                                 | Mounts it with           | Removable |
| ----------------------------- | -------------------------------------------------------- | ------------------------ | --------- |
| `@company/mfe-react`          | it names the framework version it was built for, `mfe`   | React, Module Federation | no        |
| `@company/mfe-legacy-angular` | there is no `mfe` key, plus a `name` and `mfManifestUrl` | a single-spa parcel      | yes       |

Nothing falls back on its own. `detect` asks only whether an `mfe` key is there, never how well it
is formed. An entry that names a framework version therefore belongs to the React adapter, whatever
state the rest of it is in. A malformed one is set aside with a reason, and the registry lists it
under `rejected`. Reading it as legacy instead would let a typo change how an application loads,
unseen.

Every entry is read on its own, so one bad entry loses only itself.

## The React adapter

The React adapter loads a container through Module Federation, then mounts the `createApp` and
`createWidget` definitions that container exposes. It owns the pieces that need React: the boundary
history, the scope and style roots, and the definition checks a mount runs.

Federation lives here rather than in the host, in one framework file and one shell file. Decision 6
argues that placement.

## The legacy Angular adapter

The legacy adapter reads a legacy entry into the same common shape. Identity, manifest URL and
presentation go on the common fields, and the legacy-specific fields are typed on
`LegacyRegistryEntry`. A caller reaches them through `legacyAngularAdapter.is(entry)`, so no shell
screen has to know the legacy vocabulary.

It then drives the application's own parcel lifecycle. A <Term>parcel</Term> is a piece of an
application exposing `bootstrap`, `mount` and `unmount`, for another application to mount into an
element. The adapter loads the module exposed at `./single-spa-app` and mounts it. It also resolves
the base href that application expects, and leaves a fixed set of routes to the shell.

Two rules hold there. A second mount without an unmount is refused, because two parcels rendering
into one element leave orphaned DOM behind. Disposal is terminal and idempotent, so every caller
awaits one teardown and a disposed mount cannot be revived.

`single-spa` is not a dependency of the package, not even an optional peer. The parcel, its
configuration and `mountRootParcel` are typed structurally, which is what lets the lifecycle be
tested without single-spa, Angular or a bundler.

## What both adapters share

Shared services come from the host and are the same for both. One storage store, one command
registry, one breadcrumb store, one navigation bridge and one diagnostics hub are built per runtime.

Removal is the point of the second adapter. When the last legacy application is migrated, delete
the package, one entry from the shell's `adapters` list and one import from its composition root. No
other package changes.

## What is proven, and what is not

The legacy adapter is built and tested against production-equivalent fixtures and doubles. The real
Asset Tracker and Rigstream applications have never been run against it, and decision 9 records
that.

The shell in this repository registers the adapter in `apps/shell/src/boot.tsx`, so a legacy entry
in its registry is read rather than set aside.
