---
title: 'The isolation boundaries'
description: 'The six boundaries between one mounted container and the rest of the page, and the mechanism that holds each one.'
---

For framework maintainers and shell builders. If you are writing an App or a Widget, the recipes
tell you what you need.

Six boundaries separate one mount from the rest of the page: the URL, styles, storage, the network,
errors and framework share scopes. Each one answers the same question in a different medium. What can
this container reach, and what can reach it?

The boundaries keep containers that mean well from colliding by accident: a shared storage key, a
class name that restyles another App, a token sent to a host nobody declared. They are not a
security model. Every container runs in the shell's document with the shell's privileges, and is
trusted because the company builds and deploys it
([decision 54](/docs/how-it-works/decisions#54-every-container-is-trusted-with-the-shells-privileges-the-boundaries-prevent-accidents)).

## The URL

The base path is the string form of the boundary, and it is the only prefix an author is given.
After `createRouter({ basepath })` it never appears again. Every route, `Link` and `navigate`
resolves under it.

The framework builds the boundary history by hand. `createBrowserHistory()` reassigns
`window.history.pushState` for the whole page, so two routers built that way start correcting each
other's URL. The shell owns `/`, `/$appId` and `/$appId/$`, and nothing else. Decision 1 argues the
hand-built history.

The shell's own router writes the page's history directly, and the browser reports only `popstate`.
So after each navigation of its router the shell calls `navigator.announce()`, which tells mounted
Apps where the page went. It tells them nothing when they already know.

## Styles

The build wraps every rule in a container's stylesheet in one scope rule,
`@scope ([data-mfe-scope="<id>"]) to ([data-mfe-scope])`. Scope proximity then decides ties, in
place of injection order. Two builds that both spell `bg-primary` no longer resolve by whichever
chunk the browser parsed last.

The runtime creates two roots per mount, whichever adapter built the definition. The scope root is a
`display: contents` div around the definition's element, carrying `data-mfe-scope`,
`data-mfe-mount` and `data-mfe-kind`. The overlay root is appended to `document.body`, with the same
scope value, so a dialog at body level still matches the start selector. A definition renders
inside the first, portals into the second, and adds no root of its own. A React container's
generated style root renders inside the scope root.

Three more things happen to the sheet. Document-global at-rules are hoisted out of the scope
unchanged. Every `@keyframes` the sheet defines is renamed after the container's ids, and its
references are rewritten to match. A leading `:root`, `html` or `body` compound is rewritten to
`:scope`, and the same selectors anywhere else are a build error.

`@scope` is the narrowest-supported feature the framework requires, at Chrome 118, Firefox 146 and
iOS Safari 17.4. There is no fallback, and decisions 17 and 5 record why.

An Angular container's global stylesheet is scoped the same way. Its component styles keep
Angular's own encapsulation. PrimeNG is the exception to all of it. It writes its components' rules
into unscoped style tags in the document head, named page-wide, so every Angular container on a page
has to use the same PrimeNG version. Its design tokens are page-wide by intent: containers give it
no preset, and the host declares the tokens once, with the other assets every Angular container
shares, before the first one mounts. Its Dialog, ConfirmDialog and Drawer also need `appendTo` set
to the mount's overlay root, or they render outside the scope.

## Storage

The key is `<definitionId>:<name>`, and it carries no mount token. Two mounts of one definition
therefore read one record. A definition id may not contain a colon, because the colon separates the
id from the name.

A record belongs to the browser profile, not to the person signed in. The framework keeps it until
something removes it, so a sign-out keeps it and the next user of that profile reads it. Nothing
personal belongs in storage.

`@host` is the scope outside any mount. It is spelled with an `@` because no definition id can hold
one, which is what makes the scope unclaimable. Decisions 24 and 56 argue both halves.

## The network

`#mfe/fetch` is a standard `fetch` bound to one container's transport, so a route loader passes its
own `signal` straight in. The generated module resolves a relative URL against the first field
declared `env(…, { api: true })`.

The allowlist is an exact set of scheme, host and port, with no wildcards and no substring matching.
A wildcard would hand the session token to any host the pattern happened to match. A request to an
undeclared origin goes out without a token.

The transport retries once after a 401, and only when the request can be replayed. A 403 passes
through untouched, because attaching a token is not authorization.

## Errors and diagnostics

Every framework failure is composed to one shape:
`<id>[@<version>] failed to <operation>[ <path>]: expected …, received …. <repair>`. The code comes
from a closed union, so adding one is a deliberate contract change.

Diagnostics fan out to the sinks the shell registered. A sink that throws cannot stop the others,
and a hub with no sinks discards everything.

## Framework share scopes

Each framework shares in a Module Federation share scope named after its exact installed version:
`react@19.3.0`, `angular@19.2.25`. Inside a scope go the framework-bound packages. For React that is
React, `react-dom`, `sonner`, the TanStack packages and the design system's own list. A container
shares a candidate only when it depends on that package. The adapter is bundled into each container,
so the providers it renders bind to the same copies the author's code imports.

No package is a singleton, because containers are released from repositories of their own. A
container takes the loaded copy its range accepts, so containers whose ranges agree download one
copy, and a container whose range nothing loaded satisfies loads its own copy instead of failing. A
container on another version brings its own complete set, so several React versions can share one
page. `@company/mfe-core` and `@company/mfe-runtime` are shared in the `default` scope, whatever
framework a container uses, and keep nothing that needs them to be the only copy. A registry entry
lists its container's scopes as `shareScopes`, and the loader registers the remote with exactly
those. A container may add to the candidate list and cannot remove from it.

The scopes have four costs. A container on its own copy of `sonner` queues toasts the shell's
`Toaster` never reads. Every container downloads its own adapter. A container on a newer runtime
than the shell's calls the shell's runtime object, so a member the shell's version lacks fails when
it is called. The shell shares only what it installs, so it no longer shares `recharts`.
PrimeNG is never shared at all. Decision 55 argues for no singletons, decision 33 for the scopes,
and decision 30 records how a host resolves them.
