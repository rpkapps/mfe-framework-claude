For framework maintainers and shell builders. If you are writing an App or a Widget, the recipes
tell you what you need.

A <Term>mount</Term> is one live instance of a definition on the page. It owns a mount token, a base
path, an abort signal, storage handles, telemetry, a scope root and an overlay root. Every host
creates one the same way, through `mountDefinition` in `@company/mfe-runtime`. This page follows one
mount through its five stages.

## One path for every host

A host renders an empty element and calls `mountDefinition` with the runtime, that element, the
definition id and its kind. An App request adds the base path. A Widget request adds the inputs and
an `onEvent` handler. The call returns a handle with the mount's state, `retry()`, `dispose()` and,
for a Widget, `update(inputs)`.

`AppHost`, `DynamicWidget` and the component `lazyWidget` returns all work this way. So do
`<mfe-app-host>` and `<mfe-widget>` in Angular. No host asks which framework built the definition,
so a React shell places an Angular Widget exactly as it places a React one. Decision 33 argues the
one path.

The state is one of four: `pending`, `mounted`, `error` or `disposed`. A React host shows its
`pending` slot while the state is `pending`, and its `fallback` while it is `error`. Nothing
suspends.

## Stage 1: the container loads

The runtime looks the id up in the registry first. An id the registry does not hold, or an entry of
the other kind, fails before anything downloads. The load then goes through the runtime's one loader,
inside the `aroundLoad` of the adapter that read the entry.

The loader shares a load in flight and keeps a load that resolved, so a container loads once per
page. It never keeps a rejection, so a retry after a failed load fetches afresh. The load runs under
the runtime's load deadline, 30 seconds unless the shell tunes it, and an overrun fails as
`load/timeout`.

## Stage 2: the definition is checked

The module the container exposed has to be a mountable definition: a branded record with a `mount`
function, and for a Widget a contract. It also has to be the kind the registry entry named. Either
failure is `load/entry-failure`.

## Stage 3: the roots are created

The runtime creates a scope root, a `display: contents` element carrying `data-mfe-scope`,
`data-mfe-mount` and `data-mfe-kind`. It puts the definition's element inside it. It then creates
the mount context: a mount token such as `operations#1`, the depth, the base path, telemetry, the
definition's two storage areas, an abort signal and an overlay root appended to `document.body`.
The base path is always an empty string for a Widget, which owns no URL.

A definition renders into its element and portals into the overlay root. It never adds a root of
its own.

## Stage 4: the definition mounts itself

The runtime calls `definition.mount(target)` after an `await`, never from inside a host's render.
The mount deadline starts here, measured after the code is ready.

A React definition opens a React root of its own on the element. The root renders the mount's
providers, the mount's own Query client, the style root the build attached, and then the App's
router or the Widget. `useId` values are prefixed with the mount token, so two roots never hand out
the same id. In development the root runs in StrictMode.

For an App, the first render checks the router the factory returned against what it was given. The
base path must arrive as `basepath`, and the history, `context.mfe` and the top-level
`queryClient` must be the ones supplied. A mismatch fails as `app/invalid-base-path` or
`app/invalid-router`, and any failure in that first render rejects the mount. A render error after
the first commit goes to `target.onFailure` instead, which moves the mount to `error`.

A Widget receives its inputs only when they change. The runtime drops a set shallow-equal to the
last one, and inputs that changed while the Widget was mounting arrive once, afterwards. The Widget
validates each set in three steps. Serializability comes first, so the diagnostic names the real
problem. Then the declared `inputs` schema runs, and then the parsed key names are checked against
the reserved ones. The first set that fails rejects the mount. A later set that fails keeps the last
valid inputs on screen and is reported.

`emit(name, payload)` checks that the event is declared, that the payload is JSON-serializable, and
that it matches the declared schema. All three throw at the call site, in the Widget's own stack.
A host that supplied its own contract checks the payload a second time. A payload that fails there is
reported and not delivered, because a narrower expectation is not the Widget's bug.

## Stage 5: disposal, in order

Disposal runs from the host's `dispose()`, or when the parent mount is disposed. The scope root
leaves the page at once, and teardown follows in this order.

1. The definition's own `dispose` empties its element. A React definition unmounts its root.
2. Action and navigator registrations are removed, so a disposed mount cannot appear in the palette
   mid-teardown.
3. The abort signal aborts. In React that cancels the mount's queries and clears its cache, without
   waiting on them.
4. Telemetry is disposed.
5. The overlay root is removed from `document.body`.

Disposal runs under the dispose deadline, 5 seconds unless the shell tunes it. It does not touch the
container module cache, so mounting the same App again does not refetch it.

## Where each failure goes

| Code                                        | How it ends                                 | What the consumer sees                            |
| ------------------------------------------- | ------------------------------------------- | ------------------------------------------------- |
| `registry/invalid-entry`                    | the load rejects                            | the host's `fallback`, with the message and Retry |
| `load/manifest-failure`                     | the load rejects                            | the host's `fallback`                             |
| `load/entry-failure`                        | the load or the check rejects               | the host's `fallback`                             |
| `load/timeout`, `mount/timeout`             | the deadline rejects                        | the host's `fallback`                             |
| `app/invalid-base-path`                     | the first render rejects the mount          | the host's `fallback`                             |
| `app/invalid-router`                        | the first render rejects the mount          | the host's `fallback`                             |
| `contract/input-mismatch`, first validation | the mount rejects                           | the host's `fallback`                             |
| `contract/input-mismatch`, later update     | reported to diagnostics                     | the last inputs that passed, still on screen      |
| `contract/event-mismatch`                   | thrown at the `emit` call site              | a throw in the Widget's own code                  |
| `mount/failure`, after the first commit     | `onFailure` moves the mount to `error`      | the host's `fallback`                             |
| a render error inside a mounted App         | caught by the App's `defaultErrorComponent` | that error component, inside the App              |

Without a `fallback`, a React host throws the error to its nearest error boundary. `retry()` acts
only from `error`. After a failed load it loads afresh, and after a failed mount it reuses the
loaded definition with a fresh mount token. Each failed attempt is one diagnostic, reported to the
hub the shell installed. A hub with no sinks discards everything, which is the first thing to check
when a shell reports nothing.

## StrictMode mounts everything twice

In development React mounts, unmounts and mounts again without re-rendering. The effect that calls
`mountDefinition` is the effect whose cleanup disposes the handle. So the first handle is disposed
before its load settles, and the definition's `mount` runs once. For an author this means two
things. `src/mfe.ts` stays free of side effects, and every effect is idempotent and cleans up after
itself.

## Why the effect owns the handle

`mountDefinition` starts a load and appends to the page. None of that belongs in a render React may
discard, so the host calls it from an effect and publishes the handle it returns. One render
therefore passes before the mount exists, and the host shows `pending` for it. Decision 14 records
the StrictMode bug that forced this shape.
