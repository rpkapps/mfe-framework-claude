## What stays neutral

`@company/mfe-core` and `@company/mfe-runtime` import no framework, no router and no Module
Federation. The core holds contracts only: the `MfeAdapter` interface, the common `RegistryEntry`
shape and the definition brand, and it names no framework. The runtime holds everything that is the
same for every adapter. That is the registry read, the federation loader and `mountDefinition`, the
one path every host mounts every definition through.

An application never imports either package. It imports its adapter: the root, `/host`, `/testing`
or `/registry`. Each adapter's `/host` re-exports the runtime beside its own provider, so a shell
reads the same whichever framework it is written in.

## How an entry reaches an adapter

An adapter is four things, plus one option. Its `kind`, and a cheap `detect` that says whether an
entry is its own. Then a strict `parse` that reads the entry or throws. Then an `is` guard that gets a
caller back to its own fields. An adapter may also declare `aroundLoad`, which the runtime runs
around the loads of the entries it parsed, and no others.

`readRegistry` is one pass. Each raw entry is offered to every adapter's `detect`, and exactly one of
them must recognise it. If none does, the entry is set aside as unrecognised. If two or more do, it
is set aside as ambiguous, and the reason names them. Order therefore means nothing. No adapter is
registered implicitly: `createMfeRuntime({ adapters })` names every one the shell serves.

| Adapter                | Recognises an entry when         | Mounts it with                   |
| ---------------------- | -------------------------------- | -------------------------------- |
| `@company/mfe-react`   | its `mfe` marker names `react`   | a React root per mount           |
| `@company/mfe-angular` | its `mfe` marker names `angular` | an Angular application per mount |

Nothing falls back on its own. `detect` asks only what the `mfe` marker names, never how well the
rest of the entry is formed. An entry that names a framework therefore belongs to that framework's
adapter, whatever state the rest of it is in. A malformed one is set aside with a reason, and the
registry lists it under `rejected`. Reading it with another adapter instead would let a typo change
how an application loads, unseen.

Every entry is read on its own, so one bad entry loses only itself.

## The framework adapters

The React and Angular adapters read an entry the same way, through the runtime's
`parseFederatedEntry`. Each provides the author API for its framework, `createApp` and
`createWidget`, and the host components that place other definitions. Each definition carries a
`mount` the runtime calls with an element inside the scope root.

No host asks which adapter built a definition. `AppHost`, `DynamicWidget` and `lazyWidget` in React,
and `<mfe-app-host>` and `<mfe-widget>` in Angular, all call `mountDefinition`. A React definition
then opens a React root of its own, and an Angular one creates an Angular application of its own. So
a React shell places an Angular Widget the way it places a React one, and an Angular App can host a
React Widget.

The React adapter's `aroundLoad` hides TanStack Router's development global while a React container
evaluates. The Angular adapter is Angular 19 and zoneless, so every mount schedules its own change
detection and no container loads `zone.js`. It names no UI library. Decisions 6, 31 and 33 argue the
split.

The definition brand is an open string, and the shell lists its adapters. So a third adapter is one
more package and one more entry in that list. It needs no change to the core, the runtime or the
adapters already there.

## What every adapter shares

Shared services come from the runtime and are the same for every adapter. One storage service, one
action registry, one breadcrumb store, one navigation bridge and one diagnostics hub are built per
runtime.

## What is proven

The Angular adapter's suites run in jsdom with components compiled just in time. An Angular
container's own build and tests are the Nx generator's, and run in a separate Nx workspace.
