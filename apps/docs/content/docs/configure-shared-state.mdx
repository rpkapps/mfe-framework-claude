---
title: 'Configure shared state in the shell'
description: 'Save shared selections and keep one workspace’s records separate from another’s.'
---

The shell connects shared state to backend persistence and selects its user or workspace scope.
Configure one user's records per workspace so switching workspaces restores the corresponding selection.

The shell, backend and containers can live in separate repositories. Each installs a released contract package from your registry.
This configures backend persistence. [Browser storage](/docs/remember-a-value) remains scoped to a definition and survives sign-out.

## Steps

<Steps>
<Step>
### 1. Connect the schema, storage and workspace

```ts shared title="Illustrative shell repository: src/runtime.ts (shared-state options)"
import { schema } from '@acme/shared-state-contracts/schema'

const { runtime } = createMfeRuntime({
  // Keep the shell's existing runtime options.
  sharedState: {
    schema,
    scope: JSON.stringify([tenantId, userId, workspaceId]),
    adapter: sharedStateAdapter,
    onError: reportSharedStateFailure,
  },
})
```

The three required options have separate jobs:

| Option    | What to supply                                                     |
| --------- | ------------------------------------------------------------------ |
| `schema`  | The current compiled JSON schema for the keys the shell supports.  |
| `adapter` | Your connection to the backend that reads and saves those records. |
| `scope`   | A string identifying tenant, user and workspace.                   |

Install the contract release in the shell repository and backend repository separately. The name and version below are illustrative.

```json shared title="Illustrative dependency in each repository's package.json"
{
  "dependencies": {
    "@acme/shared-state-contracts": "1.2.0"
  }
}
```

The package's `/schema` export supplies the compiled schema. Publish it with the authoring declaration,
`shared-state.manifest.json` and release policy. Each repository installs registry versions through its own lockfile.
Older containers can keep earlier compatible contract releases.

`sharedStateAdapter` connects to your backend. Use optional `onError` to report failures through the shell.
The framework's `examples/shared-state/src/browser.ts` demonstrates an adapter. Its demo harness is a reference, not a production dependency.

The adapter's `hydrate` loads records. Its `write` resolves after the backend commits the saved record.
Add `subscribe` for updates from other browsers or users.

</Step>
<Step>
### 2. Check access on the server

Before reading or saving a record, check that the signed-in user can access that workspace.
The browser's scope string selects a record. Check access separately on the server.

<Details summary="Use the reference backend with your repository">

```ts shared title="Illustrative server/shared-state.ts"
import { createSharedStateBackend } from '@company/mfe-runtime/shared-state'
import { schema } from '@acme/shared-state-contracts/schema'

export const backend = createSharedStateBackend({
  schema,
  repository: durableRepository,
  authorize: authorizeSharedState,
})
```

`durableRepository` is your database implementation of `SharedStateRepository`. Its `read` loads a saved record. `transact` checks and updates it in one database transaction. It must
finish saving before it resolves. `authorizeSharedState` performs the access check above.

Your HTTP or RPC handlers call `backend.hydrate` and `backend.write`. The browser adapter calls those handlers. Return write conflicts as errors so the picker can tell the user the save failed.
Use a durable repository in production.

</Details>

</Step>
<Step>
### 3. Switch records when the user changes workspace

```ts shared title="Illustrative shell repository: src/workspace.ts"
runtime.sharedState.setScope(JSON.stringify([tenantId, userId, nextWorkspaceId]))
```

Remount the Apps and Widgets that use shared state. Their new bindings read the new workspace's
records. A save still running from the previous workspace cannot update them.

This example includes the user id, so two users have separate selections. To share a selection
between users, use a workspace scope without the user id and authorize each user's access to it.

</Step>
</Steps>

## Check it works

Save a selection, reload the page and confirm it returns. Switch to a different scope and confirm
the first scope's selection is absent. Switch back and check its saved record remains. Reject a
backend write and confirm the interaction reports failure instead of claiming it was saved.

## Errors

<Callout type="error" title="shared-state/unsupported-contract, before mount">

```text shared
well:selection: Shell schema lacks required consumer fields or constraints; reload after upgrading the shell schema
```

The shell's schema cannot satisfy the consumer's declared keys or fields. **Fix.** Deploy the compatible current schema with the shell before deploying consumers that require the added fields.

</Callout>

<Callout type="error" title="shared-state/invalid-value, at hydration">

```text shared
well:selection: Invalid stored record
```

A saved record does not match the current schema. **Fix.** Recover it explicitly on the backend. Preserve the invalid record until recovery succeeds.

</Callout>
