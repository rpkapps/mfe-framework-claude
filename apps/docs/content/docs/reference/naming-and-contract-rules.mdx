---
title: 'Naming and contract rules'
description: 'The rules ids, outputs, inputs and payloads must follow, and where each one is checked.'
---

Every name your container publishes is checked, most of them twice: once by the build, and once when your code runs. This page collects the rules and says where each is enforced.

## Definition ids

```ts
id: 'alert-panel'
```

Lower-case letters, digits and single hyphens. No leading, trailing or doubled hyphen, and nothing else. The id is also your storage prefix and your CSS scope value, so it has to be unambiguous in both.

| Rule                                    | Checked by                                              |
| --------------------------------------- | ------------------------------------------------------- |
| The character rule above                | the build, `createApp` and `createWidget`, the registry |
| One definition per id, in one container | the build                                               |
| One registry entry per id, in a shell   | the shell, which sets aside every conflicting entry     |
| At most one App per container           | the build                                               |

`@host` is the page's own scope name. The `@` is not a legal id character, so a definition can never claim it.

## Output names

```ts
outputSchema: z.object({
  acknowledged: z.object({ alertId: z.string() }),
  selectionChanged: z.object({ ids: z.array(z.string()) }),
})
```

Each property of `outputSchema` is one output, and its name follows the same rule. Lower camel case: a lower-case letter, then letters and digits. A consumer subscribes with `on` plus the name capitalised, so `acknowledged` arrives as `onAcknowledged`.

Two outputs must also map to two different handler props. The build names both outputs and asks you to rename one. Both rules run at build time and again in `createWidget`.

## Reserved input names

A Widget may not declare an input called `key`, `ref` or `fallback`, or any name matching `on` followed by a capital letter. Those belong to the consumer, which uses them to control the mount and to subscribe to outputs.

```ts
// Rejected: onSelect is an output handler's name.
inputSchema: z.object({ onSelect: z.string() })

// Accepted: declare the output instead.
inputSchema: z.object({ alertId: z.string() })
outputSchema: z.object({
  selected: z.object({ alertId: z.string() }),
})
```

The build checks the declared keys, and the mount boundary checks the parsed ones.

## Reserved router context keys

`mfe` and `queryClient` are the two keys an App forwards unchanged. Spread the context you were given and add your own top-level keys beside them. Do not replace either key, and do not add fields inside `mfe`.

## Action names

An action name is letters, digits and hyphens, starting with a letter, for example `refresh`. The runtime qualifies it internally, so the local name has to be unambiguous on its own. One mount may not register two actions with one name. `label` must not be empty, and `palette` is the only standard placement.

## JSON-only payloads

Everything that crosses the Widget boundary must survive JSON. That covers inputs and output payloads, in both directions.

| Allowed                   | Rejected                                       |
| ------------------------- | ---------------------------------------------- |
| strings, booleans, `null` | functions, class instances                     |
| finite numbers            | `NaN` and `Infinity`                           |
| plain objects and arrays  | `Date`, `Map`, `Set`, `RegExp`, `Error`        |
| an absent optional field  | DOM nodes, React elements, circular references |

A consumer that needs a callback subscribes to an output instead. A date crosses as an ISO string, which is what `examples/alert-panel` sends in `acknowledgedAt`.

<Callout type="error" title="contract/input-mismatch">

```text
expected a JSON-serializable value, received a function. A consumer that needs a callback subscribes to an output instead. Only JSON data crosses the boundary: no functions, class instances or DOM nodes.
```

**Fix.** Declare an output for what the callback was for, and emit it.

</Callout>

## Fields that must be written as literals

The build reads your entry module without running it, so anything published in the registry has to be readable from the source.

| Field                                                       | Where                       |
| ----------------------------------------------------------- | --------------------------- |
| `id`, `version`, `title`, `description`                     | `createApp`, `createWidget` |
| `tags`, as an array of non-empty string literals            | `createApp`, `createWidget` |
| `icon`, as an imported identifier or an imported `.svg`     | `createApp`, `createWidget` |
| `capability`, as `{ name, label, icon? }`                   | a route's `staticData`      |
| `inputSchema` and `outputSchema`, as top-level declarations | `createWidget`              |

A computed value fails the build with the file, the line and the column. A schema imported from another package fails too, because the generated contract module copies the declaration and can only copy one it can see.

The build also publishes `inputSchema` and `outputSchema` in the registry entry, as JSON Schema. There, a schema it cannot read does not fail the build. The build leaves it out instead:

| What you wrote                                             | What the registry entry carries                                |
| ---------------------------------------------------------- | -------------------------------------------------------------- |
| an `inputSchema` the build cannot read, like `.refine(…)`  | no `contract.inputSchema`. A host asks for the inputs as JSON. |
| a spread or a computed key in the `outputSchema` object    | no `contract.outputSchema`. A host cannot list your outputs.   |
| an output payload the build cannot read, like `.refine(…)` | that output with `{}`, shown as "payload not published".       |

Your Widget still validates every input and payload in all three cases. Only a host reading the registry knows less.

## Where definitions may be declared

`createApp` and `createWidget` calls are discovered in `src/mfe.ts` only, and every definition must be exported. A call in another module is never built into the container. A default export is accepted only when it is the container's only definition.
