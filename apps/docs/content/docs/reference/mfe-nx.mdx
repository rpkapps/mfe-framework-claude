`@company/mfe-nx` scaffolds and builds Angular containers in an Nx workspace. It is the Angular
counterpart of `pluginMfe()`: the same framework-neutral build, `@company/mfe-build`, wired into Nx's
Angular webpack builder instead of Rsbuild. Install it from your team's registry in an Nx consumer workspace in your own repository.
The shell runs independently and registers your generated container record. The framework repository's Fieldwork example is one sample consumer.

## Generate a container

```sh
# From your own Nx consumer workspace.
pnpm add -D @company/mfe-nx@^0.1.0
pnpm exec nx g @company/mfe-nx:app my-app --port 3101
pnpm exec nx g @company/mfe-nx:widget my-widget --port 3103
pnpm install
```

Select the compatible published framework release your team uses. The generator writes published dependency ranges and updates your consumer workspace's manifest.
It does not link framework source packages. For a new Nx workspace, follow the [quickstart](/docs/quickstart).

The workspace must be on Nx 20, 21 or 22. The generator refuses any other version before it writes a
file, because Nx 23's Angular plugin requires Angular 20.

| Option            | Default                         | What it is                                                     |
| ----------------- | ------------------------------- | -------------------------------------------------------------- |
| `name`            | —                               | The Nx project name.                                           |
| `id`              | the kebab-cased `name`          | The definition id, the federation name and the storage prefix. |
| `directory`       | `apps/<name>`                   | The project root.                                              |
| `port`            | `3101` (app) or `3103` (widget) | The dev server port.                                           |
| `packageName`     | `@example/<id>`                 | The generated project's own package name.                      |
| `tags`            | none                            | Comma-separated Nx project tags.                               |
| `skipFormat`      | `false`                         | Skip formatting the generated files.                           |
| `skipPackageJson` | `false`                         | Leave the workspace `package.json` alone.                      |

An `app` project holds `src/mfe.ts` with `createApp`, a route file with a capability route, a
configuration schema and `.mfe/runtime-config.json`, your local values. A `widget` project holds
`createWidget` with its contract exported separately. Both hold `src/primeng.ts`, a
`webpack.config.ts`, an `eslint.config.ts` against the Angular lint preset, and Vitest
configuration.

## The targets

| Target      | Runs                          | Does                                                         |
| ----------- | ----------------------------- | ------------------------------------------------------------ |
| `generate`  | `@company/mfe-nx:generate`    | Writes `.mfe/` and seeds `.mfe/runtime-config.json`.         |
| `build`     | `@nx/angular:webpack-browser` | Builds the remote, with `customWebpackConfig`.               |
| `serve`     | `@nx/angular:dev-server`      | Serves it on the project's port, open to the shell's origin. |
| `test`      | `nx:run-commands`             | `vitest run`.                                                |
| `typecheck` | `nx:run-commands`             | `tsc --noEmit` over the app and spec configurations.         |
| `lint`      | `nx:run-commands`             | `eslint .`.                                                  |

Every other target depends on `generate`, because the `#mfe/*` modules have to exist before webpack,
Vitest, `tsc` or ESLint can resolve them.

```sh
# From your own consumer workspace, using the generated project name.
pnpm exec nx run my-app:generate
pnpm exec nx build my-app
pnpm exec nx serve my-app
```

The generated project has Nx targets rather than package scripts. These targets run your container's build and dev server.
They do not build framework packages or start the shell. Hand the generated `mfe-registry.json` record and manifest URL to the shell owner.
The shell starts separately in its own repository.

## `withMfe()`

```ts title="webpack.config.ts"
import { withMfe } from '@company/mfe-nx/webpack'

export default withMfe()
```

The builder calls the exported function with the configuration Angular built. `withMfe()` adds one
plugin and replaces nothing you wrote. It plans the container from its sources before every
compile, adds the Module Federation 2 plugin, and makes the generated entry the only one. It scopes
the generated stylesheet with `@scope`, and `src/styles.css` with it. Component styles keep
Angular's own encapsulation. It also emits the registry entry, with `framework: 'angular'` and the
container's share scopes. In the dev server it answers `runtime-config.json` with your
`.mfe/runtime-config.json`, which no build copies, so a production build ships only the declared
defaults.

`withMfe({ shared })` adds share candidates. `withMfe({ containerRoot })` points it at a container
other than the project being built.

## What a container shares

| Group     | Scope                               | Packages                                                               |
| --------- | ----------------------------------- | ---------------------------------------------------------------------- |
| Framework | `angular@<installed @angular/core>` | the `@angular/*` packages, `@angular/cdk` and `rxjs`                   |
| Page      | `default`                           | `@company/mfe-core` and `@company/mfe-runtime`                         |
| Bundled   | —                                   | `@company/mfe-angular`, so it imports what the author's code imports   |
| Never     | —                                   | `primeng`, `@primeng/themes`, `@primeuix/styled` and `@primeuix/utils` |

No shared package is a singleton, because containers are released from repositories of their own.
A container takes the loaded copy its range accepts, and loads its own when none does, rather than
failing. Containers whose ranges agree download one copy, and a container on another Angular version
brings its own set. A package you add joins the Angular scope. An addition never removes or moves a
candidate, and `withMfe({ shared })` refuses PrimeNG.

## Versions

| Tool       | Version                                                    |
| ---------- | ---------------------------------------------------------- |
| Angular    | 19.2, zoneless, with no polyfills                          |
| TypeScript | 5.8, because Angular 19.2's compiler rejects 5.9 and later |
| PrimeNG    | 19.1.4, with no preset: the host declares its tokens       |
| Nx         | 20 to 22                                                   |
| Node       | 20.19 or later, or 22.12 or later                          |

Published framework packages contain compiled JavaScript and declarations. Consumer repositories install those artifacts and never include framework source in their `tsconfig`.

<Details summary="Framework maintainers using workspace links">

When testing unpublished packages inside the framework checkout, build them before using workspace links.
The framework repository's `pnpm release` builds packages before publishing. Each package's `prepack` refuses a missing or stale build.
These commands belong to the framework repository, not to an independent consumer workspace.

</Details>
