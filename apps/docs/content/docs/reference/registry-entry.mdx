title: 'Registry entry'
description: 'The entries your build writes, the entry a shell reads, and how a shell assembles them.'
---

Each container build publishes `mfe-registry.json` with its assets. It holds one registry entry per App or Widget the container exports, already in the shape a shell reads. Only `manifestUrl` is left relative, so your shell repository or registry service resolves it and appends the entries to the registry the shell reads.

## The entries your build writes

```json title="mfe-registry.json (published container artifact)"
[
  {
    "id": "alert-panel",
    "kind": "widget",
    "mfe": { "framework": "react" },
    "manifestUrl": "mf-manifest.json",
    "container": "example_alert_panel",
    "expose": "./widgets/alert-panel",
    "shareScopes": ["default", "react@19.3.0"],
    "requiresRuntime": ">=1.1.0 <2.0.0",
    "version": "1.4.0",
    "contract": {
      "inputSchema": { "type": "object", "properties": { "alertId": { "type": "string" } } },
      "outputSchema": {
        "type": "object",
        "properties": {
          "acknowledged": {
            "type": "object",
            "properties": {
              "alertId": { "type": "string" },
              "acknowledgedAt": { "type": "string" }
            }
          },
          "dismissed": { "type": "object", "properties": { "alertId": { "type": "string" } } }
        }
      }
    },
    "build": { "hash": "1e485caec528f7fa", "time": "2026-09-21T05:54:21.786Z" },
    "title": "Alert panel",
    "description": "Open alerts for one asset, acknowledged or dismissed in place.",
    "tags": ["alerts", "operations", "safety"],
    "icon": {
      "viewBox": "0 0 24 24",
      "node": [["path", { "d": "M10.268 21a2 2 0 0 0 3.464 0" }]]
    }
  }
]
```

Its type is `PublishedRegistryEntry`. A container that exports an App and a Widget writes two entries. They repeat the container's `mfe`, `manifestUrl`, `container`, `shareScopes`, `requiresRuntime` and `build`, and each has its own `expose`.

## The entry a shell reads

A shell reads the same entry with `manifestUrl` made absolute, such as
`https://containers.example.com/alert-panel/1.4.0/mf-manifest.json`, and with any presentation
overrides your shell applies.

| Field                                  | Required | What it is                                                                                                                 |
| -------------------------------------- | -------- | -------------------------------------------------------------------------------------------------------------------------- |
| `id`                                   | yes      | The definition id, under the usual character rule.                                                                         |
| `kind`                                 | yes      | `"app"` or `"widget"`.                                                                                                     |
| `mfe`                                  | yes      | `{ "framework": "react" }` or `{ "framework": "angular" }`. The marker picks the entry adapter.                            |
| `manifestUrl`                          | yes      | An absolute URL to the container's manifest.                                                                               |
| `container`                            | yes      | The federation container name. The runtime's loader registers the remote under it.                                         |
| `expose`                               | no       | The path the definition is published at. Defaults to `./app` or `./widgets/<id>`.                                          |
| `shareScopes`                          | no       | The share scopes the loader registers the remote with. Without it, only `default`.                                         |
| `version`                              | no       | Recorded in diagnostics.                                                                                                   |
| `requiresRuntime`                      | yes      | Generated stable SemVer comparator range; checked against `runtime.apiVersion` before adapter selection and shape parsing. |
| `capabilities`                         | no       | App-only. One record per marked route.                                                                                     |
| `routes`                               | no       | App-only. Every route the build could read, sorted by path. See below.                                                     |
| `contract`                             | no       | Widget-only. The `inputSchema` and `outputSchema`, each when the build could read it. See below.                           |
| `build`                                | no       | Repeated from the build's own record onto every entry it produced.                                                         |
| `hidden`                               | no       | `true` keeps the entry out of catalogue views. It is not a security boundary.                                              |
| `title`, `description`, `tags`, `icon` | no       | Presentation, so a catalogue can draw the definition unloaded.                                                             |

`contract.outputSchema` has the same shape as `contract.inputSchema`, and the same names as a tool's or an action's schemas. It is an object schema with one property per declared output, in declaration order. Each property holds the JSON Schema of that output's payload.

`runtime.apiVersion` and `requiresRuntime` are the single framework compatibility contract for
registry format, mount protocol and shell-owned services. Runtime incompatibility is refused
before adapter selection and registry shape parsing. Supported entries still require the framework
marker and the same registry and widget schema checks. The loaded definition is checked again
before mounting to cover a registry that points at newer container code.

Entries and definitions must both declare `requiresRuntime`. A missing or malformed requirement
fails with `registry/invalid-entry`. The runtime must declare its `apiVersion` too; no version is
assumed for missing metadata.

| What the build could not read | What the entry carries                                    |
| ----------------------------- | --------------------------------------------------------- |
| the `inputSchema`             | no `contract.inputSchema`                                 |
| one output's payload          | that output, with `{}` as its payload, meaning "anything" |
| the output names              | no `contract.outputSchema`                                |

A missing field means "unknown". An empty schema means the Widget takes or emits nothing. The Widget still validates every input and payload itself.

Read both schemas with [`describeInputs` and `describeOutputs`](/docs/reference/hooks-and-components#describeinputs-and-describeoutputs). Do not walk them yourself.

A capability is `{ name, label, path, icon? }`, where `name` is `settings`, `help` or `releaseNotes`. A shell skips a capability whose name it does not know and keeps the rest of the entry. Runtime API compatibility is checked separately; accepting a capability does not override a missing runtime API.

A route is `{ path, search? }`. `path` is App-relative and written the same way for every router: a parameter is `:name`, an optional one `:name?`, and a catch-all `*`. `search` is the JSON Schema of the search params the route reads, its parent routes' included. It is absent when the router declares none, as Angular's does not, or when the build could not read the schema. The shell uses `routes` to navigate, and to offer its agent the way to each page, before the App is loaded.

| Router          | What the build reads                                                                                                                                                                                       |
| --------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| TanStack Router | every `createFileRoute('<path>')` in the routes directory, and each route's and the root's `validateSearch`. Files the router's generator skips are skipped: a `-` prefix, a `*.test.*` or `*.spec.*` file |
| Angular         | every route with a component in the array `createApp` receives, through inline `children`                                                                                                                  |

A layout that adds no URL segment, a redirect and the `**` catch-all are not listed. The index route inside such a layout is. A parameter with a prefix or a suffix in its segment, such as `{$id}.json`, has no neutral spelling, so its route is not listed. Angular routes with a `matcher` or on a named outlet are not listed. Nor are the routes a lazy `loadChildren` module declares; the route that loads them is.

## How a published file becomes registry entries

Production assembly belongs to your platform or shell repository. Its release pipeline fetches each container's published `mfe-registry.json`. Container repositories need no checkout of the shell or framework source.

For each entry in the file, the integration:

1. Resolves `manifestUrl` against the URL the file was fetched from, including any path prefix.
2. Applies any shell-owned presentation overrides for that `id`.

It changes nothing else. For a file at `https://containers.example.com/alert-panel/1.4.0/mfe-registry.json`, `mf-manifest.json` resolves to `https://containers.example.com/alert-panel/1.4.0/mf-manifest.json`.

Publish every container's entries, concatenated into one array, at the registry URL your shell fetches. The shell uses its configured adapters to read that array. Updating a container artifact and updating this registry are separate release operations.

A file that holds an object rather than an array was written by a build before this format. Reject it and rebuild its container.

The framework supplies the entry format and registry reader. Your platform supplies production registration, storage and aggregation. There is no required production aggregator CLI or registration endpoint in this package.

### Framework demo harness

`tools/dev/build-registry.mjs` is the framework repository's example implementation. It scans local `examples/` projects and reads their `.mfe/mfe-registry.json` files. It resolves each `manifestUrl` against the container's development port, applies the overrides below, and writes `apps/shell/public/registry.json`.

That script also reads `apps/shell/registry.source.json` for demo presentation overrides and rejection fixtures. These paths and commands belong to the framework's combined demo harness. Independent container and shell repositories supply their own registry integration.

## Presentation overrides

A production registry integration can apply shell-owned presentation overrides keyed by definition id. Your platform decides where to store them. Generated ids, contracts and deployment URLs remain authoritative.

The framework demo stores its overrides in `apps/shell/registry.source.json`:

```json title="apps/shell/registry.source.json"
{
  "presentation": {
    "operations": { "title": "Operations", "icon": "OPS" },
    "alert-panel": { "title": "Alert panel" }
  }
}
```

This demo file is not a required production configuration file. Its presentation block overrides only wording and icons. Contract fields come from each container’s generated entries.

## Demo rejection fixtures

The framework demo’s `registry.source.json` also carries deliberately broken entries in `fixtures`. They exercise independent entry rejection. Production registry assembly should exclude these test fixtures.

```json title="apps/shell/registry.source.json"
{
  "fixtures": [
    {
      "id": "legacy-reports",
      "kind": "app",
      "mfe": { "framework": "react" },
      "requiresRuntime": ">=2.0.0 <3.0.0",
      "manifestUrl": "http://localhost:3106/mf-manifest.json",
      "container": "legacy_reports",
      "expose": "./app",
      "title": "Legacy Reports"
    }
  ]
}
```

The `legacy-reports` fixture requires runtime API `>=2.0.0 <3.0.0`, which the shell does not support,
and is rejected with `contract/runtime-incompatible` before its registry shape is parsed. The
`no-manifest` fixture declares no `manifestUrl` and is rejected with `registry/invalid-entry`.
