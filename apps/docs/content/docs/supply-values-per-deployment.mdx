---
title: 'Supply values per deployment'
description: 'Publish runtime-config.json beside your container assets, one file per environment.'
---

`runtime-config.json` belongs to your container deployment. Build and publish that container from its own repository and CI pipeline. The build ships the file with your declared defaults only. Your deployment writes its
values into it, and your container reads it at load time.

## Steps

<Steps>

<Step>

### 1. Write the file for local development

```json shared title="Illustrative container: .mfe/runtime-config.json"
{
  "apiBaseUrl": "http://localhost:3010/api/",
  "telemetryEnabled": false
}
```

A flat object of values, which your dev server answers `runtime-config.json` with and no build
copies. Your React generation script or Angular project target seeds defaults and preserves existing values.

</Step>

<Step>

### 2. Hand the deployment the names

```bash shared title="Illustrative container: .mfe/.env.example (generated, trimmed)"
# apiBaseUrl: a string in uri form
# Declares an API origin: its origin joins this container's authentication allowlist.
# Required.
API_BASE_URL=

# telemetryEnabled: true or false
# Optional. Defaults to true.
TELEMETRY_ENABLED=
```

The build writes this file from your declarations, with every name and expectation, and never a
value.

</Step>

<Step>

### 3. Validate the file before release

```json shared title="Illustrative container: .mfe/runtime-config.schema.json (generated, trimmed)"
{
  "type": "object",
  "properties": {
    "apiBaseUrl": { "type": "string", "format": "uri" }
  },
  "required": ["apiBaseUrl"],
  "additionalProperties": false
}
```

Validate the deployment's file against this schema before release, because it lists every required
field and rejects a key you did not declare.

</Step>

</Steps>

## Keep your local values committed

`.mfe/runtime-config.json` is the one file in `.mfe/` you commit. Ignore `.mfe/*` rather than
`.mfe/`, and add `!.mfe/runtime-config.json`, as a scaffolded container's `.gitignore` already does:
a directory pattern stops git looking inside, so no exception could apply. The build's own
`.mfe/.gitignore` makes the same exception.

`runtimeConfigFileName` in `pluginMfe()` or `withMfe()` renames the published file, and the dev
server then answers with `.mfe/<that name>`. The generate command does not read your bundler
config, so it neither seeds that file nor excepts it in `.mfe/.gitignore`. Create it yourself and
commit it once with `git add -f`; git keeps tracking it after that.

Earlier versions kept the file in `public/`, which every build copies into its output. The next
container generation moves it to `.mfe/` byte for byte, and says so. If both exist it leaves both and
warns that the `public/` copy is no longer read and can now ship in production: delete it.

## Package your container's release artifact

Run these commands in your container repository's CI. Framework packages and contract packages are installed from your registry through the repository's lockfile.
For Angular, replace `orders` and `apps/orders` with your Nx project name and root.

<Tabs items={['React', 'Angular']} defaultValue="React">
<Tab value="React">

```sh title="React container CI"
# Run from the React package directory, such as apps/field-notes.
pnpm install --frozen-lockfile
pnpm run build
mkdir -p image-context/assets
cp -R dist/. image-context/assets/
cp .mfe/runtime-config.sh image-context/runtime-config.sh
```

</Tab>
<Tab value="Angular">

```sh title="Angular container CI"
pnpm install --frozen-lockfile
pnpm exec nx build orders --configuration=production
mkdir -p image-context/assets
cp -R dist/apps/orders/. image-context/assets/
cp apps/orders/.mfe/runtime-config.sh image-context/runtime-config.sh
```

</Tab>
</Tabs>

The scaffold uses these output paths. If you change the bundler's output directory, stage that directory instead.
For React, these paths are relative to the package directory; for Angular, they are relative to the Nx workspace root. Upload `image-context/` from that directory as the release artifact. It contains this container's built assets and generated configuration script.
The framework development workspace and demo backend are not part of the artifact.

## Run the artifact in a Docker image

Build this image from the downloaded `image-context/` artifact. The generated script needs `sh` and `awk`.
The official nginx image runs executable scripts in `/docker-entrypoint.d/` before serving assets.

```dockerfile shared title="Illustrative release artifact: Dockerfile"
FROM nginx:alpine
COPY assets/ /usr/share/nginx/html/
COPY runtime-config.sh /docker-entrypoint.d/40-mfe-runtime-config.sh
RUN chmod +x /docker-entrypoint.d/40-mfe-runtime-config.sh
```

```sh shared title="Release image"
docker build -t my-container image-context/
docker run -e API_BASE_URL=https://api.example.com/ -e TELEMETRY_ENABLED=false my-container
```

Include this Dockerfile in `image-context/` before building. Each environment runs the same image with its own values.

When the container starts, the script:

| Case                                   | What it writes                                                        |
| -------------------------------------- | --------------------------------------------------------------------- |
| the variable is set                    | that value, typed by its schema: `false` is a boolean, `25` a number  |
| the variable is unset or empty         | the value already in the file, which is the default the build shipped |
| a required variable has no value       | nothing: the container exits with the variable's name                 |
| a value has the wrong shape            | nothing: the container exits, naming the variable and the value       |
| a nullable field gets the value `null` | `null`                                                                |
| an array or object field               | the variable's text as JSON, for example `HOSTS='["a.example.com"]'`  |

The script checks booleans, numbers and enum members. The browser still validates every value
against your full schema, formats and bounds included.

The startup script replaces `runtime-config.json` using a temporary file and rename, so the served
directory and target must be writable. For a Kubernetes ConfigMap, copy its file into the writable
served directory before running the script. Alternatively, serve the mounted file directly and
skip the startup script; deployment variables will then not modify that file.

Another server works as well. Run the script before the server starts and pass it the served
directory, as in `runtime-config.sh /srv/www`, or set `MFE_RUNTIME_CONFIG_DIR`. Without either, it
writes to `/usr/share/nginx/html`. It has to be able to write there, so an unprivileged nginx image
needs that directory owned by its user.

## Check it works

Start your own container's dev server and open its `runtime-config.json` URL. It answers
with `.mfe/runtime-config.json`, the values your App will read, and reads the file again on every
request. A container scaffolded as a Widget has no configuration, so run its generation script or Nx project target after adding `src/mfe.config.ts`. In a deployment the values are a snapshot, so
changing one takes a new deployment and a page reload.

## Errors

<Callout type="error" title="runtime-config.sh: … is required">

```text shared
runtime-config.sh: API_BASE_URL is required (apiBaseUrl: a string in uri form). Set it on the container.
```

**Fix.** Set the variable on the container, for example with `docker run -e API_BASE_URL=…`. The
container stops at start so the browser never loads a file with the value missing.

</Callout>

<Callout type="error" title="config/missing">

```text shared
operations failed to load its runtime configuration: expected a file at
http://localhost:3001/runtime-config.json, received 404 Not Found.
```

**Fix.** Publish the file next to the container's assets. In development, run your React container's generation script or Angular project's generation target, then reload.

</Callout>

<Callout type="error" title="config/unreachable">

```text shared
operations failed to load its runtime configuration: expected a 200 response from
http://localhost:3001/runtime-config.json, received 503 Service Unavailable.
```

**Fix.** Check how the deployment serves the file. A container cannot start without its
configuration, and nothing retries in the background.

</Callout>

<Callout type="error" title="config/invalid">

```text shared
operations failed to read its runtime configuration: expected a JSON object of configuration
values, received a body that is not JSON.
```

**Fix.** Check what the deployment wrote. A server that answers an error page with status 200
lands here.

</Callout>

## In a host

A host, the shell that loads the containers, gets the same files: declare its values in its own
`src/mfe.config.ts`, add `pluginMfeHostConfig()` from `@company/mfe-rspack` to its Rsbuild config,
and give that shell repository its own `generate` script of `mfe-generate --host`. Its `#mfe/config` is read the same way and
fails the same way, but validates without Zod: a host reads its configuration before anything else
on the page loads, so the generated module checks each value against the JSON Schema the build
derived from your declaration, and the declarations reach it as a type only. The build already
refuses any schema it cannot read that way, so both kinds of module accept exactly the same values.

A host's module also reports a missing file served as `index.html` with a 200 as missing, and
fetches with same-origin credentials, so a `<link rel="preload" as="fetch" crossorigin>` for the
file in the host document answers it.
