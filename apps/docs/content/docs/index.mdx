These pages are for the developer who has been handed a piece of a product to build and told it
will be loaded into somebody else's page. You already know React and TanStack Router. You do not
need to know anything about micro-frontends: everything below the React you are used to writing is
what this documentation covers.

A <Term>micro-frontend</Term> is a piece of a single web page that is built, versioned and deployed
on its own, by its own team, and is loaded into a page it does not own at run time. There are no
iframes here: the page is one browser document with one React tree, and your code renders inside it
beside code from other teams.

Three words appear on every page after this one.

- A <Term>container</Term> is one deployable unit: a package with its own build, its own port in
  development, its own deployed origin, and one `src/mfe.ts` entry. What you build and ship is a
  container.
- The <Term>shell</Term> is the one application on the page that is not itself listed in the
  registry. It fetches the registry, owns the document — header, theme, session, the routes above
  your boundary — and mounts containers into itself. "Host" is the general word for that role;
  `apps/shell` is this repository's.
- The <Term>registry</Term> is a JSON array the shell fetches at boot, saying which definitions
  exist, where each container's manifest is, and what each Widget takes. It is generated by the
  build, never hand-written.

## The two things you can build

Apps take URLs. Widgets take props. Anything that cannot be expressed as a URL is a Widget, not an
App.

### An App takes a URL

An <Term>App</Term> is a routable, independently deployable product surface. It owns a stretch of
the URL and routes everything below it with its own TanStack Router instance. One container exports
at most one App.

```ts title="examples/operations/src/mfe.ts (trimmed)"
function makeRouter({ basePath, history, context }: AppRouterOptions) {
  return createRouter({
    routeTree,
    basepath: basePath,
    history,
    context: { ...context },
  })
}

export default createApp({ id: 'operations', version: '2.1.0', router: makeRouter })
```

### A Widget takes props

A <Term>Widget</Term> is a non-routable, independently mountable embedded surface. It owns no URL,
takes props from whoever renders it, and tells that consumer what happened by emitting a declared
event. One container may export any number of Widgets.

```ts title="examples/alert-panel/src/mfe.ts (trimmed)"
export const alertPanel = createWidget({
  id: 'alert-panel',
  version: '1.4.0',
  inputs: z.object({ alertId: z.string() }),
  events: { acknowledged: z.object({ alertId: z.string() }) },
  render: AlertPanel,
})
```

Both calls return a <Term>definition</Term>: a plain, side-effect-free descriptor that the build
reads statically and the shell loads and mounts. Neither is a component, and neither runs anything
when the module is evaluated.

## The reading order

The ten guides are in order, one line each.

1. [The shape: App or Widget](/docs/guides/shape) — whether the surface you are building takes a
   URL or takes props, and what that choice decides.
2. [Declaring it](/docs/guides/declaring) — the definition file that tells the shell what you
   built, and how the build turns it into a container.
3. [Configuration and data](/docs/guides/config-and-data) — per-deployment values through the
   generated config module, and calls to your API through the container transport.
4. [What the shell gives you](/docs/guides/what-the-shell-gives-you) — identity, theme,
   breadcrumbs, commands, telemetry and storage: the services a mounted container calls without
   importing anything from the shell.
5. [What you must not do](/docs/guides/what-you-must-not-do) — the page is shared, so these are the
   moves that break the containers around you.
6. [Lifecycle](/docs/guides/lifecycle) — what happens to your App or Widget between the moment the
   shell needs it and the moment it is gone.
7. [Storage](/docs/guides/storage) — scoped keys, retention, and what survives a reload, a sign-out
   and another user on the same browser.
8. [Styling](/docs/guides/styling) — why a shared page needs a CSS boundary, what the shell owns at
   document level, and what your container's build does to the stylesheet it generates for you.
9. [Daily workflow](/docs/guides/daily-workflow) — scaffolding a container, generating its modules,
   running it against the shell, keeping hot updates working, and the checks to run before you push.
10. [Shipping and failures](/docs/guides/shipping-and-failures) — what a container build produces,
    how its record reaches the shell's registry, every reason an entry is quarantined, and how to
    read the failures your users will see.

Read 1 to 4 before you write anything. The rest answer themselves when the need arises.

## Where the rest is

The [design map](/docs/design) is the picture of the whole system: the packages, the deployed
topology, the boot sequence and the boundaries between one container and the rest of the page. Read
it when you want to know why a piece exists rather than how to call it.

The [glossary](/docs/glossary) defines every term in one place. Each guide also defines its terms
where it uses them, so you never have to read the glossary first.

The [decisions](/docs/decisions) log is the record of why the framework is shaped the way it is,
including the failures that shaped it. Guides link into it wherever a rule has a reason worth
reading.
