## What is deployed, and where

<Diagram
  src="/diagrams/system-at-rest.svg"
  alt="The shell origin with its registry, three container origins, the files every container publishes, the API and the browser page."
  caption="What is deployed where, before anyone opens the page."
>
Eleven boxes, read left to right.

- **The shell origin**, on `http://localhost:3000` in development, holds `index.html` and
  `registry.json`, which carries one record per definition.
- An arrow **manifestUrl** reaches **Three container origins**: `operations` (an App, `:3001`),
  `alert-panel` (one Widget, `:3003`) and `insights` (three Widgets, `:3004`).
- An arrow **publishes** reaches **Every container publishes**, holding `mf-manifest.json`,
  `remoteEntry.js`, `styles.css` and `runtime-config.json`.
- An arrow **names the API** drops from `runtime-config.json` to **The API**, on `:3010` in
  development, serving `GET /api/assets`.
- **The browser page** sits at the bottom left, one document from the shell origin. An arrow
  **served from** points up to the shell origin, and **fetched into** points down from the
  published files. A legend names the five colours.

</Diagram>

Your container is a deployment of its own, with its own build, version and origin. It publishes
four files: `mf-manifest.json`, `remoteEntry.js`, `styles.css` and `runtime-config.json`. The shell
is a separate deployment, and it serves the page. At boot it fetches one `registry.json` holding one
record per App or Widget. Your build writes your record, so nobody hand-writes that JSON. The page
stays one browser document, and there is no iframe. Your App or Widget renders in a React root of
its own inside it. Your API is a third
deployment. `runtime-config.json` names its URL, so moving the API is a deployment rather than a
rebuild.

## What happens between a page load and your App

<Diagram
  src="/diagrams/boot-to-mount.svg"
  alt="Seven numbered steps from the shell booting to a rendered App, with two panels of failure codes."
  caption="Page load to a rendered App, in the order the code runs."
>
Twelve boxes: seven numbered steps in two columns, and five error codes.

- The left column is **In the shell**, `apps/shell/src/boot.tsx`. It holds **1. The document
  boots**, **2. Diagnostics, then session** (`installShellAuth`), **3. The registry arrives**
  (`await fetch('/registry.json')`) and **4. Runtime reads the registry**.
- An arrow carries step 4 into the right column, **In the framework**, the adapter and then the
  runtime.
- That column holds **5. URL picks the boundary**
  (`<AppHost appId='operations' basePath='/operations'>`), **6. The container loads once**
  (`mountDefinition`, then `loadRemote('operations/app')`) and **7. The App mounts itself**, in its
  own React root.
- A red arrow **rejects** leaves step 6 for **When step 6 fails**: `load/manifest-failure`,
  `load/entry-failure` and `load/timeout`.
- A red arrow **rejects** leaves step 7 for **When step 7 fails**, drawn with a Retry:
  `app/invalid-base-path` and `app/invalid-router`.

</Diagram>

The shell boots first. It builds its diagnostics, installs the page's one session, then fetches
`registry.json`. Nothing of yours has run yet, because your code is not in the shell's build. The
URL then picks a boundary. At `/operations/wells` the shell mounts the App whose id is `operations`
and hands it `/operations` as its base path. The framework loads your container once per page and
checks the definition `src/mfe.ts` exports. It creates the mount and its roots, and your App opens
its own React root and renders your router. A container that will not load within 30 seconds fails
as `load/timeout`. Any failure costs that one region. The chrome stays, the other Apps stay
reachable, and the person sees your failure message and a Retry button.

## The packages you import, and the one you configure

<Diagram
  src="/diagrams/layers.svg"
  alt="The framework packages, which way their imports point, and what the build plugin generates."
  caption="The packages, which way the imports point, and who sees them."
>
Twelve boxes in two regions.

- **In the browser**, where an arrow points at what a package depends on. `apps/shell` and
  `examples/operations` both point at `@company/mfe-react`. The three adapters,
  `@company/mfe-react`, `@company/mfe-angular` and `@company/mfe-legacy-angular`, each point at
  `@company/mfe-runtime`, which points at `@company/mfe-core`.
- A line under that graph names what sits beside it: `@company/create-mfe`,
  `@company/eslint-plugin-mfe` and `@company/mfe-devtools`.
- **At build time**, one integration per framework and one neutral layer. `@company/mfe-rspack`
  (`pluginMfe()`, for React) and `@company/mfe-nx` (`withMfe()`, for Angular) both point at
  `@company/mfe-build`, which **generates** `#mfe/config, #mfe/fetch` and the `.mfe/` entries and
  stylesheet.
- A green dot marks what an author writes or imports: `examples/operations`, `@company/mfe-react`,
  `@company/mfe-angular` and `#mfe/config, #mfe/fetch`. The legend names the four colours and the
  dot.

</Diagram>

You import from `@company/mfe-react` and from nothing else in the framework. Everything an author
needs is re-exported there, types included, and lint blocks the rest. Tests import
`@company/mfe-react/testing`, and a shell imports `@company/mfe-react/host`.
`@company/mfe-runtime` and `@company/mfe-core` sit under it and hold no React. Your build adds one
line, `pluginMfe()` in `rsbuild.config.ts`. It composes `@company/mfe-build`, the half of the
build every framework shares, and generates `#mfe/config`, `#mfe/fetch`, `#mfe/meta`, your container
entries and your scoped stylesheet. You write `src/mfe.ts`, the routes under `src/routes/`,
`src/mfe.config.ts` and that plugin line. Everything under `.mfe/` is generated, and the next build
overwrites it.

## How the adapters fit together

<Diagram
  src="/diagrams/adapters.svg"
  alt="The shell's registry entering the neutral runtime, the three adapters the shell lists, and the container each one reaches."
  caption="One neutral runtime, and the adapters the shell lists."
>
Ten boxes, read top to bottom.

- **The shell** sits at the top and lists
  `adapters: [reactAdapter, angularAdapter, legacyAngularAdapter]`. An arrow **registry.json**
  enters **The neutral runtime**, `@company/mfe-runtime`, which imports no framework and no
  federation.
- The runtime holds **Shared services** (storage, actions, navigation, diagnostics), **Federation
  loader** and **One mount path**, `mountDefinition`.
- An arrow **detect, parse** drops into **The adapters**, where exactly one recognises each entry:
  the React adapter, the Angular adapter and the removable legacy Angular adapter.
- An arrow **defines, mounts** drops from the React adapter to `operations` and from the Angular
  adapter to an Nx container. A dashed arrow **entries only** drops from the legacy adapter to
  `asset-tracker`, which is not mounted yet. The legend names the shell, a neutral package, an
  adapter package and a container.

</Diagram>

A neutral runtime reads the registry and offers each entry to every adapter the shell lists. Exactly
one adapter must recognise it. Your entry names the framework your container was built with, so the
React adapter reads it. The runtime then loads your container and calls your definition's own
`mount`, which renders it in a React root of its own. An Angular container is read by the Angular
adapter and mounted the same way, so a React page and an Angular container meet only in the
runtime. An existing single-spa Angular application names no framework, and a removable legacy
adapter reads it. Nothing falls back on its own. An entry that names a framework stays with that
framework's adapter, even when a field in it is wrong, and it is set aside with a reason. Storage,
actions, navigation and diagnostics come from the runtime, so every kind behaves alike.
