---
title: 'Version your container and its contract'
description: 'The versions a container carries, and which changes break the people who render you.'
---

Import your container's version from `package.json` so each release needs one version update.
The build also adds a runtime requirement, which decides whether the shell loads you.

## Steps

| Version           | Where you set it                                                           | What it does                                         |
| ----------------- | -------------------------------------------------------------------------- | ---------------------------------------------------- |
| release version   | `"version"` in the container's `package.json`, imported by each definition | names your build in diagnostics and registry entries |
| runtime API range | generated from the build integration's compatibility metadata              | decides whether the shell can read and mount you     |

<Steps>

<Step>
### 1. Import the package version

<Tabs items={['React', 'Angular']} defaultIndex={0}>
<Tab value="React">

```ts title="Illustrative src/mfe.ts (trimmed)"
import packageJson from '../package.json'

export default createApp({
  id: 'operations',
  version: packageJson.version,
  router: makeRouter,
})
```

</Tab>
<Tab value="Angular">

```ts title="Illustrative src/mfe.ts (version example)"
import { createApp } from '@company/mfe-angular'
import packageJson from '../package.json'
import { AppComponent } from './app.component'
import { routes } from './app.routes'

export const fieldwork = createApp({
  id: 'fieldwork',
  version: packageJson.version,
  component: AppComponent,
  routes,
})
```

Angular supplies `component` and `routes`. The version names this release in diagnostics and registry entries.

</Tab>
</Tabs>

Use `version: packageJson.version` on every App and Widget in the container.
The build reads the JSON directly, and diagnostics name the same release, such as `operations@2.1.0`.
Enable `resolveJsonModule` in your TypeScript configuration if your project does not already allow JSON imports.
The generators enable it for you.

Named imports also work: `import { version } from '../package.json'`, followed by `version` in the definition options.
Existing inline version strings remain supported.

</Step>

<Step>
### 2. Update the package version for each release

<Tabs items={['React', 'Angular']} defaultIndex={0}>
<Tab value="React">

```json title="Illustrative package.json (trimmed)"
{
  "name": "@your-org/operations",
  "version": "2.1.0"
}
```

</Tab>
<Tab value="Angular">

```json title="Illustrative package.json (version example)"
{
  "name": "@your-org/fieldwork",
  "version": "2.1.0"
}
```

</Tab>
</Tabs>

Update only `package.json` when you release. Every definition importing it uses the new version in registry entries and diagnostics.
Release this repository independently. Pin published framework and build-integration versions, commit the lockfile, and build against that installed set.

</Step>

<Step>
### 3. Leave the runtime requirement to the framework

```json title="Illustrative .mfe/mfe-registry.json (trimmed)" shared
{ "requiresRuntime": ">=1.1.0 <2.0.0" }
```

The build writes this range from its compatibility metadata. The range shown is illustrative.
The shell checks it against the API version of its installed runtime. One API version covers the registry format, mount protocol and shell-owned services.
The check runs before the shell chooses an adapter or reads the rest of the entry. The
`mfe.framework` marker still names the adapter, and Widget schemas still validate values.

The shell checks the loaded definition again before mounting, in case the container changed after
the registry was written. React and Angular adapters check too, including in a shell that has no
check of its own.

A backward-compatible change to the format, mount protocol or services raises the API minor. An
incompatible change raises its major. Package versions are separate: a newer runtime package
cannot replace the object the shell already created.

The definition helpers and build integrations write the same framework requirement. A container
profile cannot override it. Every entry and definition needs `requiresRuntime`, and the runtime
helper supplies `apiVersion`. Missing metadata is an error.

The range reader accepts `>=`, `>`, `<=`, `<`, `=` or an exact version, joined with spaces. It
accepts no prereleases, caret/tilde ranges, wildcards or alternatives. Build metadata does not
change the comparison.

</Step>

<Step>
### 4. Decide whether a change breaks your consumers

The runtime requirement applies to Apps and Widgets. A Widget also checks the actual inputs and
output payloads with Zod. Before mounting, the host checks that each output name in the consumer's
imported contract still exists. It does not compare input schemas in advance.

| Change to a Widget contract  | What a consumer gets                                                        |
| ---------------------------- | --------------------------------------------------------------------------- |
| a new optional input         | nothing. Its inputs still pass                                              |
| a new output                 | nothing, until it handles the new name                                      |
| an output removed or renamed | a consumer contract that expects it fails before mounting                   |
| a new required input         | a mount fails if the values sent omit it; a later invalid update is refused |
| a tighter input schema       | the same failure when a value sent no longer passes the schema              |
| a new definition id          | a different definition. Its stored records stay under the old id            |

Ship any of the four breaking rows under a new name: a new output, a new input, or a new id.

</Step>

</Steps>

## Check it works

Open the developer tools' **Registry** tab. Each loaded entry prints its id with the version you
imported from `package.json`. Change only that version and rebuild to check the registry updates.
Make one of your screens fail on purpose, and the message names the same
`<id>@<version>` pair.

## Errors

<Callout type="error" title="failed to read the definition version">

```text shared
src/mfe.ts:44:3: 'operations' failed to read the definition version: expected a plain string
literal or a version imported directly from package.json, found getVersion().
```

**Fix.** Import `packageJson` directly from `../package.json` and use `version: packageJson.version`.
Set a non-empty version string in that JSON. Arbitrary runtime expressions cannot be read during the build.

</Callout>

<Callout type="error" title="contract/runtime-incompatible">

```text shared
operations failed to check shell runtime compatibility: expected runtime API >=1.1.0 <2.0.0,
received runtime API 1.0.0.
```

**Fix.** Upgrade and reload the shell, or rebuild the container against the API the shell provides.
Retry cannot add an API the shell lacks. The other Apps and Widgets keep running.

</Callout>
