---
title: 'Version your container and its contract'
description: 'The versions a container carries, and which changes break the people who render you.'
---

Your definition and package each have a version. The build adds a runtime requirement, which
decides whether the shell loads you at all. Apps and Widgets carry the same three.

## Steps

| Version            | Where you set it                                              | What it does                                      |
| ------------------ | ------------------------------------------------------------- | ------------------------------------------------- |
| definition version | `version` on `createApp` or `createWidget`                    | names your build in every message and every entry |
| package version    | `"version"` in the container's `package.json`                 | your own release record. No entry carries it      |
| runtime API range  | generated from the build integration's compatibility metadata | decides whether the shell can read and mount you  |

<Steps>

<Step>
### 1. Write the definition version inline

```ts title="examples/operations/src/mfe.ts (trimmed)"
export default createApp({
  id: 'operations',
  version: '2.1.0',
  router: makeRouter,
})
```

It has to be a plain string literal, and every message about this App then names it as
`operations@2.1.0`.

</Step>

<Step>
### 2. Move the package version with it

```json title="examples/operations/package.json (trimmed)"
{
  "name": "@example/operations",
  "version": "2.1.0"
}
```

The registry entry carries the definition version alone, and nothing checks that these two agree.

</Step>

<Step>
### 3. Leave the runtime requirement to the framework

```json title="examples/alert-panel/.mfe/mfe-registry.json (trimmed)"
{ "requiresRuntime": ">=1.1.0 <2.0.0" }
```

The build writes this range, and the shell checks it against `runtime.apiVersion`, currently
`"1.1.0"`. One API version covers the registry format, mount protocol and shell-owned services.
The check runs before the shell chooses an adapter or reads the rest of the entry. The
`mfe.framework` marker still names the adapter, and Widget schemas still validate values.

The shell checks the loaded definition again before mounting, in case the container changed after
the registry was written. React and Angular adapters check too, including in a shell that has no
check of its own.

A backward-compatible change to the format, mount protocol or services raises the API minor. An
incompatible change raises its major. Package versions are separate: a newer runtime package
cannot replace the object the shell already created.

If you write a build integration, set `ContainerProfile.requiresRuntime` to a stable comparator
range such as `>=1.1.0 <2.0.0`. The reader accepts `>=`, `>`, `<=`, `<`, `=` or an exact version,
joined with spaces. It accepts no prereleases, caret/tilde ranges, wildcards or alternatives.
Build metadata does not change the comparison.

Missing `requiresRuntime` uses `>=1.0.0 <2.0.0`; a runtime without `apiVersion` reads as `1.0.0`.

</Step>

<Step>
### 4. Decide whether a change breaks your consumers

| Change to a Widget contract  | What a consumer gets                                                     |
| ---------------------------- | ------------------------------------------------------------------------ |
| a new optional input         | nothing. Its inputs still pass                                           |
| a new output                 | nothing, until it handles the new name                                   |
| an output removed or renamed | a consumer contract that expects it fails before mounting                |
| a new required input         | an old consumer contract fails before mounting; values are still checked |
| a tighter input schema       | the same failure when the checker can compare the change                 |
| a new definition id          | a different definition. Its stored records stay under the old id         |

Ship any of the four breaking rows under a new name: a new output, a new input, or a new id.

</Step>

</Steps>

## Check it works

Open the developer tools' **Registry** tab. Each loaded entry prints its id with the version you
declared. Make one of your screens fail on purpose, and the message names the same
`<id>@<version>` pair.

## Errors

<Callout type="error" title="failed to read the definition version">

```text
src/mfe.ts:44:3: 'operations' failed to read the definition version: expected a plain string
literal, found pkg.version.
```

**Fix.** Write the version inline, as `version: '2.1.0'`. The build reads it without running your
code, so a computed version cannot be read at all.

</Callout>

<Callout type="error" title="contract/runtime-incompatible">

```text
operations failed to check shell runtime compatibility: expected runtime API >=1.1.0 <2.0.0,
received runtime API 1.0.0.
```

**Fix.** Upgrade and reload the shell, or rebuild the container against the API the shell provides.
Retry cannot add an API the shell lacks. The other Apps and Widgets keep running.

</Callout>
