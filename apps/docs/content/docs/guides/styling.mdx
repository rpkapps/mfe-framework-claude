title: '8. Styling'
description: 'What your build does to your CSS, the three roots a mount renders, and the styling errors you will see.'
---

You write no CSS configuration in a container: no stylesheet entry, no `postcss.config`, no theme
variables. Your build collects the classes you rendered, generates one <Term>scoped stylesheet</Term>,
and wraps it in a CSS `@scope` rule keyed on your [definition id](/docs/glossary). Your rules then
apply inside your
own mount roots and nowhere else.

## What you write, and what the build generates

You write TSX, and the build generates everything else.

| You write                           | The build generates                                           | Where it lands                                 |
| ----------------------------------- | ------------------------------------------------------------- | ---------------------------------------------- |
| TSX with Tailwind classes           | the utilities those classes need, and nothing else            | `.mfe/styles.css`, imported by every entry     |
| no `postcss.config`                 | `@tailwindcss/postcss`, then the container scope plugin       | your Rsbuild config, appended by `pluginMfe()` |
| no `@scope` rule                    | `@scope ([data-mfe-scope="<id>"]) to ([data-mfe-scope])`      | around every rule in the generated stylesheet  |
| no reset, no fonts, no theme values | nothing: the shell's document half inherits into your subtree | `apps/shell/src/styles/app.css`                |
| no overlay wiring                   | a style root component, when you depend on `@tecton/react`    | `.mfe/entries/style-root.tsx`                  |

The shell owns the document half of the page's CSS, and your container owns the rest.

| The shell's half, page-wide                | Your half, inside your scope                    |
| ------------------------------------------ | ----------------------------------------------- |
| the preflight reset                        | the utilities your own classes need             |
| `@font-face`, `--font-sans`, `--font-mono` | the design system's scoped entry, if you use it |
| Tailwind's `@property` registrations       | the `@scope` rule wrapped around both           |
| the theme variables on `:root`             | your `@keyframes`, renamed after your ids       |

Everything in the shell's half inherits into every mounted subtree. A theme flip or a tenant
customisation made once in the shell reaches every container with nothing wired up. Fonts arrive the
same way: the shell declares them, and you read `--font-sans` and `--font-mono`.

### The stylesheet your build writes

Generation writes `.mfe/styles.css`, and every generated federation entry imports it. For a
container that depends on `@tecton/react`, this is the whole file:

{/* prettier-ignore */}
```css title="examples/alert-panel/.mfe/styles.css (generated)"
/**
 * Generated by @company/mfe-rspack. Do not edit: the next build overwrites it.
 */

/*
 * Tailwind, split: the theme and the utilities, and deliberately not
 * `@import "tailwindcss"`, which would also bring preflight. The reset
 * belongs to whoever owns the document, and that is the shell — along
 * with the fonts, which reach this container through --font-sans and
 * --font-mono like any other inherited value.
 */
@layer theme, base, components, utilities;
@import "tailwindcss/theme.css" layer(theme);
@import "tailwindcss/utilities.css" layer(utilities);

/*
 * The design system's scoped entry: utilities only, no variables, so
 * nothing here redeclares what the shell's :root already says.
 */
@import "@tecton/react/styles/scoped.css";

/*
 * What Tailwind scans. Splitting the imports above turns automatic source
 * detection off, so every directory holding classes this container renders
 * has to be named here — the library scans its own. The one entry
 * below covers the whole of this container's `src/`; nothing under
 * node_modules needs scanning.
 */
@source "../src/**/*.{ts,tsx}";
```

`pluginMfe()` appends to your Rsbuild configuration and never replaces it. It skips
`@tailwindcss/postcss` when your own config already declares a plugin whose name contains
`tailwindcss`. Tailwind runs first either way, because scoping before the utilities exist would
scope nothing. The design system's scoped entry appears only while `@tecton/react` is in your
dependencies, so keep the dependency.

### The `@scope` rule

```ts title="packages/mfe-rspack/src/css/scope.ts"
const SCOPE_ATTRIBUTE = 'data-mfe-scope'

return loadScopePlugin(options.containerRoot)({
  scope: scopes.map(id => `[${SCOPE_ATTRIBUTE}="${id}"]`).join(', '),
  boundary: `[${SCOPE_ATTRIBUTE}]`,
  keyframes: { suffix: scopes.join('-') },
})
```

`scopes` is every definition id the container exports, so `examples/alert-panel` emits one rule:

{/* prettier-ignore */}
```css
@scope ([data-mfe-scope="alert-panel"]) to ([data-mfe-scope])
```

A container exporting four Widgets, like `examples/insights`, emits one rule whose start selector
lists all four ids. Three more things happen to the sheet.

- Document-global at-rules are hoisted out of the scope unchanged: `@charset`, `@import`,
  `@property`, `@font-face`, `@keyframes` and bodiless `@layer a, b;` statements.
- Every `@keyframes` your sheet defines is renamed to `<name>--<your ids joined by hyphens>`, and
  the references in `animation`, `animation-name` and `--animate-*` are rewritten to match. A name
  your sheet does not define belongs to the shell and is left alone.
- A leading `:root`, `html` or `body` compound is rewritten to `:scope`, so Tailwind's root defaults
  land on your scope root. The same selectors anywhere else in a rule are a build error.

<Callout type="warning" title="This is not the selector the design system's own docs show">
  The design system documents `@scope (.mfe-a) to ([data-tecton-root])`, which are the plugin's
  defaults. This framework overrides both. Your rules are keyed on the `data-mfe-scope` attribute.
  The lower boundary is the next mount root inside yours, so a nested container's CSS is never
  yours.
</Callout>

## The three roots: scope, style, overlay

Every <Term>mount</Term> renders three roots around your tree: scope, style and overlay.

| Root         | Element                                                  | What it carries                                                                   |
| ------------ | -------------------------------------------------------- | --------------------------------------------------------------------------------- |
| scope root   | a `display: contents` div around your whole tree         | `data-mfe-scope="<id>"`, `data-mfe-mount`, `data-mfe-kind`                        |
| style root   | a generated component inside the scope root              | your container's own `ThemeRoot`, pointed at your overlay root                    |
| overlay root | a div the framework appends to `document.body` per mount | the same `data-mfe-scope` value, plus `data-mfe-overlay-root`, `data-tecton-root` |

{/* prettier-ignore */}
```html title="the page while an App is mounted"
<body>
  ... the shell chrome ...
  <div data-mfe-scope="operations" data-mfe-kind="app" data-mfe-mount="operations#1"
       style="display: contents">                    <!-- the scope root -->
    <StyleRoot>                                      <!-- the container's own ThemeRoot -->
      ... the App ...
  <div data-mfe-scope="operations" data-mfe-mount="operations#1"
       data-mfe-overlay-root data-tecton-root>       <!-- the overlay root -->
    ... every dialog, popover, tooltip and menu ...
```

The scope root is `display: contents`, so it anchors a selector without becoming a box. Your
outermost element is the one the host laid out, with no framework div in between. The overlay root
carries the same `data-mfe-scope` value, so an overlay at body level still matches your `@scope`
start selector.

`data-tecton-root` on the overlay root is the other half. The design system hangs its base border
and outline colours on that marker and its descendants. Portalled content descends from the overlay
root rather than from your in-page tree, so without the marker a dialog would open with no base
colours.

`SCOPE_ATTRIBUTE` is exported from `@company/mfe-react` for code that needs the attribute name. The
generated entry exports `withStyleRoot(authored, StyleRoot)` and calls
`createOverlayRoot(definitionId, mountToken, document)` for you, so you call neither.

## Use the design system inside a container

Use the design system by importing components by subpath, as the examples do. There is no barrel
import.

```tsx title="examples/alert-panel/src/alert-panel.tsx"
import { Alert, AlertAction, AlertDescription, AlertTitle } from '@tecton/react/components/alert'
import { Button } from '@tecton/react/components/button'
import { CheckIcon, InfoIcon, OctagonAlertIcon, TriangleAlertIcon, XIcon } from 'lucide-react'
```

Four rules apply inside a container.

- **The theme is the shell's.** The generated style root renders `ThemeRoot` for you. Do not render
  a second one, and do not set a theme on it.
- **Overlays take care of themselves.** Dialog, sheet, popover, tooltip, select, combobox, menu and
  drawer read their portal target from the design system's context. Raise them normally.
- **Use `onPress`, not `onClick`.** The controls are built on React Aria. A `Button` with `onClick`
  looks right and does nothing. The design system's `docs/components/button` page is the reference.
- **Stock Tailwind colour classes generate no CSS.** The design system's theme block opens with
  `--color-*: initial`, which unsets every stock colour before the Tecton families are declared.

| Instead of                            | Write                                                                                                                                         |
| ------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `bg-red-500`, `bg-white`              | a semantic token: `bg-destructive`, `bg-background`, `text-muted-foreground`, `border-border-subtle`                                          |
| `text-zinc-400`, `dark:text-zinc-200` | a Tecton palette step: `text-gray-830`, `bg-blue-120`. The number is a contrast level, not a lightness, and there is no `dark:` pair to write |

[Decision 17](/docs/decisions#17-each-container-ships-its-own-stylesheet-scoped-to-its-own-mount-roots)
records why each container ships its own stylesheet.

<Callout type="warning" title="Nothing fails when you get a colour wrong">
  A stock colour class produces no CSS and no error. The lint rule that would catch it belonged to
  `@tecton/eslint-config`, which the design system has removed, so no preset in this workspace
  checks a class against the token set. Check the colour in the browser rather than waiting for a
  failure.
</Callout>

## Do not write a stylesheet entry

Write no `.css` file and no `postcss.config` in a container. Every CSS file under `examples/` is
generated output:

```sh
$ find examples -name "*.css" -o -name "postcss.config*"
examples/alert-panel/.mfe/styles.css
examples/insights/.mfe/styles.css
examples/lab/.mfe/styles.css
examples/operations/.mfe/styles.css
examples/reports/.mfe/styles.css
```

Five files, one per container, all under the gitignored `.mfe/` directory. No example container has
an authored `.css` file, a `postcss.config.*` or a CSS import anywhere in `src/`.

The design system's own "Micro-frontends" page tells a remote author to write `src/styles/remote.css`
and a `postcss.config.mjs` by hand. That page is for a remote in any host. Here the build writes
both, with the framework's selectors rather than the defaults, so writing them yourself produces a
second, differently scoped sheet. Three rules follow.

- Do not define a `@property` or an `@font-face` in a container. Both register a name page-wide, and
  whichever the browser parsed last wins.
- Do not redeclare a theme variable. `pnpm verify:page` asserts that your scope root inherits
  `--primary` rather than setting its own.
- Do not portal an overlay to `document.body` by hand. It leaves your `@scope` and loses your CSS.

## Errors you will see

Two of these errors happen at build time, both from `packages/mfe-rspack/src/css/scope.ts`.

<Callout type="error" title="An empty scope list">
  `/work/alert-panel/src/mfe.ts: the build failed to scope this container stylesheet: expected at
  least one definition id to scope to, found an empty scope list. This expectation is declared by
  the container stylesheet scope. Export the definitions this container provides. Their ids are the
  values the mount roots carry in their data-mfe-scope attribute, and the stylesheet is scoped to
  them.`

**Fix.** Export a definition from `src/mfe.ts`. The build discovers `createApp` and `createWidget`
results statically, so one assigned to a local variable and never exported is invisible to it.

</Callout>

<Callout type="error" title="The scope plugin could not be resolved">
  `/work/alert-panel/package.json: the build failed to load the stylesheet scope plugin: expected to
  resolve '@tecton/react/postcss/scope' from the container or from the build plugin, found no copy
  of @tecton/react beside either. This expectation is declared by the container stylesheet scope.
  Install @tecton/react (>=0.1.0). Its PostCSS plugin is what contains a container stylesheet,
  whether or not the container renders the design system itself.`

**Fix.** Add `@tecton/react` to the container's dependencies. The plugin resolves from the container
root first, so a container pinned to an older design system is scoped by that version's recipe.

</Callout>

A third failure comes from the scope plugin itself. It fires when a stylesheet carries a `:root`,
`:host`, `html` or `body` selector anywhere but as the leading compound. It names the file and the
selector, and tells you to write the rule against `[data-tecton-root]` instead.

Everything else is caught in a browser by `pnpm verify:page`, which drives Chromium over the shell
and every example. Per definition id it asserts:

| The check                                                                  | What a failure means                                                             |
| -------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| `<id>'s scoped stylesheet reached the document`                            | the container did not load, or its sheet was not scoped                          |
| `no :root or :host selector survives inside an @scope rule`                | the leading-selector rewrite did not run                                         |
| `<id>'s scope root inherits --primary rather than redeclaring it`          | a container declared a theme variable of its own                                 |
| `the w-60 utility exists only inside a container @scope, never shell-wide` | a container's utilities leaked to the document                                   |
| `the overlay's ancestor scope root is the container's own overlay root`    | an overlay portalled to a bare `document.body`, or back inside the in-page mount |
| the shell's own stylesheet carries no `@scope` rule                        | the document half was scoped, so it would inherit into nothing                   |

The first check looks for an `@scope` rule starting `[data-mfe-scope="<id>"]` and ending
`[data-mfe-scope]`. Use `--url /operations/wells` to check one page.

## Browser support for `@scope`

`@scope` has the narrowest browser support of anything the framework requires, and it is emitted
with no fallback.

| Browser    | Minimum version |
| ---------- | --------------- |
| Chrome     | 118             |
| Firefox    | 146             |
| iOS Safari | 17.4            |

Below those versions the rule is unknown, so its block is dropped. The winner at equal layer and
specificity becomes whichever stylesheet the document parsed last, for the whole page. The symptom
is colours, spacing and sizing from the wrong build, changing with whichever screen the user opened
first.

`docs/decisions.md` §5 measured the whole feature set at **89.9685%** usage coverage against a 91%
target, "native CSS `@scope` being the entire gap". There is no fallback to switch on.

## Why a shared page needs a CSS boundary

A shared page needs a CSS boundary because one document means one cascade. The design system's own
scope plugin states the problem:

> A remote that brings its own `@tecton/react` spells `bg-primary`, `text-sm` and every component
> class exactly like its host does, and the two builds do not necessarily mean the same thing by
> them. At equal layer and specificity the copy injected last wins, and injection order follows
> chunk loading, not ownership.

Chunk loading order depends on which screen the user visited first. You do not control that. So the
framework does not try to win the cascade. `@scope` resolves ties by proximity to the scope
root, and proximity is fixed by the DOM rather than by load order.
