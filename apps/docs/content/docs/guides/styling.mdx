description: 'Why a shared page needs a CSS boundary, what the shell owns at document level, and what your container’s build does to the stylesheet it generates for you.'
---

You write Tailwind utility classes and `@tecton/react` components in your TSX, and they look right.
Then a second team's surface mounts on the same page, built six weeks later against a different
release of the design system, and your spacing moves. This page is the machinery that stops that,
almost all of which runs without you writing a line of CSS: you ship no stylesheet entry, no
`postcss.config` and no theme variables, and your build generates a stylesheet from the classes you
used and wraps it in a CSS `@scope` rule keyed on your definition id.

## Why styles need a boundary on a shared page

A <Term>micro-frontend</Term> is a piece of one web page that is built, versioned and deployed on
its own and loaded at run time into a page it does not own. A <Term>container</Term> is one such
deployable: one package, one build, one origin, one `src/mfe.ts`. The <Term>shell</Term> is the
single application on the page that is not listed in the registry; it owns the document and mounts
your surface into itself.

One document means one cascade. The design system's own scope plugin states the problem:

> A remote that brings its own `@tecton/react` spells `bg-primary`, `text-sm` and every component
> class exactly like its host does, and the two builds do not necessarily mean the same thing by
> them. At equal layer and specificity the copy injected last wins, and injection order follows
> chunk loading, not ownership.

Chunk loading order depends on which surface the user visited first, which you do not control. So
the framework does not try to win the cascade. It wraps every container's rules in `@scope`, which
resolves ties by proximity to the scope root instead of by injection order.

## What the shell owns at document level

One stylesheet carries the document-level half for the whole page: the preflight reset, the
`@font-face` declarations, Tailwind's `@property` registrations and the theme variables on `:root`.
All four inherit into every mounted subtree, so a tenant customisation or a theme flip made once in
the shell reaches every container with nothing wired up. Both of the shell's files are short enough
to read whole:

```css title="apps/shell/src/styles/app.css"
/* Tecton's palette replaces Tailwind's, so stock colour utilities (`bg-red-500`) generate no CSS at all. */

@import '@tecton/react/globals.css';

/* Each container ships the utilities its own classes need (§17); what stays here is the document-level half every mounted subtree inherits. */
@source "../**/*.{ts,tsx}";

/* The developer tools are a package rather than a container and render into the shell's own document, so their utilities belong in this sheet. */
@source "../../../../packages/mfe-devtools/src/**/*.{ts,tsx}";

html,
body,
#root {
  height: 100%;
}

body {
  margin: 0;
}
```

```js title="apps/shell/postcss.config.mjs"
/** Tailwind v4 runs as a PostCSS plugin; the design system's globals.css is the entry it expands. */
export default {
  plugins: {
    '@tailwindcss/postcss': {},
  },
}
```

Fonts reach you the way every other inherited value does: the shell declares them, you read
`--font-sans` and `--font-mono`. No container depends on a font package.

## What your container's build does to your CSS

`pluginMfe()` contributes to your Rsbuild configuration and never replaces it. For CSS it appends
two PostCSS plugins to whatever the container already has: `@tailwindcss/postcss` first — skipped
when your own config already declares a plugin whose name contains `tailwindcss` — then the
container scope plugin. The order is the point: "Tailwind before the scope plugin: scoping before
the utilities exist would scope nothing."

### The stylesheet entry the build generates

Generation writes `.mfe/styles.css`, and every generated federation entry imports it, so it reaches
the document before anything renders against it. For a container depending on `@tecton/react` this
is the whole file, comments included:

{/* prettier-ignore */}
```css title="examples/alert-panel/.mfe/styles.css (generated)"
/**
 * Generated by @company/mfe-rspack. Do not edit: the next build overwrites it.
 */

/*
 * Tailwind, split: the theme and the utilities, and deliberately not
 * `@import "tailwindcss"`, which would also bring preflight. The reset
 * belongs to whoever owns the document, and that is the shell — along
 * with the fonts, which reach this container through --font-sans and
 * --font-mono like any other inherited value.
 */
@layer theme, base, components, utilities;
@import "tailwindcss/theme.css" layer(theme);
@import "tailwindcss/utilities.css" layer(utilities);

/*
 * The design system's scoped entry: utilities only, no variables, so
 * nothing here redeclares what the shell's :root already says.
 */
@import "@tecton/react/styles/scoped.css";

/*
 * What Tailwind scans. Splitting the imports above turns automatic source
 * detection off, so every directory holding classes this container renders
 * has to be named here — the library scans its own. The one entry
 * below covers the whole of this container's `src/`; nothing under
 * node_modules needs scanning.
 */
@source "../src/**/*.{ts,tsx}";
```

The design system's scoped entry appears only when `@tecton/react` is in your dependencies.
Dropping that dependency removes the import and the style root described below, so keep it.

### The `@scope` rule the framework emits

A <Term>scoped stylesheet</Term> is the CSS a container ships for its own classes, wrapped so it
applies only inside that container's mount roots. The framework supplies both selectors
(`packages/mfe-rspack/src/css/scope.ts`):

```ts title="packages/mfe-rspack/src/css/scope.ts"
const SCOPE_ATTRIBUTE = 'data-mfe-scope'

return loadScopePlugin(options.containerRoot)({
  scope: scopes.map(id => `[${SCOPE_ATTRIBUTE}="${id}"]`).join(', '),
  boundary: `[${SCOPE_ATTRIBUTE}]`,
  keyframes: { suffix: scopes.join('-') },
})
```

`scopes` is every definition id the container exports, so `examples/alert-panel` emits one rule:

{/* prettier-ignore */}
```css
@scope ([data-mfe-scope="alert-panel"]) to ([data-mfe-scope])
```

A container exporting four Widgets, like `examples/insights`, emits one rule whose start selector
lists all four ids.

<Callout type="warning" title="This is not the selector the design system's own docs show">
  The design system documents `@scope (.mfe-a) to ([data-tecton-root])` — a class for the scope
  root, `[data-tecton-root]` for the boundary. Those are the plugin's defaults, and this framework
  overrides both. Your rules are keyed on the `data-mfe-scope` attribute, and the lower boundary is
  the next mount root inside yours, so a nested container's CSS is never yours.
  `tools/dev/verify-page.mjs` asserts that exact shape in a real browser.
</Callout>

Two more things happen to the sheet. Document-global at-rules are hoisted out of the scope
unchanged — `@charset`, `@import`, `@property`, `@font-face`, `@keyframes` and bodiless
`@layer a, b;` statements, all of which `@scope` would ignore. And every `@keyframes` your sheet
defines is renamed to `<name>--<your ids joined by hyphens>`, with the references in `animation`,
`animation-name` and any `--animate-*` property rewritten to match, because a keyframes name is
page-wide whatever scopes the rules. A name your sheet does not define belongs to the shell and is
left alone.

A leading `:root`, `html` or `body` compound is rewritten to `:scope`, so Tailwind's own root
defaults land on your scope root and inherit into your subtree. The same selectors anywhere else in
a rule are a build error, quoted at the end of this page.

## The stylesheet entry you must not write

You write none. Every CSS file under `examples/` is generated output:

```sh
$ find examples -name "*.css" -o -name "postcss.config*"
examples/alert-panel/.mfe/styles.css
examples/insights/.mfe/styles.css
examples/lab/.mfe/styles.css
examples/operations/.mfe/styles.css
examples/reports/.mfe/styles.css
```

Five files, one per container, all under the gitignored `.mfe/` directory. No example container has
an authored `.css` file, a `postcss.config.*` or a CSS import anywhere in `src/`, and CSS never
appears in their `rsbuild.config.ts`, where `pluginMfe()` is one entry in `plugins`.

The design system's own "Micro-frontends" page tells a remote author to write
`src/styles/remote.css` and a `postcss.config.mjs` by hand. That page is for a remote in any host;
here the build writes both, with the framework's selectors rather than the defaults, so writing
them yourself produces a second, differently scoped sheet. Three rules follow:

- Do not define a `@property` or an `@font-face` in a container. Both register a name page-wide, and
  whichever the browser parsed last wins.
- Do not redeclare a theme variable. `verify:page` asserts that your scope root inherits `--primary`
  rather than setting its own.
- Do not portal an overlay to `document.body` by hand. It leaves your `@scope` and loses your CSS.

## The scope root, the style root and the overlay root

Three elements exist per <Term>mount</Term> — one live instance of your definition on the page.

**The scope root** is what your CSS is keyed on. Every mount renders one around your whole tree
(`packages/mfe-react/src/scope-root.tsx`):

```tsx
<div
  {...{ [SCOPE_ATTRIBUTE]: definitionId, [MOUNT_ATTRIBUTE]: mountToken }}
  data-mfe-kind={kind}
  style={LAYOUT_NEUTRAL}
>
```

`SCOPE_ATTRIBUTE` is `'data-mfe-scope'`, exported from `@company/mfe-react`; it is the supported way
to name the attribute from code. `LAYOUT_NEUTRAL` is `{ display: 'contents' }`, so the scope root
anchors a selector without becoming a box: your outermost element is the one the host laid out, with
no framework `<div>` in between.

**The overlay root** is a `<div>` the framework appends to `document.body` per mount and removes on
disposal. `createOverlayRoot(definitionId, mountToken, document)` gives it the same `data-mfe-scope`
value as the in-page root, plus `data-mfe-mount` and `data-mfe-overlay-root`. That is the trick: an
overlay at body level still matches your `@scope` start selector though it is nowhere near your
subtree.

**The style root** is a component the build generates and attaches to your definition, so the design
system's React context — including its portal target — comes from _your_ copy of the library:

```tsx title=".mfe/entries/style-root.tsx (generated)"
export function StyleRoot({
  overlayContainer,
  children,
}: {
  readonly overlayContainer: HTMLElement
  readonly children: ReactNode
}): ReactNode {
  useLayoutEffect(() => {
    overlayContainer.setAttribute('data-tecton-root', '')
    return () => {
      overlayContainer.removeAttribute('data-tecton-root')
    }
  }, [overlayContainer])

  return (
    <ThemeRoot overlayContainer={overlayContainer} style={LAYOUT_NEUTRAL}>
      {children}
    </ThemeRoot>
  )
}
```

`data-tecton-root` on the overlay root is the second half of the trick. The library hangs its base
border and outline colours on that marker and its descendants, and portalled contents are
descendants of the overlay root rather than of the root inside the page, so without the marker a
dialog would open inside your scope with no base colours.

The generated entry then exports `withStyleRoot(authored, StyleRoot)`. `withStyleRoot` and
`createOverlayRoot` are exported from `@company/mfe-react` only because that generated entry imports
them. You never call either.

## Using the design system inside a container

Import components by subpath, as the examples do. There is no barrel import.

```tsx title="examples/alert-panel/src/alert-panel.tsx"
import { Alert, AlertAction, AlertDescription, AlertTitle } from '@tecton/react/components/alert'
import { Button } from '@tecton/react/components/button'
import { CheckIcon, InfoIcon, OctagonAlertIcon, TriangleAlertIcon, XIcon } from 'lucide-react'
```

Four rules apply inside a container specifically.

**The theme is the shell's, and you inherit it.** The generated style root renders `ThemeRoot` for
you. Do not render a second one and do not set a theme on it: the shell holds one value, applies the
`dark` class to `<html>`, and every container reads it through inheritance.

**Overlays take care of themselves.** Dialog, sheet, popover, tooltip, select, combobox, menu and
drawer read their portal target from the design system's context, which the style root points at
your mount's overlay root. Raise them normally.

**Use `onPress`, not `onClick`.** The controls are built on React Aria, and `onClick` on a `Button`
renders a control that looks right and does nothing; the design system's own
`docs/components/button` page is the reference.

**Stock Tailwind colour utilities generate no CSS.** The design system's theme block opens with
`--color-*: initial`, unsetting every stock colour before the Tecton families are declared, so
`bg-red-500` and `text-zinc-400` emit nothing at all — not a wrong colour, no rule.

| Instead of                            | Write                                                                                                                                         |
| ------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `bg-red-500`, `bg-white`              | a semantic token: `bg-destructive`, `bg-background`, `text-muted-foreground`, `border-border-subtle`                                          |
| `text-zinc-400`, `dark:text-zinc-200` | a Tecton palette step: `text-gray-830`, `bg-blue-120`. The number is a contrast level, not a lightness, and there is no `dark:` pair to write |

<Callout type="error" title="Nothing fails when you get this wrong">
  A stock colour class produces no CSS and no error. The lint rule that would catch it belongs to
  `@tecton/eslint-config`, and a container scaffolded by `pnpm create @company/mfe` wires only
  `mfe.author(...)`. In this repository the design system's `strict` preset is switched off at the
  root with a recorded reason, so check the colour in the browser rather than waiting for a failure.
</Callout>

## Where `@scope` is not supported

`@scope` has the narrowest browser support of anything the framework requires, and it is emitted
with no fallback. `docs/decisions.md` §5 measured the whole feature set at **89.9685%** usage
coverage against a 91% target, "native CSS `@scope` being the entire gap", and records that "an
audience on Chrome below 118, Firefox below 146 or iOS Safari below 17.4 sees unscoped CSS".

What such a user sees: the page renders, every surface mounts, nothing throws. The `@scope` rule is
unknown, so its block is dropped, and the winner at equal layer and specificity becomes whichever
container's stylesheet the document parsed last — for the whole page, the shell included. The
symptom is colours, spacing and sizing that come from the wrong build and change depending on which
surface the user opened first. There is no fallback to switch on.

## When the styling is wrong: the messages you will see

Two failures happen at build time, both from `packages/mfe-rspack/src/css/scope.ts`.

<Callout type="error" title="An empty scope list">
  `/work/alert-panel/src/mfe.ts: the build failed to scope this container stylesheet: expected at
  least one definition id to scope to, found an empty scope list. The container stylesheet scope
  declares this expectation. Export the definitions this container provides. Their ids are the
  values the mount roots carry in their data-mfe-scope attribute, and the stylesheet is scoped to
  them.`

**The fix:** export a definition from `src/mfe.ts`. The build discovers `createApp` and
`createWidget` results statically, so one assigned to a local variable and never exported is
invisible to it.

</Callout>

<Callout type="error" title="The scope plugin could not be resolved">
  `/work/alert-panel/package.json: the build failed to load the stylesheet scope plugin: expected to
  resolve '@tecton/react/postcss/scope' from the container or from the build plugin, found no copy
  of @tecton/react beside either. The container stylesheet scope declares this expectation. Install
  @tecton/react (>=0.1.0). Its PostCSS plugin is what contains a container stylesheet, whether or
  not the container renders the design system itself.`

**The fix:** add `@tecton/react` to the container's dependencies. The plugin resolves from the
container root first, so a container pinned to an older design system is scoped by that version's
recipe; the build plugin's copy is only the fallback.

</Callout>

A third failure comes from the scope plugin itself if you add a stylesheet with a `:root`, `:host`,
`html` or `body` selector anywhere but as the leading compound. It throws, names the file and the
selector, and tells you to write the rule against `[data-tecton-root]` instead.

Everything else is caught in a browser by `pnpm verify:page`, which drives Chromium over the shell
and every example and checks these, per definition id:

| The check                                                                  | What a failure means                                                                                                                               |
| -------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| `<id>'s scoped stylesheet reached the document`                            | no `@scope` rule starting `[data-mfe-scope="<id>"]` and ending `[data-mfe-scope]` exists — the container did not load, or its sheet was not scoped |
| `no :root or :host selector survives inside an @scope rule`                | the leading-selector rewrite did not run                                                                                                           |
| `<id>'s scope root inherits --primary rather than redeclaring it`          | a container declared a theme variable of its own                                                                                                   |
| `the w-60 utility exists only inside a container @scope, never shell-wide` | a container's utilities leaked to the document                                                                                                     |
| `the overlay's ancestor scope root is the container's own overlay root`    | an overlay portalled to a bare `document.body`, or back inside the in-page mount                                                                   |

It also asserts that the shell's own stylesheet carries no `@scope` rule, since a scoped document
half would inherit into nothing. Use `--url /operations/wells` to check one page.
