Your container is built once and deployed many times, and each <Term>deployment</Term> publishes
its own values beside your assets. Two generated modules read them: `#mfe/config` for the values,
`#mfe/fetch` for requests that carry the shell's session token. This page is how to declare a
value, read it, call your API with it, and read every failure on that path.

## Declare a value your deployment supplies

```ts title="examples/operations/src/mfe.config.ts"
/** Declarations only: values live in the deployed runtime-config.json, so no secret belongs here. */

import { env } from '@company/mfe-rspack'
import { z } from 'zod'

export default {
  apiBaseUrl: env('API_BASE_URL', z.string().url(), { api: true }),
  telemetryEnabled: env('TELEMETRY_ENABLED', z.coerce.boolean().default(true)),
}
```

Declare every value your deployment supplies in `src/mfe.config.ts`. It holds declarations and no
values, so no secret and no environment's URL is committed with the code. Each `env(name, schema,
options?)` declares one field:

| Part              | Rule                                                                                                                                                                                |
| ----------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| the field name    | Lower camel case. It becomes a property on the object `#mfe/config` exports.                                                                                                        |
| the variable name | Upper snake case, written inline as a literal. It is copied into the generated `.env.example`, so it has to be writable in a shell.                                                 |
| the schema        | A Zod schema, written inline. The type of the field comes from it, and the build turns it into JSON Schema for the deployment to validate against.                                  |
| the default       | `.default(…)` on the schema. A field with one is optional for the deployment, and a field without one is listed under `required` in the generated JSON Schema.                      |
| `{ api: true }`   | Adds that value's origin to the allowlist `#mfe/fetch` may send the session token to. The **first** `{ api: true }` field is also the base URL a relative request resolves against. |

The parser reads this file and never executes it. So it takes a default-exported object literal and
one `name: env(…)` property per line, with no spreads and no shorthand. Write the
environment-variable name and the `api` flag as literals. `.catch(…)` is rejected by name:
`Use .default(…) for a value the deployment may omit, and let an invalid value fail. A container
that silently substitutes configuration hides the misconfiguration until something downstream
misbehaves.`

## Read a value: `#mfe/config`

```ts
import { config } from '#mfe/config'

const enabled = config.telemetryEnabled
```

The build generates `#mfe/config` for every container that has a `src/mfe.config.ts`. Its type
comes from your schemas, so it cannot drift from what is validated. It fetches the deployment's
`runtime-config.json` and validates it in a top-level `await`, so no module that imports it runs
before validation passes. The result is frozen: changing a value takes a new deployment and a page
reload, and nothing polls.

A container without that file has no `#mfe/config` at all. `examples/alert-panel` and
`examples/insights` are the two that ship none.

```json title="examples/operations/public/runtime-config.json"
{
  "apiBaseUrl": "http://localhost:3010/api/",
  "telemetryEnabled": false
}
```

The URL is resolved against **the container's own deployed location**, not the shell document, so a
container served from another origin finds its own values. In development the container's dev
server publishes them from `public/`. In a deployment, whatever publishes the assets writes the
same file beside them.

The build also emits two files for the deployment to work from. `.mfe/runtime-config.schema.json`
is JSON Schema with `additionalProperties: false` and every non-optional field listed as required.
`.mfe/.env.example` lists every variable name and what it has to look like, and never a value.

## Call your API: `#mfe/fetch`

```ts
import { fetch } from '#mfe/fetch'

const response = await fetch(`assets?site=${encodeURIComponent(siteId)}`, { signal })
```

Every container gets `#mfe/fetch`, whether or not it has configuration. It exports a standard
`fetch` and a `getAccessToken`, both built from the container [transport](/docs/glossary). That
transport holds the base URL, the origin allowlist and the binding to the shell's session.

Nothing global is replaced: the browser's own `fetch` is untouched, and what you import wraps it.
Per call, in order:

1. **The URL is resolved.** An absolute URL is used as is. A relative one resolves against
   `apiBaseUrl` with plain `new URL(input, base)`, so a trailing slash on the base is significant
   as usual. A relative URL is never resolved against the shell document.
2. **The origin is checked against the <Term>origin allowlist</Term>** — the exact
   `scheme://host:port` strings built from your `{ api: true }` declarations. No wildcards, no
   substring matching. A request to any other origin is sent with no token.
3. **Your own `Authorization` header wins.** If you set one, the framework neither replaces nor
   refreshes it.
4. **The session token is attached** as `Authorization: Bearer <token>`, if the shell has one.
5. **A 401 is handled once**, and only when the framework attached the token. It refreshes, and if
   the new token differs it sends the request exactly once more. There is no loop to bound.

Four things it does not do.

- It does not authorize anything, so a 403 passes through untouched.
- It does not buffer your request body in case a replay is needed.
- It does not retry a failed configuration load in the background.
- It never hands the session token to an origin you did not declare:
  `List every API origin explicitly. A wildcard would hand the session bearer token to any host the pattern happens to match.`

Whether the retry in step 5 can happen at all depends on the body you passed:

| The body you passed                                                     | Sent again after a 401 | What happens                                                                                             |
| ----------------------------------------------------------------------- | ---------------------- | -------------------------------------------------------------------------------------------------------- |
| a string, `Blob`, `ArrayBuffer`, `FormData`, `URLSearchParams`, or none | yes                    | The framework refreshes the token and sends the request once more.                                       |
| a `ReadableStream`                                                      | no                     | Reported as `config/invalid`. You get the original 401, and the token is refreshed for the next request. |
| a `Request` object that already carries a body                          | no                     | The same. The attempt that sends it consumes the body.                                                   |

The shell owns one session for the whole page, so a token refresh is single-flight across every
mount. A second concurrent refresh would present a credential the server has already ended, and
sign the user out
([decision 10](/docs/decisions#10-the-framework-owns-no-session-the-shell-installs-one-and-the-container-binds-to-it)).

For a WebSocket, an EventSource or a foreign HTTP stack, `getAccessToken` is the escape hatch.
Always await it, call it per connection, and never store what it returns.

## Use it with TanStack Query

```ts title="examples/operations/src/queries/assets.ts"
export function assetsQueryOptions(siteId: string) {
  return queryOptions({
    // Every variable that determines the response is in the key.
    queryKey: ['operations', 'assets', { siteId }],
    queryFn: async ({ signal }): Promise<Asset[]> => {
      const response = await fetch(`assets?site=${encodeURIComponent(siteId)}`, { signal })
      if (!response.ok) {
        throw new Error(`Loading assets for site ${siteId} failed with ${response.status}.`)
      }
      return z.array(assetSchema).parse(await response.json())
    },
    staleTime: 30_000,
  })
}
```

```ts title="examples/operations/src/routes/assets.tsx"
loader: ({ context, deps }) => {
  context.mfe.telemetry.debug('Loading assets', { site: deps.site })
  // The loader and the component use the same options, so they share one cache entry.
  return context.queryClient.ensureQueryData(assetsQueryOptions(deps.site))
},
```

The Query client comes from the mount through your router context, so you never build one. Put the
request in a `queryOptions` factory. Share that factory between the route loader and the component,
and the two hit one cache entry rather than two. Pass the loader's own `signal` to `fetch`, not the
mount's, because a loader cancels with its own.

In development, `pnpm dev` also starts a stand-in API on port 3010, which the examples'
`runtime-config.json` points at. It is not part of the framework, and `MFE_DEV_API_PORT` moves it.

## Test the request boundary

```ts title="examples/operations/src/routes/assets.test.tsx"
setMfeConfig({ apiBaseUrl: API, telemetryEnabled: false })
setMfeApiBaseUrl(API)
setMfeAccessToken('token-7')
setMfeFetch(() => json(ASSETS))

const rendered = renderApp(operations, { initialEntries: ['/assets'] })

await waitFor(() => {
  expect(mfeRequests()).toHaveLength(1)
})
expect(mfeRequests()[0]?.url).toBe('https://api.example.test/v1/assets?site=north')
expect(mfeRequests()[0]?.authorization).toBe('Bearer token-7')
```

A container's `vitest.config.ts` points `#mfe/config` at `@company/mfe-react/testing/mfe-config`
and `#mfe/fetch` at `@company/mfe-react/testing/mfe-fetch`. Your source keeps its production
imports, and only the runner's resolution changes. The production interceptor still runs, so
base-URL resolution, the allowlist and the 401 replay are all exercised. Reading a field nobody
installed throws and names it, rather than reading as `undefined`.

## Errors you will see

The errors below come from the configuration path and the request path. The first four stop the
container before any importing module evaluates.

| Code                     | When                                                                           | The message                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         | Fix                                                                                               |
| ------------------------ | ------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| `config/missing`         | No `runtime-config.json` beside the container's assets.                        | `operations failed to load its runtime configuration: expected a file at http://localhost:3001/runtime-config.json, received 404 Not Found. The container configuration contract declares this expectation. Publish the runtime configuration with the container. The generated .env.example lists every value it has to carry, and the generated JSON Schema validates it before release.`                                                                                                                                         | Publish the file with the container.                                                              |
| `config/unreachable`     | The request never finished, or the answer was not a 200 or a 404.              | `operations failed to load its runtime configuration: expected a readable file at http://localhost:3001/runtime-config.json, received a request that never completed. The container configuration contract declares this expectation. Check that the deployment publishes this file next to the container assets and that the browser can reach it.` An answer that is neither 200 nor 404 reads `expected a 200 response from …, received 503 Service Unavailable.`                                                                | Publish the file beside the container's assets, and check that its origin answers.                |
| `config/invalid`         | A declared field is absent, or holds the wrong type.                           | `operations failed to validate apiBaseUrl: expected a string in uri form, received Invalid input: expected string, received undefined. The container configuration contract declares this expectation. Set API_BASE_URL in the deployment that writes this container's runtime configuration, then reload the page.`                                                                                                                                                                                                                | Add the field with the shape the message names, or give the schema a `.default(…)`.               |
| `config/invalid`         | The file carries a key your declarations do not.                               | `expected only the declared fields (apiBaseUrl, telemetryEnabled), received apiBaseURL. … Remove the extra keys, or declare them with env() in src/mfe.config.ts. An undeclared key is usually a misspelled one, and ignoring it would silently fall back to a default.`                                                                                                                                                                                                                                                            | Fix the spelling in the file, or declare the key with `env()`.                                    |
| `config/missing`         | A relative URL, and no `{ api: true }` field to resolve it against.            | `operations failed to resolve the request URL: expected an absolute URL, or an apiBaseUrl to resolve a relative one against, received the relative URL "assets?site=north" and no configured apiBaseUrl. Set apiBaseUrl (for example "https://api.example.test/v1/"), or pass an absolute URL. A relative URL is never resolved against the shell document URL, so this request had no base and was not sent.`                                                                                                                      | Declare a `{ api: true }` field, or pass the absolute URL at the call site.                       |
| `auth/undeclared-origin` | A request to an origin you did not declare. Development only, once per origin. | `operations failed to attach the access token for https://reports.example.test: expected a request to an origin the author declared as an API with { api: true }, received a request to https://reports.example.test, which is not declared. Declare https://reports.example.test with { api: true } if it is your API, or leave it undeclared if it must never receive the session bearer token. It was sent without one, so an endpoint that requires it answers 401 — that 401 is this missing declaration, not a broken token.` | If this is your API, declare the origin. If it must never receive the token, leave it undeclared. |
| `config/invalid`         | A 401 on a request the framework cannot send twice.                            | The operation reads `retry POST https://api.example.test after 401`, and the observed reason names the body, for example `a ReadableStream body, which is consumed as it is sent and cannot be read a second time`. The repair: `Buffer the body before sending it — a string, Blob, ArrayBuffer, FormData or URLSearchParams can be replayed — or handle the 401 at the call site.`                                                                                                                                                | Buffer the body, or handle the 401 at the call site.                                              |

In development, a `config/missing` usually means the file is not there. Create
`public/runtime-config.json` in the container and restart its dev server, which publishes `public/`
beside its assets. The scaffold's App template ships that file. A container scaffolded from the
Widget template has no `public/` directory, so this is the first thing you hit after adding a
`src/mfe.config.ts` to one.

The replay code is a known mismatch: nothing in the closed error union describes replayability
([decision 7](/docs/decisions#7-two-error-conditions-have-no-exact-code-in-the-closed-union)).

## Why configuration is fetched, not bundled

Configuration is fetched because one build serves every environment: a test environment, a staging
environment, one per customer. The API sits at a different URL in each. A value compiled into the
bundle would mean one build per environment, and a rebuild to correct a URL.

So the values arrive at load time, and the declarations stay in the code. The schemas are what the
build publishes for the deployment to fill in, and what validates the file it wrote. An undeclared
key fails rather than being ignored, because it is usually a misspelled one.
