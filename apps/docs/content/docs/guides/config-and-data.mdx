---
title: '3. Configuration and data'
description: 'Per-deployment values through the generated config module, and calls to your API through the container transport.'
---

Your container is built once and deployed many times — a test environment, a staging environment,
one per customer — and the API it talks to sits at a different URL in each. So nothing about where
it talks to may be baked into the bundle. This page is where those values come from instead, how a
request reaches your API with the session's token on it, and what every failure on that path says.

A <Term>container</Term> is the deployable unit you ship: one build, one origin, one
`src/mfe.ts`. A <Term>deployment</Term> is one place that build is serving from, with its own
values beside it. The <Term>shell</Term> is the application that owns the page and mounts your
container into it; it owns the session, and your container borrows it through a generated module
rather than holding credentials of its own.

## Declaring what a deployment must supply

A container with configuration has a `src/mfe.config.ts`. It holds declarations and no values, so
no secret and no environment's URL is ever committed with the code.

```ts title="examples/operations/src/mfe.config.ts"
/** Declarations only: values live in the deployed runtime-config.json, so no secret belongs here. */

import { env } from '@company/mfe-rspack'
import { z } from 'zod'

export default {
  apiBaseUrl: env('API_BASE_URL', z.string().url(), { api: true }),
  telemetryEnabled: env('TELEMETRY_ENABLED', z.coerce.boolean().default(true)),
}
```

Each `env(name, schema, options?)` declares one field:

| Part              | Rule                                                                                                                                                                                |
| ----------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| the field name    | Lower camel case. It becomes a property on the object `#mfe/config` exports.                                                                                                        |
| the variable name | Upper snake case, written inline as a literal. It is copied into the generated `.env.example`, so it has to be writable in a shell.                                                 |
| the schema        | A Zod schema, written inline. The type of the field comes from it, and the build turns it into JSON Schema for the deployment to validate against.                                  |
| the default       | `.default(…)` on the schema. A field with one is optional for the deployment; a field without one is required, and the generated JSON Schema lists it under `required`.             |
| `{ api: true }`   | Adds that value's origin to the allowlist `#mfe/fetch` may send the session token to. The **first** `{ api: true }` field is also the base URL a relative request resolves against. |

The file is read by the parser and never executed, which is where its rules come from: a
default-exported object literal, one `name: env(…)` property per line, no spreads and no shorthand,
and the environment-variable name and the `api` flag written as literals. `.catch(…)` is rejected
by name — `Use .default(…) for a value the deployment may omit, and let an invalid value fail. A
container that silently substitutes configuration hides the misconfiguration until something
downstream misbehaves.`

## Reading the values: `#mfe/config`

The build generates one module per container that has a `src/mfe.config.ts`, aliased `#mfe/config`.
A container without that file has no `#mfe/config` at all — `examples/alert-panel` and
`examples/insights` are the two that ship none.

```ts
import { config } from '#mfe/config'

const enabled = config.telemetryEnabled
```

Its type is derived from your schemas, so it cannot drift from what is validated. It fetches the
deployment's `runtime-config.json` and validates it in a top-level `await`, which means no module
that imports it runs before validation has passed. The result is frozen: changing a value takes a
new deployment and a page reload, and nothing polls.

The file is resolved against **the container's own deployed location**, not the shell document, so
a container served from another origin finds its own values. In development the container's dev
server publishes them from `public/`:

```json title="examples/operations/public/runtime-config.json"
{
  "apiBaseUrl": "http://localhost:3010/api/",
  "telemetryEnabled": false
}
```

In a deployment, the same file is written beside the container's assets by whatever publishes them.
The build also emits `.mfe/runtime-config.schema.json` — JSON Schema, `additionalProperties: false`,
with every non-optional field listed as required — and `.mfe/.env.example`, which lists every
variable name and what it has to look like, and never a value.

### When configuration stops the container

All of these are thrown before any importing module evaluates, so the container does not start.

<Callout type="error" title="config/missing">

`operations failed to load its runtime configuration: expected a file at
http://localhost:3001/runtime-config.json, received 404 Not Found. The container configuration
contract declares this expectation. Publish the runtime configuration with the container. The
generated .env.example lists every value it has to carry, and the generated JSON Schema validates
it before release.`

In development this means the file is not there: create `public/runtime-config.json` in the
container and restart its dev server, which publishes `public/` beside its assets. The scaffold's
App template ships that file; a container scaffolded from the Widget template has no `public/`
directory, so this is the first thing you hit after adding a `src/mfe.config.ts` to one.

</Callout>

<Callout type="error" title="config/invalid">

`operations failed to validate apiBaseUrl: expected a string in uri form, received Invalid input:
expected string, received undefined. The container configuration contract declares this
expectation. Set API_BASE_URL in the deployment that writes this container's runtime
configuration, then reload the page.`

The field is absent from the file, or holds the wrong type. Add it to `runtime-config.json` with
the shape the message names — `"apiBaseUrl": "https://api.example.test/v1/"` — or give the schema a
`.default(…)` if the deployment is allowed to omit it.

</Callout>

A key the file carries and your declarations do not is the same code, with a different sentence:
`expected only the declared fields (apiBaseUrl, telemetryEnabled), received apiBaseURL. … Remove
the extra keys, or declare them with env() in src/mfe.config.ts. An undeclared key is usually a
misspelled one, and ignoring it would silently fall back to a default.` A file the deployment could
not serve at all is `config/unreachable`.

## Making requests: `#mfe/fetch`

Every container gets `#mfe/fetch`, whether or not it has configuration. It exports a standard
`fetch` and a `getAccessToken`, built from the container <Term>transport</Term> — the object that
holds the base URL, the origin allowlist and the binding to the shell's session. Nothing global is
replaced: the browser's own `fetch` is untouched, and what you import is a function that wraps it.

```ts
import { fetch } from '#mfe/fetch'

const response = await fetch(`assets?site=${encodeURIComponent(siteId)}`, { signal })
```

Per call, in order:

1. **The URL is resolved.** An absolute URL is used as is. A relative one resolves against
   `apiBaseUrl` with plain `new URL(input, base)`, so a trailing slash on the base is significant
   as usual. A relative URL is never resolved against the shell document.
2. **The origin is checked against the <Term>origin allowlist</Term>** — the exact
   `scheme://host:port` strings built from your `{ api: true }` declarations. No wildcards, no substring matching. A request to any
   other origin is sent with no token.
3. **Your own `Authorization` header wins.** If you set one, the framework neither replaces nor
   refreshes it.
4. **The session token is attached** as `Authorization: Bearer <token>`, if the shell has one.
5. **A 401 is handled once.** Only when the framework attached the token: it refreshes, and if the
   new token differs it sends the request exactly once more. There is no loop to bound.

What it does not do: it does not authorize anything — a **403 passes through untouched**, because
attaching a token is not authorization. It does not buffer your request body in case a replay is
needed. It does not retry a failed configuration load in the background. And it never hands the
session token to an origin you did not declare, which is the rule the allowlist exists for: `List
every API origin explicitly. A wildcard would hand the session bearer token to any host the pattern
happens to match.`

### The failures on the request path

<Callout type="error" title="config/missing">

`operations failed to resolve the request URL: expected an absolute URL, or an apiBaseUrl to
resolve a relative one against, received the relative URL "assets?site=north" and no configured
apiBaseUrl. Set apiBaseUrl (for example "https://api.example.test/v1/"), or pass an absolute URL. A
relative URL is never resolved against the shell document URL, so this request had no base and was
not sent.`

The container declared no `{ api: true }` field, so it has no base. Add one to
`src/mfe.config.ts`, or pass the absolute URL at the call site.

</Callout>

<Callout type="warning" title="auth/undeclared-origin, in development only">

`operations failed to attach the access token for https://reports.example.test: expected a request
to an origin the author declared as an API with { api: true }, received a request to
https://reports.example.test, which is not declared. Declare https://reports.example.test with {
api: true } if it is your API, or leave it undeclared if it must never receive the session bearer
token. It was sent without one, so an endpoint that requires it answers 401 — that 401 is this
missing declaration, not a broken token.`

The request went out without a token. Declare the origin with `{ api: true }`, or leave it
undeclared deliberately. This is reported once per origin, so it cannot bury the rest of the
console.

</Callout>

A 401 on a request that cannot be sent twice is reported as `config/invalid` with the operation
`retry POST https://api.example.test after 401` and the observed reason `a ReadableStream body,
which is consumed as it is sent and cannot be read a second time`. The repair: `Buffer the body
before sending it — a string, Blob, ArrayBuffer, FormData or URLSearchParams can be replayed — or
handle the 401 at the call site.` That code is a known mismatch: nothing in the closed error union
describes replayability
([decision 7](/docs/decisions#7-two-error-conditions-have-no-exact-code-in-the-closed-union)).

For a WebSocket, an EventSource or a foreign HTTP stack, `getAccessToken` is the escape hatch.
Always await it, call it per connection, and never store what it returns.

## With TanStack Query

The Query client comes from the mount, through your router context, so you never build one. Put the
request in a `queryOptions` factory and share it between the route loader and the component, and
the two hit one cache entry rather than two.

```ts title="examples/operations/src/queries/assets.ts"
export function assetsQueryOptions(siteId: string) {
  return queryOptions({
    // Every variable that determines the response is in the key.
    queryKey: ['operations', 'assets', { siteId }],
    queryFn: async ({ signal }): Promise<Asset[]> => {
      const response = await fetch(`assets?site=${encodeURIComponent(siteId)}`, { signal })
      if (!response.ok) {
        throw new Error(`Loading assets for site ${siteId} failed with ${response.status}.`)
      }
      return z.array(assetSchema).parse(await response.json())
    },
    staleTime: 30_000,
  })
}
```

```ts title="examples/operations/src/routes/assets.tsx"
loader: ({ context, deps }) => {
  context.mfe.telemetry.debug('Loading assets', { site: deps.site })
  // The loader and the component use the same options, so they share one cache entry.
  return context.queryClient.ensureQueryData(assetsQueryOptions(deps.site))
},
```

Pass the loader's own `signal` to `fetch`, not the mount's: a loader cancels with its own.

In development, `pnpm dev` also starts a stand-in API on port 3010, which the examples'
`runtime-config.json` points at. It is not part of the framework — a deployment brings its own —
but a container whose requests all fail demonstrates nothing about the request boundary. 3010 is
the one port `pnpm dev` does not check before starting, so a process already holding it surfaces as
one `dev api` line.

## Testing the request boundary

A container's `vitest.config.ts` points `#mfe/config` at `@company/mfe-react/testing/mfe-config` and
`#mfe/fetch` at `@company/mfe-react/testing/mfe-fetch`. Your source keeps its production imports;
only the runner's resolution changes.

```ts title="examples/operations/src/routes/assets.test.tsx"
setMfeConfig({ apiBaseUrl: API, telemetryEnabled: false })
setMfeApiBaseUrl(API)
setMfeAccessToken('token-7')
setMfeFetch(() => json(ASSETS))

const rendered = renderApp(operations, { initialEntries: ['/assets'] })

await waitFor(() => {
  expect(mfeRequests()).toHaveLength(1)
})
expect(mfeRequests()[0]?.url).toBe('https://api.example.test/v1/assets?site=north')
expect(mfeRequests()[0]?.authorization).toBe('Bearer token-7')
```

The production interceptor still runs: only the session and the network at the far end are
replaced, so base-URL resolution, the allowlist and the 401 replay are all exercised. Reading a
field nobody installed throws and names it, rather than reading as `undefined`.
