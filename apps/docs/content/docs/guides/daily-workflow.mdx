Your surface is one deployable among several on a page you do not own, so "run it and look at it"
means running three things together: the <Term>shell</Term>, the one application on the page that
owns the document and mounts the others into itself; the <Term>registry</Term>, the JSON file the
shell reads at boot to learn which surfaces exist and where their code is; and at least one
container. This page is the loop you will be in all day: scaffold, generate, `pnpm dev`, point the
shell at your dev server, edit, test, check.

Every command here comes from a `package.json` script or a file under `tools/dev/`.

## Scaffolding a container

A <Term>container</Term> is one deployable unit: one package, one build, its own port in
development, its own deployed origin, and one `src/mfe.ts`. It exports at most one App and any
number of Widgets.

```sh
pnpm create @company/mfe <directory> --id <id> [--template app|widget]
```

The usage block, verbatim from `packages/create-mfe/src/cli.ts`:

```text
pnpm create @company/mfe <directory> [options]

Options:
  --id <id>         definition id (lower-case letters, digits, single hyphens)
  --template <kind> app | widget            (default: app)
  --force           write into a non-empty directory
  --help            show this message

Examples:
  pnpm create @company/mfe operations --id operations
  pnpm create @company/mfe alert-panel --id alert-panel --template widget
```

`--id` defaults to the last segment of the directory. The package name is derived rather than
asked — `@example/<id>` — which keeps the id and the package aligned. A non-empty directory is
refused unless you pass `--force`, and generation is deterministic: a second run produces identical
files.

<Callout type="error" title="An id the framework cannot use">
  `"Order_Book" is not a usable definition id. Ids are lower-case letters, digits and single
  hyphens, for example "alert-panel". The id is also the storage prefix and the CSS scope value, so
  it has to be unambiguous in both.`

**The fix:** pass `--id order-book`.

</Callout>

Both templates write these files:

| File                          | What it is                                                                                                            |
| ----------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| `package.json`                | the **`mfe` block** (below), eight scripts, and the dependency lists                                                  |
| `.gitignore`                  | `node_modules/`, `dist/`, then the generated output: `routeTree.gen.ts` and `.mfe/`                                   |
| `.prettierrc.json`            | no semicolons, single quotes, trailing commas, `printWidth: 100`, `arrowParens: 'avoid'`                              |
| `eslint.config.mjs`           | `mfe.author({ tsconfigRootDir, files: ['src/**/*.{ts,tsx}'] })`                                                       |
| `tsconfig.json`               | the repo base, plus `paths` for `#mfe/config`, `#mfe/fetch` and `#mfe/meta`                                           |
| `vitest.config.ts`            | the three `#mfe/*` aliases, `environment: 'jsdom'`, `setupFiles`                                                      |
| `vitest.setup.ts`             | jest-dom's matchers, installed and declared in one file                                                               |
| `rsbuild.config.ts`           | `plugins: [pluginReact(), pluginMfe()]`, the port from the manifest, `server.publicDir`, `dev.lazyCompilation: false` |
| `runtime-config.example.json` | `{ "apiBaseUrl": "https://api.example.test/v1/" }`                                                                    |

The eight scripts are the same in both templates:

```json title="package.json (scaffolded)"
{
  "dev": "pnpm run generate && rsbuild dev",
  "build": "pnpm run generate && rsbuild build",
  "generate": "mfe-generate",
  "typecheck": "pnpm run generate && tsc --noEmit",
  "test": "pnpm run generate && vitest run",
  "lint": "eslint .",
  "format": "prettier --write .",
  "format:check": "prettier --check ."
}
```

The App template adds `public/runtime-config.json` (local values, so a scaffolded App does not fail
at boot with `config/missing`), `src/mfe.ts` with the router factory and the
`declare module '@tanstack/react-router'` augmentation, `src/mfe.config.ts`, three routes under
`src/routes/`, a route test, and a README; its dependencies gain `@tanstack/react-router` and
`@tanstack/react-query`. The Widget template adds `src/mfe.ts` holding the exported contract and the
`createWidget` call, `src/<id>.tsx` holding the render function alone, `src/mfe.test.tsx`, an
`exports` map pointing at the generated contract module, and a README. It writes no `src/routes/`,
no `src/mfe.config.ts` and no router.

The split between `src/mfe.ts` and `src/<id>.tsx` is not stylistic; the hot-update section below is
the reason.

<Callout type="warning" title="One line of the scaffolded Widget README is not true">
  It says `pnpm run dev` "previews it through the shell-hosted placement, with validated example
  inputs and an event viewer". There is no such harness. `pnpm run dev` starts the container's dev
  server; to see the Widget, point the shell at it with an override and open a page that consumes
  it, or use the shell's own widget dashboard at `/`.
</Callout>

## The `mfe` block in package.json

Every container declares its port and the ids it exports once, and the tooling reads it back:

```json title="examples/operations/package.json"
"mfe": {
  "port": 3001,
  "definitions": ["operations"]
}
```

The scaffold sets `port` to 3101 for an App and 3103 for a Widget, clear of the 3000–3005 the shell
and the examples use, and the "Next steps" it prints repeats the same number in the override
snippet.

`port` is read by the container's own `rsbuild.config.ts`, by `pnpm dev`, by the registry builder
and by `pnpm verify:page`. It is part of the container's address: generation writes
`http://localhost:<port>/mf-manifest.json` into the shell's registry, so moving a container to
another port loses it. `pluginMfe()` sets `server.strictPort: true` for that reason — "The shell's
registry names this port; falling back to another hides the container."

`definitions` decides which ids the override snippet assigns. Nothing validates it against what
`src/mfe.ts` exports — discovery reads the entry module — so keeping it accurate is a convention.

## `pnpm run generate`: what is generated and where

The framework generates a container's `#mfe/*` modules, its registry descriptor and (for an App)
its route tree. None of it is in version control, and none of it is edited by hand.

| Command                         | Scope                                                            |
| ------------------------------- | ---------------------------------------------------------------- |
| `pnpm run generate` (root)      | `pnpm -r run generate`, then `node tools/dev/build-registry.mjs` |
| `mfe-generate` (in a container) | that container alone; `--root <directory>` for another           |

What lands in `.mfe/`: `styles.css` (the container stylesheet), `fetch.ts` behind `#mfe/fetch`,
`config.ts` behind `#mfe/config` when `src/mfe.config.ts` exists, `meta.ts` behind `#mfe/meta`, one
federation entry per definition, a generated `style-root.tsx` when the container depends on
`@tecton/react`, one contract module per Widget, `mfe-registry.json`, `runtime-config.schema.json`
and `.env.example` when there is a config source, `tsconfig.paths.json`, `css.d.ts`, and a
`.gitignore` that is itself generated. An App also gets `routeTree.gen.ts` at the container root.

`mfe-generate` runs the same `generateContainer` the build runs, so the two cannot drift. When
nothing changed it prints `@example/operations: generated output is already current.` Findings in
your own sources — a stray definition, a bare relative asset path — go to stderr and fail the
command with exit code 1.

This is the one documented recovery command. From `README.md`:

> Generated output (`.mfe/`, `routeTree.gen.ts`, `apps/shell/public/registry.json`) is not in
> version control. If a build behaves as though a file is missing, `pnpm run generate` is the fix.

## Starting everything with `pnpm dev`

```sh
pnpm dev                                        # shell + every example
pnpm dev:shell                                  # the shell alone
pnpm dev:mfes                                   # examples only, against a shell you started
node tools/dev/dev.mjs --only=operations,alert-panel
```

| Service                                                            | Port      |
| ------------------------------------------------------------------ | --------- |
| `apps/shell`                                                       | 3000      |
| `examples/operations`, `reports`, `alert-panel`, `insights`, `lab` | 3001–3005 |
| the stand-in API (`tools/dev/api.mjs`)                             | 3010      |

`pnpm dev` checks that 3000–3005 are free **before** it starts anything, so a busy port is reported
once, by name, rather than as one bundler's fallback and another's crash. 3010 is not checked; a
process already holding it makes the API's `listen` throw, which appears as one `dev api` line.
Then it runs generation in every container, assembles the registry from the results, prints the
service table and the override snippets, and starts the servers.

```text
Port 3001 already in use.

These are not preferences: `pnpm run generate` writes each container's URL
into the shell registry, so a container cannot be moved to another port
without the shell losing it. Usually this is a dev server from an earlier
run that did not shut down.

Find what holds it:

  lsof -i :3001

then stop it with `kill <pid>`.
```

On Windows the same message prints `netstat -ano | findstr :3001` and `taskkill /PID <pid> /F`
instead.

The stand-in API is not part of the framework: a deployment brings its own, and this one exists so
the request boundary is observable. It serves `GET /api/assets?site=north|south|central` and
`GET /api/lab/probe`, the probe answering `{ sawAuthorization, scheme, path }` and never the token
itself.

## Pointing the shell at your container: the override

The shell learns a container exists only from its registry, so a local dev server reaches it through
a boot-time <Term>override</Term>: one entry in `localStorage`, definition id to absolute manifest
URL, read before the registry is normalized and before any remote is registered. It is a URL only,
never a token and never configuration. `pnpm dev` prints the snippet with real ids and URLs:

{/* prettier-ignore */}
```js
const key = "company:mfe:overrides"
const overrides = JSON.parse(localStorage.getItem(key) || '{}')
  overrides["operations"] = "http://localhost:3001/mf-manifest.json"
localStorage.setItem(key, JSON.stringify(overrides))
location.reload()
```

To reset one id while keeping the others, the printed snippet replaces the middle line with
`delete overrides["operations"]`.

The reload is not optional. From `README.md`:

> Changing an override requires a page reload: the old container's modules are already registered in
> the federation runtime under the same name, and its chunks and stylesheets are document-level, so
> disposing a mount touches none of that.

Every way an override can be wrong is diagnosed at boot as a warning, because an override that
silently did nothing is the bug this mechanism exists to prevent: unreadable storage, text that is
not JSON, a value that is not an absolute URL string, a relative URL, or two definitions from one
container pointed at different URLs. The last one reads:

> `expected one consistent override URL for every definition exported by a container … Point every
definition from this container at the same manifest URL. One container is loaded once; conflicting
URLs cannot both apply.`

Nothing on the page itself says an override is active — the strip that used to say so was removed
(`docs/decisions.md` §23). An override pointing at a stopped dev server therefore looks exactly like
a broken deployment. The developer tools and the bug report are where it shows.

## Running one container against a shell you started yourself

`pnpm dev:shell` in one terminal and `pnpm dev:mfes` in another is the split; start a subset with
`node tools/dev/dev.mjs --only=<names>` and run your own container's `pnpm dev` from its directory.
The root `pnpm run generate` still has to have run, or the shell's registry does not name it.

## Why one edit hot-updates and another reloads the page

React Refresh replaces a module in place only when it can prove **every** export is a component. One
exported hook, constant, schema or factory beside them makes the module unable to accept an update;
the update propagates to whatever imported it until it reaches an entry, which accepts nothing, so
the page reloads and every piece of state on it is lost.

`src/mfe.ts` exports a definition and usually a contract, so it can never be a refresh boundary. A
Widget written inline in its entry reloads the page on every edit. The examples say so in code:

```ts title="examples/alert-panel/src/mfe.ts"
/** The build reads these schemas statically and publishes them in the registry, so a host can offer
 * this Widget in a catalogue without loading the container (§16). The render function lives in
 * `alert-panel.tsx` because a module exporting a contract and a definition is no React Refresh
 * boundary, so an edit here would reload the page (§18). */
```

The symptom is silent: everything still works, it is only slower and starts over each time, which
reads as a bundler problem rather than a module-shape one. `pnpm hmr:probe` answers the question
directly, by putting a value on `window` that a reload cannot carry:

```sh
pnpm hmr:probe examples/lab/src/routes/index.tsx /lab
```

```text
file:      examples/lab/src/routes/index.tsx
url:       http://localhost:3000/lab
result:    hot-updated in place
console:   (nothing about hot updates)
```

The other answer is `result:    (the page reloaded)`. Exit code 0 means a hot update, 1 a reload. It
runs against servers you already started, appends a comment to the file, waits, and restores it.

## The developer tools overlay

The tools ship in every build and are gated at runtime on one `localStorage` key, because the page
where they are most needed is a deployed one.

| How                                                                          | What happens                                                |
| ---------------------------------------------------------------------------- | ----------------------------------------------------------- |
| `http://localhost:3000/?devtools=1`                                          | turns them on and persists it; `?devtools=0` turns them off |
| <Kbd>g</Kbd> <Kbd>d</Kbd>                                                    | opens the panel on the **Overrides** tab                    |
| <Kbd>g</Kbd> <Kbd>r</Kbd>, or <Kbd>⌘</Kbd><Kbd>K</Kbd> → "Open the registry" | opens it on the **Registry** tab                            |
| the wrench, bottom left                                                      | toggles the panel                                           |

**Overrides** lists every registered definition with the URL it loaded from, and gives each row
"Point `<id>` at the dev server", "Edit the manifest URL for `<id>`" and "Clear the override for
`<id>`". The action bar reads `<n> pending — applied on reload` or `<n> override(s) applied at boot`.
It refuses a URL the boot reader would reject and says so before writing, rather than after the
reload.

**Registry** has two inner views with counts: **Loaded**, where an accepted entry shows its facts, a
mark if it is overridden, and a "Copy the manifest URL" action; and **Rejected**, which names each
quarantined entry, why it was rejected, and the descriptor as published. The empty states are
`Nothing was registered` and `Every entry validated`.

The **bug report** is the shell's own surface — the bug icon in the header, or <Kbd>⌘</Kbd><Kbd>K</Kbd>.
It collects, on demand, the workspace, URL, mounted surface, theme, user, groups, viewport and user
agent, then whether `registry.json` loaded, the accepted count, every rejected entry as
`<id>: <reason>`, every override as `<id> → <url>`, and one line per accepted entry naming its build
as `<id>: <hash> · <time>`, or `<id>: no build published`. It is Markdown, and since the override
strip was removed it is the only place on the page that says what the shell was running.

## Writing tests

Container tests run on Vitest in jsdom. Generation runs first, because the test config resolves
`#mfe/meta` to the real generated module while aliasing the other two to fixtures:

```ts title="examples/operations/vitest.config.ts"
{ find: /^#mfe\/config$/, replacement: '@company/mfe-react/testing/mfe-config' },
{ find: /^#mfe\/fetch$/,  replacement: '@company/mfe-react/testing/mfe-fetch' },
{ find: /^#mfe\/meta$/,   replacement: fileURLToPath(new URL('./.mfe/meta.ts', import.meta.url)) },
```

Your source keeps its production imports, and `tsconfig` still maps them to the real generated
modules, so the types stay exact. `@company/mfe-react/testing` gives you:

- `renderApp(definition, options)` and `renderWidget(definition, options)` — the real adapter and
  the real validation path, over a memory history and in-memory stores;
- `createMfeTestEnvironment(options)` — a runtime, a mount, a `wrapper` for hook tests, a typed
  `routerContext`, `setShellState`, and recorded `telemetry`, `diagnostics`, `navigation` and
  `storageAreas`;
- `renderSuspending(ui)` for a tree that will suspend;
- the alias setters: `setMfeConfig`, `setMfeApiBaseUrl`, `setMfeApiOrigins`, `setMfeFetch`,
  `setMfeAccessToken`, `mfeRequests()` and `resetGeneratedAliases()`.

Every example test disposes the same way:

```ts title="examples/alert-panel/src/mfe.test.tsx"
let cleanup: (() => Promise<void>) | null = null

afterEach(async () => {
  // Cleared before the await: a later test may have assigned a new handle by the time this resolves.
  const dispose = cleanup
  cleanup = null
  await dispose?.()
})
```

## Checking the page in a browser, and before you push

`pnpm verify:page` generates, boots the shell and every example, and drives Chromium through
Playwright. It exists because the first time the shell loaded a real container, five defects
surfaced that compiled, type-checked and passed the whole suite while rendering nothing. Per page it
asserts that each App mounted from its own container, that a Widget from a second container rendered
inside one, that a child App delegated at a splat route reads its own URL, that a popover portals
into its own container's overlay root, that an unloadable manifest costs that App alone, that the
shell chrome renders exactly once, and every `@scope` fact on the page. `--url /operations` checks
one page, `--keep-open` leaves the browser up, and it needs a Chromium
(`pnpm exec playwright install chromium` once, or `PLAYWRIGHT_BROWSERS_PATH`).

`pnpm check` is what CI runs:

```json
"check": "pnpm run generate && pnpm run format:check && pnpm run lint && pnpm run typecheck && pnpm run boundaries && pnpm run diagrams:check && pnpm run test"
```

Generation, format check, lint, strict typecheck, package-boundary checks, the diagram check and the
test suites, in that order. The steps run individually too: `pnpm format`, `pnpm lint`,
`pnpm typecheck`, `pnpm boundaries`, `pnpm test`.

## Windows

Everything above runs on Windows; every script goes through node rather than a shell. Two things to
know:

- **Ports.** 3000–3005 must be free, and the busy-port message prints
  `netstat -ano | findstr :3001` to name the process and `taskkill /PID <pid> /F` to stop it. The
  port check probes both `127.0.0.1` and `::1`, because Windows resolves `localhost` to `::1` first
  and a server on one with a check on the other disagree about whether the port is free.
- **Generated output.** `.mfe/`, `routeTree.gen.ts` and `apps/shell/public/registry.json` are not in
  version control, so a fresh clone has neither and an editor opened on it reports errors until
  something generates them. `pnpm run generate` is the fix.
