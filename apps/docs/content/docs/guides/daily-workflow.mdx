description: 'The commands you run all day: scaffold a container, generate its modules, start everything, point the shell at it, and check before you push.'

Running your App or Widget means running the <Term>shell</Term> that owns the page, the
[registry](/docs/glossary) it reads at boot, and at least one container. `pnpm dev` starts all of
them, and one `localStorage` override points the shell at your own dev server. Every command here
comes from a `package.json` script or a file under `tools/dev/`.

## Scaffold a container

One command scaffolds a container, and two more start it.

<Steps>

<Step>

```sh
pnpm create @company/mfe <directory> --id <id> [--template app|widget]
```

The usage block, verbatim from `packages/create-mfe/src/cli.ts`:

```text
pnpm create @company/mfe <directory> [options]

Options:
  --id <id>         definition id (lower-case letters, digits, single hyphens)
  --template <kind> app | widget            (default: app)
  --force           write into a non-empty directory
  --help            show this message

Examples:
  pnpm create @company/mfe operations --id operations
  pnpm create @company/mfe alert-panel --id alert-panel --template widget
```

</Step>

<Step>

```sh
cd <directory>
pnpm install
```

</Step>

<Step>

```sh
pnpm run dev
```

This starts the container's own Rsbuild dev server on its `mfe.port`, and nothing else. There is no
standalone preview harness, so seeing it on a page means starting the shell too.

</Step>

</Steps>

`--id` defaults to the last segment of the directory, and the package name is derived from it as
`@example/<id>`. A non-empty directory is refused unless you pass `--force`. Generation is
deterministic, so a second run produces identical files.

<Callout type="error" title="An id the framework cannot use">
  `"Order_Book" is not a usable definition id. Ids are lower-case letters, digits and single
  hyphens, for example "alert-panel". The id is also the storage prefix and the CSS scope value, so
  it has to be unambiguous in both.`

**Fix.** Pass `--id order-book`.

</Callout>

Both templates write these files:

| File                | What it is                                                                                                                                                                                                                    |
| ------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `package.json`      | the **`mfe` block** (below), eight scripts, and the dependency lists                                                                                                                                                          |
| `.gitignore`        | `node_modules/`, `dist/` and the generated output (`routeTree.gen.ts`, `.mfe/`). No local-values file is listed, because nothing reads one: the values live in `public/runtime-config.json`, which is published, not ignored. |
| `.prettierrc.json`  | no semicolons, single quotes, trailing commas, `printWidth: 100`, `arrowParens: 'avoid'`                                                                                                                                      |
| `eslint.config.ts`  | `mfe.author({ tsconfigRootDir, files: ['src/**/*.{ts,tsx}'] })` and `mfe.tooling({ tsconfigRootDir })` for the build and test configuration beside it                                                                         |
| `tsconfig.json`     | the repo base, plus `paths` for `#mfe/config`, `#mfe/fetch` and `#mfe/meta`                                                                                                                                                   |
| `vitest.config.ts`  | the three `#mfe/*` aliases, `environment: 'jsdom'`, `setupFiles`                                                                                                                                                              |
| `vitest.setup.ts`   | jest-dom's matchers, installed and declared in one file                                                                                                                                                                       |
| `rsbuild.config.ts` | `plugins: [pluginReact(), pluginMfe()]`, the port from the manifest, `server.publicDir`, `dev.lazyCompilation: false`                                                                                                         |

The eight scripts are the same in both templates:

```json title="package.json (scaffolded)"
{
  "dev": "pnpm run generate && rsbuild dev",
  "build": "pnpm run generate && rsbuild build",
  "generate": "mfe-generate",
  "typecheck": "pnpm run generate && tsc --noEmit",
  "test": "pnpm run generate && vitest run",
  "lint": "eslint .",
  "format": "prettier --write .",
  "format:check": "prettier --check ."
}
```

The templates differ in what else they write:

```text
app                              widget
  public/runtime-config.json       src/mfe.ts          the contract and createWidget
  src/mfe.ts                       src/<id>.tsx        the render function alone
  src/mfe.config.ts                src/mfe.test.tsx
  src/routes/__root.tsx            README.md
  src/routes/index.tsx
  src/routes/settings.tsx
  src/routes/index.test.tsx
  README.md
```

An App's dependencies gain `@tanstack/react-router` and `@tanstack/react-query`. Its `src/mfe.ts`
holds the router factory and two `declare module '@tanstack/react-router'` augmentations. The second
types a route's `staticData` with `MfeStaticData`, which [2. Declaring
it](/docs/guides/declaring#declare-an-app) shows.

Its `public/runtime-config.json` keeps a scaffolded App from failing at boot with `config/missing`.

A Widget gets an `exports` map pointing at its generated contract module, and no router. Its render
function lives in `src/<id>.tsx` for the reason under "Keep hot updates working" below.

Every container declares its port and the ids it exports once, and the tooling reads it back:

```json title="examples/operations/package.json"
"mfe": {
  "port": 3001,
  "definitions": ["operations"]
}
```

The scaffold sets `port` to 3101 for an App and 3103 for a Widget, clear of the 3000–3005 the shell
and the examples use. The port is part of the container's address: generation writes
`http://localhost:<port>/mf-manifest.json` into the shell's registry, so a container moved to
another port is lost. `pluginMfe()` sets `server.strictPort: true` for that reason.

`definitions` decides which ids the override snippet assigns. Nothing validates it against what
`src/mfe.ts` exports, so keeping it accurate is a convention.

## Start everything: `pnpm dev`

```sh
pnpm dev                                        # shell + every example
pnpm dev:shell                                  # the shell alone
pnpm dev:mfes                                   # examples only, against a shell you started
node tools/dev/dev.mjs --only=operations,alert-panel
```

| Service                                                            | Port      |
| ------------------------------------------------------------------ | --------- |
| `apps/shell`                                                       | 3000      |
| `examples/operations`, `reports`, `alert-panel`, `insights`, `lab` | 3001–3005 |
| the stand-in API (`tools/dev/api.mjs`)                             | 3010      |

`pnpm dev` checks that 3000–3005 and 3010 are free **before** it starts anything, so a busy port is
reported once and by name. It then runs generation in every container, assembles the registry from
the results, prints the service table and the override snippets, and starts the servers. One Ctrl-C
stops every server and waits for those ports to come back.

The stand-in API is not part of the framework. A deployment brings its own, and this one makes the
request boundary observable. It serves `GET /api/assets?site=north|south|central` and
`GET /api/lab/probe`, whose answer is `{ sawAuthorization, scheme, path }` and never the token.
`MFE_DEV_API_PORT` moves both the check and the server.

## Point the shell at your container

<Steps>

<Step>

Open the shell at `http://localhost:3000` and run the snippet `pnpm dev` printed, in the browser
console:

{/* prettier-ignore */}
```js
const key = "company:mfe:overrides"
const overrides = JSON.parse(localStorage.getItem(key) || '{}')
  overrides["operations"] = "http://localhost:3001/mf-manifest.json"
localStorage.setItem(key, JSON.stringify(overrides))
location.reload()
```

</Step>

<Step>

To reset one id and keep the others, run the same snippet with the middle line replaced:

```js
delete overrides['operations']
```

</Step>

</Steps>

An [override](/docs/glossary) is one entry in `localStorage`, from definition id to absolute
manifest URL. The shell reads it before the registry is normalized and before any remote is
registered. It is a URL only, never a token and never configuration.

The reload is not optional. From `README.md`:

> Changing an override requires a page reload: the old container's modules are already registered in
> the federation runtime under the same name, and its chunks and stylesheets are document-level, so
> disposing a mount touches none of that.

Every way an override can be wrong is reported at boot, as a warning. An override that silently did
nothing is the bug this mechanism exists to prevent.

| What you wrote                                     | What the shell does              |
| -------------------------------------------------- | -------------------------------- |
| storage it cannot read                             | warns, and registers no override |
| text that is not JSON                              | warns, and registers no override |
| a value that is not a string                       | warns, and skips that entry      |
| a relative URL                                     | warns, and skips that entry      |
| two definitions of one container at different URLs | warns, and skips them both       |

The last one reads:

> `expected one consistent override URL for every definition exported by a container … Point every
definition from this container at the same manifest URL. One container is loaded once; conflicting
URLs cannot both apply.`

Nothing on the page says an override is active, because the strip that used to say so was removed
(`docs/decisions.md` §23). An override pointing at a stopped dev server therefore looks exactly like
a broken deployment. The developer tools and the bug report are where it shows.

## Generate the `#mfe` modules

```sh
pnpm run generate           # every container, then the shell's registry
mfe-generate                # this container alone
mfe-generate --root <dir>   # another container
```

At the root, `pnpm run generate` is `pnpm -r run generate` followed by
`node tools/dev/build-registry.mjs`. Inside a container, `mfe-generate` runs the same
`generateContainer` the build runs, so the two cannot drift. None of the output is in version
control, and none of it is edited by hand.

| Generated file                                  | What it is                                | Written when                             |
| ----------------------------------------------- | ----------------------------------------- | ---------------------------------------- |
| `.mfe/styles.css`                               | the container stylesheet                  | always                                   |
| `.mfe/fetch.ts`                                 | the module behind `#mfe/fetch`            | always                                   |
| `.mfe/config.ts`                                | the module behind `#mfe/config`           | `src/mfe.config.ts` exists               |
| `.mfe/meta.ts`                                  | the module behind `#mfe/meta`             | always                                   |
| one federation entry per definition             | what the shell loads                      | always                                   |
| `style-root.tsx`                                | the generated style root                  | the container depends on `@tecton/react` |
| one contract module per Widget                  | the Widget's published inputs and events  | the container exports a Widget           |
| `.mfe/mfe-registry.json`                        | this container's entries for the registry | always                                   |
| `runtime-config.schema.json`, `.env.example`    | the shape of the deployment's values      | there is a config source                 |
| `tsconfig.paths.json`, `css.d.ts`, `.gitignore` | the paths, the CSS types, the ignores     | always                                   |
| `routeTree.gen.ts`, at the container root       | the route tree                            | the container exports an App             |

When nothing changed, the command prints `@example/operations: generated output is already current.`
Findings in your own sources go to stderr and fail the command with exit code 1. A stray definition
and a bare relative asset path are two of them.

This is the one documented recovery command. From `README.md`:

> Generated output (`.mfe/`, `routeTree.gen.ts`, `apps/shell/public/registry.json`) is not in
> version control. If a build behaves as though a file is missing, `pnpm run generate` is the fix.

## Keep hot updates working

```sh
pnpm hmr:probe examples/lab/src/routes/index.tsx /lab
```

```text
file:      examples/lab/src/routes/index.tsx
url:       http://localhost:3000/lab
result:    hot-updated in place
console:   (nothing about hot updates)
```

Keep your render function in a module that exports components alone. React Refresh replaces a module
in place only when it can prove **every** export is a component. One exported hook, constant, schema
or factory beside them makes the module unable to accept an update.

The update then travels up to whatever imported it, as far as an entry, which accepts nothing. The
page reloads, and every piece of state on it is lost.

| Module                | What it exports                      | What an edit costs                      |
| --------------------- | ------------------------------------ | --------------------------------------- |
| `src/mfe.ts`          | a definition, and usually a contract | the page reloads, and its state is gone |
| `src/alert-panel.tsx` | the render function alone            | a hot update in place, with state kept  |

The examples say the same thing in code:

```ts title="examples/alert-panel/src/mfe.ts"
/** The build reads these schemas statically and publishes them in the registry, so a host can offer
 * this Widget in a catalogue without loading the container (§16). The render function lives in
 * `alert-panel.tsx` because a module exporting a contract and a definition is no React Refresh
 * boundary, so an edit here would reload the page (§18). */
```

The symptom is silent: everything still works, it is only slower and starts over each time. The
probe answers the question by putting a value on `window` that a reload cannot carry. The other
result is `result:    (the page reloaded)`, and exit code 0 means a hot update, 1 a reload. It runs
against servers you already started, appends a comment to the file, waits, and restores it.

## Write tests

```sh
pnpm test              # every workspace
pnpm run test          # inside a container: generate, then vitest run
```

Container tests run on Vitest in jsdom. Generation runs first, because the test config resolves
`#mfe/meta` to the real generated module while aliasing the other two to fixtures:

```ts title="examples/operations/vitest.config.ts"
{ find: /^#mfe\/config$/, replacement: '@company/mfe-react/testing/mfe-config' },
{ find: /^#mfe\/fetch$/,  replacement: '@company/mfe-react/testing/mfe-fetch' },
{ find: /^#mfe\/meta$/,   replacement: fileURLToPath(new URL('./.mfe/meta.ts', import.meta.url)) },
```

Your source keeps its production imports, and `tsconfig` still maps them to the real generated
modules, so the types stay exact. `@company/mfe-react/testing` gives you:

- `renderApp(definition, options)` and `renderWidget(definition, options)` — the real adapter and
  the real validation path, over a memory history and in-memory stores.
- `createMfeTestEnvironment(options)` — a runtime, a mount, a `wrapper` for hook tests, a typed
  `routerContext`, `setShellState`, and recorded `telemetry`, `diagnostics`, `navigation` and
  `storageAreas`.
- `renderSuspending(ui)` for a tree that will suspend.
- the alias setters: `setMfeConfig`, `setMfeApiBaseUrl`, `setMfeApiOrigins`, `setMfeFetch`,
  `setMfeAccessToken`, `mfeRequests()` and `resetGeneratedAliases()`.

Every example test disposes the same way:

```ts title="examples/alert-panel/src/mfe.test.tsx"
let cleanup: (() => Promise<void>) | null = null

afterEach(async () => {
  // Cleared before the await: a later test may have assigned a new handle by the time this resolves.
  const dispose = cleanup
  cleanup = null
  await dispose?.()
})
```

## Check before you push

```sh
pnpm check           # what CI runs
pnpm verify:page     # the shell and every example, in a real browser
pnpm diagrams:check  # every committed SVG still matches its scene
```

`pnpm check` is the CI command:

```json
"check": "pnpm run generate && pnpm run format:check && pnpm run lint && pnpm run typecheck && pnpm run boundaries && pnpm run test"
```

Generation, format check, lint, strict typecheck, package-boundary checks and the test suites, in
that order. The steps run individually too: `pnpm format`, `pnpm lint`, `pnpm typecheck`,
`pnpm boundaries`, `pnpm test`.

`pnpm verify:page` generates, boots the shell and every example, and drives Chromium through
Playwright. The first time the shell loaded a real container, five defects appeared that compiled,
type-checked and passed the whole suite while rendering nothing. Per page it asserts that:

- each App mounted from its own container.
- a Widget from a second container rendered inside one.
- a child App delegated at a splat route reads its own URL.
- a popover portals into its own container's overlay root.
- an unloadable manifest costs that App alone.
- the shell chrome renders exactly once.
- every `@scope` fact on the page holds, as [8. Styling](/docs/guides/styling) lists them.

Pass `--url /operations` to check one page, and `--keep-open` to leave the browser up. It needs a
Chromium: `pnpm exec playwright install chromium` once, or `PLAYWRIGHT_BROWSERS_PATH`.

`pnpm diagrams:check` re-renders every Excalidraw scene and fails when a committed SVG no longer
matches. It needs a Chromium too. Neither it nor `pnpm verify:page` belongs to `pnpm check`, which
stays browser-free.

## Troubleshooting

Troubleshoot from the symptom.

| Symptom                                              | Cause                                              | Fix                                          |
| ---------------------------------------------------- | -------------------------------------------------- | -------------------------------------------- |
| `Port 3001 already in use.`                          | a dev server from an earlier run                   | `lsof -i :3001`, then `kill <pid>`           |
| the shell never mentions your container              | the registry does not name it                      | `pnpm run generate` at the root              |
| a build acts as though a file is missing             | the generated output is absent                     | `pnpm run generate`                          |
| your App or Widget does not load, with no other sign | an override points at a stopped dev server         | start it, or clear the override              |
| an override changed and nothing did                  | the page was not reloaded                          | reload the page                              |
| the page reloads on every edit                       | the module you edited exports more than components | move the render function into its own module |

The busy-port message names the process for you:

```text
Port 3001 already in use.

These are not preferences: `pnpm run generate` writes each container's URL
into the shell registry, so a container cannot be moved to another port
without the shell losing it. Usually this is a dev server from an earlier
run that did not shut down.

Find what holds it:

  lsof -i :3001

then stop it with `kill <pid>`.
```

The developer tools are where a container that did not load shows up. They ship in every build and
are gated on one `localStorage` key, because the page where they are most needed is a deployed one.

| How                                                                          | What happens                                                |
| ---------------------------------------------------------------------------- | ----------------------------------------------------------- |
| `http://localhost:3000/?devtools=1`                                          | turns them on and persists it. `?devtools=0` turns them off |
| <Kbd>g</Kbd> <Kbd>d</Kbd>                                                    | opens the panel on the **Overrides** tab                    |
| <Kbd>g</Kbd> <Kbd>r</Kbd>, or <Kbd>⌘</Kbd><Kbd>K</Kbd> → "Open the registry" | opens it on the **Registry** tab                            |
| the wrench, bottom left                                                      | toggles the panel                                           |

- **Overrides** lists every registered definition with the URL it loaded from. Each row offers
  "Point `<id>` at the dev server", "Edit the manifest URL" and "Clear the override". It refuses a
  URL the boot reader would reject, before writing it rather than after the reload.
- **Registry** has two inner views with counts. **Loaded** gives each accepted entry's facts and
  marks an overridden one. **Rejected** names each set-aside entry and its reason.
- **The bug report** is the bug icon in the header, or <Kbd>⌘</Kbd><Kbd>K</Kbd>. It collects the
  workspace, the URL, the mounted definition, the session, every rejected entry, every override and
  each accepted entry's build, as Markdown.

## Windows

Everything above runs on Windows, and every script goes through node rather than a shell. The
busy-port message prints `netstat -ano | findstr :3001` and `taskkill /PID <pid> /F` instead. The
port check probes both `127.0.0.1` and `::1`, because Windows resolves `localhost` to `::1` first. A
server on one address and a check on the other would disagree about whether the port is free.

A fresh clone has no generated output, so an editor opened on it reports errors until something
generates them. `pnpm run generate` is the fix.
