title: '1. The shape: App or Widget'
description: 'Choose between an App and a Widget, declare either one, and read the errors each choice produces.'

One decision comes first: App or Widget. An <Term>App</Term> takes a URL and routes everything
below it, and a <Term>Widget</Term> takes props from whoever renders it. This page gives you the
test for choosing, the smallest working declaration of each, and the errors each shape produces.

## Choose in one question

The question is whether a user should be able to link to the screen. If they should, build an App.
If its consumer decides where it goes, build a Widget.

<Diagram
  src="/diagrams/app-vs-widget.svg"
  alt="A decision diamond asking whether a screen is addressable by a URL, with the App branch on the left and the Widget branch on the right, each listing four calls."
  caption="Apps take URLs. Widgets take props."
>

One question at the top, two answers, and four boxes under each answer.

- The diamond asks **Addressable by a URL?** An arrow labelled `yes` leaves it to the left, and an arrow labelled `no` to the right.
- The left panel is **Yes — it is an App**, subtitled "routable, independently deployable". Four boxes follow, each with an arrow to the next:
  - `https://shell.example/operations/wells`
  - `createApp({ id: 'operations', router })`
  - `createRouter({ basepath: basePath })`
  - `mfeRoute({ appId: 'reports' })`
- The right panel is **No — it is a Widget**, subtitled "non-routable, many per page". Its four boxes run the same way:
  - `createWidget({ id: 'alert-panel' })`
  - `lazyWidget('alert-panel', { contract })`
  - `<AlertPanel alertId={id} onAcknowledged={ack} />`
  - `<DynamicWidget widgetId={id} {...inputs} />`

</Diagram>

| What you have                                                              | Build                             | Choose the other, and                                            |
| -------------------------------------------------------------------------- | --------------------------------- | ---------------------------------------------------------------- |
| A screen a user can bookmark, or that appears in the application finder    | App                               | there is no URL to send a colleague.                             |
| Several screens with their own navigation between them, surviving a reload | App                               | a reload loses where the user was.                               |
| A screen the shell opens by capability — settings, help, release notes     | App                               | the shell cannot open it. Capabilities are App-only.             |
| A panel placed on a dashboard the consumer composes                        | Widget                            | you get a URL for it that nobody wanted.                         |
| A card embedded in somebody else's page, twice, with different ids         | Widget                            | one App owns one boundary, so the second copy has nowhere to go. |
| Something that hands a result back to the page around it                   | Widget, emitting a declared event | nothing carries the result back.                                 |
| Something that needs per-instance data from its consumer                   | Widget                            | an App reads that from its own URL, never from props.            |

## Build an App

```ts title="examples/operations/src/mfe.ts"
function makeRouter({ basePath, history, context }: AppRouterOptions) {
  return createRouter({
    routeTree,
    basepath: basePath,
    history,
    context: { ...context },
    defaultPreload: 'intent',
  })
}

export default createApp({
  id: 'operations',
  version: '2.1.0',
  router: makeRouter,
})
```

An App is an ordinary TanStack Router application plus one call. `createApp` takes an `id`, an
optional `version` and a `router` factory. The framework calls that factory once per
[mount](/docs/glossary), one live instance of a definition on the page. An App mounted twice gets
two independent routers over one generated route tree.

Your factory receives three values and has to pass all three through unchanged.

| Argument   | What you do with it                                                                                                  | Error if you do not     |
| ---------- | -------------------------------------------------------------------------------------------------------------------- | ----------------------- |
| `basePath` | Pass it as `createRouter({ basepath })`. Every route, `Link` and `navigate` is then relative to it.                  | `app/invalid-base-path` |
| `history`  | Forward the instance you were given. `createBrowserHistory()` reassigns `window.history.pushState` for every router. | `app/invalid-router`    |
| `context`  | Spread it: `context: { ...context, yourKey }`. It carries the mount's services and its Query client.                 | `app/invalid-router`    |

The shell owns `/<id>`, and everything below it belongs to your App. Write your own routes as
`/assets` and `/wells/$wellId`, because the mount prefix never appears in your code. Above your App the shell renders the header, the breadcrumb trail, the palette and the theme.
Inside your boundary it renders nothing of its own, so your root route is your layout.

## Nest an App at a splat route

```ts title="examples/operations/src/routes/reports.$.tsx"
import { createFileRoute } from '@tanstack/react-router'
import { mfeRoute } from '@company/mfe-react'

/** A child App takes per-instance data through its own URL, never through inputs (Widgets take props). */
export const Route = createFileRoute('/reports/$')(mfeRoute({ appId: 'reports' }))
```

The child's boundary is the current pathname with the splat remainder removed, which is what
`boundaryAboveSplat` does. So `reports` is mounted at `/operations/reports` and routes
`/accounts/fda-2-3` for itself. A child App's contract is identical to a top-level App's, and it
never learns which boundary it was mounted at.

## Build a Widget

```ts title="examples/alert-panel/src/mfe.ts"
export const alertPanelContract = {
  inputs: z.object({
    alertId: z.string(),
    severity: z.enum(['info', 'warning', 'critical']).default('info'),
  }),
  events: {
    acknowledged: z.object({ alertId: z.string(), acknowledgedAt: z.string() }),
    dismissed: z.object({ alertId: z.string() }),
  },
}

export const alertPanel = createWidget({
  id: 'alert-panel',
  version: '1.4.0',
  ...alertPanelContract,
  render: AlertPanel,
})
```

`createWidget` takes an `id`, an optional `version`, an `inputs` schema, an `events` map and a
`render` function. The two schemas together are the Widget's [contract](/docs/glossary): one source
of truth for runtime validation and for the author-facing types, so the two cannot drift.

`render` receives exactly two props, both typed from the schemas:

```tsx title="examples/alert-panel/src/alert-panel.tsx"
export function AlertPanel({
  inputs,
  emit,
}: WidgetRenderProps<typeof alertPanelContract>): ReactNode {
```

`inputs` arrives already validated and parsed, so schema defaults are applied before your code
runs. Omit `severity` and it is `'info'` inside `render`. `emit` validates the payload at the call
site and refuses any event the contract does not declare.

The build reads both schemas statically and publishes them in the registry. The shell's dashboard
can then draw a form for a Widget it has never imported
([decision 16](/docs/decisions#16-the-registry-carries-each-widgets-contract-because-a-catalogue-is-rendered-before-anything-is-fetched)).
A published `z.enum([...])` becomes a dropdown.

## Consume each one

Each shape is consumed a different way.

| Shape                                | Consumed by             | How                                                            |
| ------------------------------------ | ----------------------- | -------------------------------------------------------------- |
| App, at the top of the page          | the shell               | `AppHost`, at the shell's `/<id>` boundary. Nothing you write. |
| App, inside another App              | the parent App          | `mfeRoute({ appId })` on a splat route                         |
| Widget, known at build time          | any App or the shell    | `lazyWidget(id, { contract })` at module scope                 |
| Widget, known only from the registry | a host composing a page | `<DynamicWidget widgetId={…} />` with `onEvent`                |

```ts title="examples/operations/src/widgets.ts"
import { lazyWidget } from '@company/mfe-react'

import { events, inputs } from '@example/alert-panel/contracts'

export const AlertPanel = lazyWidget('alert-panel', { contract: { inputs, events } })
```

```tsx
<AlertPanel alertId={id} onAcknowledged={event => acknowledge(event.alertId)} />
```

Call `lazyWidget` at module scope. It returns a component, and React uses that component's identity
to decide it is looking at the same element. One built during render creates a new identity every
pass. The host then unmounts the running Widget, throws away its state and refetches its data
([decision 15](/docs/decisions#15-a-host-composing-the-registry-cannot-call-lazywidget)).

Inputs are props, and each declared event arrives as an `onX` prop, both typed from the contract
you passed. The contract is optional: `lazyWidget('alert-panel')` works, with inputs typed as
`Record<string, unknown>` and no consumer-side validation. The provider validates every input and
every event payload either way.

A host that learns which Widgets exist only when it reads the registry cannot call `lazyWidget` at
module scope. It uses `DynamicWidget` instead, which takes the id as a prop and delivers every
event by name through `onEvent(name, payload)`. `lazyWidget` deliberately has no `onEvent`
([decision 28](/docs/decisions#28-reading-a-widgets-published-inputs-is-headless-and-a-test-is-what-keeps-it-honest)).

## Name your definition

Name your definition with lower-case letters, digits and single hyphens, for example `alert-panel`.
Both factories check
the `id` before anything else, because it is also the storage prefix and the CSS scope value.

<Callout type="error" title="registry/invalid-descriptor">

`Order_Book failed to createApp: expected lower-case letters, digits and single hyphens (for
example "alert-panel"), received "Order_Book". Give the definition a stable id; it is also its
storage prefix and CSS scope value.`

**Fix.** Rename the definition to `order-book`.

</Callout>

```ts title="src/mfe.ts"
// Before
export default createApp({ id: 'Order_Book', router: makeRouter })

// After
export default createApp({ id: 'order-book', router: makeRouter })
```

The same check runs in `createWidget`, with `createWidget` in place of `createApp` in the message.

## Errors you will see

Two errors come from the choice between an App and a Widget.

### A Widget was handed the wrong prop type

The Widget validates what it is handed, whatever the consumer believes. A prop that fails the
`inputs` schema is rejected at the provider boundary, with the field, the value and the repair.

<Callout type="error" title="contract/input-mismatch">

`alert-panel@1.4.0 failed to accept input alertId: 7; ✖ Invalid input: expected string, received
number → at alertId. Check the alertId prop on the Widget.`

**Fix.** Send the type the contract declares.

</Callout>

```tsx
// Before: the id came out of a numeric column
<AlertPanel alertId={alert.id} onAcknowledged={ack} />

// After: the contract says string, so send a string
<AlertPanel alertId={String(alert.id)} onAcknowledged={ack} />
```

On the first render there is nothing to fall back to, so the provider throws and the consumer's
`fallback` renders. On a later update the mounted Widget keeps its last valid inputs on screen. It
reports the rejection instead of throwing, so a mistyped filter does not blank the panel.

### Two Apps in one container

One container exports at most one App, and the build stops when it finds a second.

<Callout type="error" title="registry/invalid-descriptor, at build time">

`/home/you/orders/src/mfe.ts: the build failed to collect the definitions this container exports: expected at most one App per container, found 2 Apps ('orders' and 'invoices'). This expectation is declared by the container contract. Split them into separate containers. A container deploys and versions as one unit, and an App owns routing for its whole subtree, so two of them cannot share one.`

**Fix.** Move one App into its own package with its own `src/mfe.ts`. If it was never
URL-addressable, declare it with `createWidget` instead.

</Callout>

## Why a URL decides the shape

A URL decides the shape because being routable is what makes a screen reachable from outside itself.
A deep link into an App
survives a reload, and a user can paste it into a message. The shell's application finder and
command palette open an App by going to its URL, and the breadcrumb trail comes from its route
matches.

A Widget owns no URL, so it gets a typed prop contract instead. A URL cannot express "this one,
here, with these inputs, and another one beside it". A Widget covers those cases: two instances on one
page, or one inside a dialog or a table cell. It also works on a dashboard composed by a shell that
has never imported it.
