---
title: '7. Storage'
description: 'Declare a storage key with a schema, choose who may read the value back, and fix the errors it can raise.'
---

Declare a key with a schema and `useStoredState` hands you the stored value and a setter. Every key
is prefixed with your definition id, and <Term>retention</Term> decides who may read the value back
later. You write no `localStorage` call yourself.

## Store a value: `useStoredState`

```tsx title="src/routes/storage.tsx"
import { useStoredState } from '@company/mfe-react'
import { z } from 'zod'

/** Module scope: a schema rebuilt in a component body is a different object on every render. */
const filtersSchema = z.object({ status: z.enum(['open', 'closed']) })

export function Filters() {
  const [filters, setFilters] = useStoredState('filters', filtersSchema, {
    defaultValue: { status: 'open' },
  })

  return <StatusPicker value={filters.status} onChange={status => setFilters({ status })} />
}
```

Declare the schema at module scope. The framework compares schemas by reference when two components
bind one key. A schema built inside a component body is a new object on every render, and that
rebinds the key each time.

## The options

| Option         | What it is                                                                                     | Default   |
| -------------- | ---------------------------------------------------------------------------------------------- | --------- |
| `name`         | A non-empty string, stable across renders. The stored key is `<definitionId>:<name>`.          | required  |
| `schema`       | A Zod schema at module scope. It types the value and validates every read and write.           | required  |
| `defaultValue` | What you read while the key is absent. It is validated where you declare it, not on first use. | required  |
| `storage`      | `'local'` or `'session'`. The two are separate spaces, so one name in each is two records.     | `'local'` |
| `retention`    | `'user'` or `'browser'`. The next section compares them.                                       | `'user'`  |
| `version`      | An integer of 1 or more. Raise it whenever the stored shape changes.                           | `1`       |
| `migrate`      | `migrate(value, fromVersion)`, synchronous and free of side effects.                           | none      |

The key carries no mount token, so two mounts of one definition read one record. Your definition id
may not contain a `:`, because the colon separates the id from the name. The setter takes a value or
an updater function, and keeps its identity across a rebinding. An unreadable stored value throws
rather than falling back to the default, so a corrupt record reaches an error boundary.

## Choose a retention

Leave `retention` unset unless the value is impersonal.

| What happens                                             | `retention: 'user'` (default) | `retention: 'browser'`                  |
| -------------------------------------------------------- | ----------------------------- | --------------------------------------- |
| the identity changes: sign-in, sign-out, account, tenant | deleted                       | kept, and the next person here reads it |
| the group set changes                                    | deleted                       | kept                                    |
| a reload                                                 | kept                          | kept                                    |
| the tab closes, with `storage: 'session'`                | gone with the tab             | gone with the tab                       |
| the build raises `version`                               | `migrate()`, or unreadable    | `migrate()`, or unreadable              |

`storage` decides how long the browser keeps a value. Retention decides who may read it back.

Each `retention: 'user'` record carries the [session generation](/docs/glossary). It is an opaque
string, created once per signed-in identity per tab and stored at `@host:session-generation`. A
reload of the same tab under the same identity reuses that generation, so your record survives. When
the shell reports an identity change or a changed group set, the framework creates a new generation.

It then deletes every `retention: 'user'` record in both stores, including records for definitions
that are not mounted. A record that survives a failed delete still reads as absent, because its
generation no longer matches. A generation is never reused. A theme change, a token refresh and a
reordered group list change nothing.

```ts title="src/routes/storage.tsx"
// Survives a sign-out, so the next person on this browser reads it.
const [draft, setDraft] = useStoredState('draft', draftSchema, {
  defaultValue: { note: '', pinned: false },
  retention: 'browser',
})

// Dies with the tab, and is deleted on sign-out.
const [visits, setVisits] = useStoredState('visits', visitsSchema, {
  defaultValue: 0,
  retention: 'user',
  storage: 'session',
})
```

<Callout type="warning" title="Choose browser retention only for impersonal state">
  Use `retention: 'browser'` for a display density, a collapsed panel or a chosen tab. Anything
  derived from a signed-in user's data stays on the default. The framework never clears a `browser`
  record, so every user of that browser profile reads the same value.
</Callout>

## Read a value outside render: `useMfeStorage`

```ts title="src/export.ts"
import { useMfeStorage } from '@company/mfe-react'

const storage = useMfeStorage() // 'local' by default; pass 'session' for the other area
const key = storage.key('filters', filtersSchema, { defaultValue: { status: 'open' } })

key.get() // the value, or null for a missing key — never null for an invalid one
key.set({ status: 'closed' })
key.remove()
storage.clear() // only keys under the exact `operations:` prefix
```

Take this handle for an event handler, a loader or a cleanup. `get()` does not subscribe, so
anything you render still uses `useStoredState`. `get()` also forces a fresh read of the browser
store, where `useStoredState` serves a cached snapshot, and an imperative write notifies that key's
subscribers.

`clear()` removes only the exact `<id>:` prefix. A definition called `acme-orders` never touches
`acme-orders-legacy:`, the shell's keys, or another team's. The store never removes what it did not
write.

## The `@host` scope

Outside any mount, in shell chrome or a boot script, `useStoredState` resolves to the reserved scope
`@host`, and the key becomes `@host:dashboard`. A definition id holds only lower-case letters,
digits and single hyphens, so no registry entry can take that name. Inside a mount you always get
your own definition, so the shell's records can never collide with yours.

<Callout type="error" title="storage/failure">
  @host failed to bind a storage key: expected a definition id, received the reserved host scope
  '@host'. Use bindHost() or hostStorage() for state the host page owns; they reach the same scope
  deliberately.

**Fix.** From inside a mount, drop the scope argument and let it resolve to your definition. Only
shell code reaches `@host`, through `bindHost()` or `hostStorage()`.

</Callout>

## Migrate a stored value

Raise `version` whenever the stored shape changes, and declare `migrate` beside it.

```ts title="src/filters.ts"
const [filters] = useStoredState('filters', filtersSchema, {
  defaultValue: { status: 'open' },
  version: 2,
  migrate: (value, fromVersion) =>
    fromVersion === 0
      ? { status: 'open' }
      : { status: (value as { open: boolean }).open ? 'open' : 'closed' },
})
```

Four rules govern what happens next.

- A record written by a **newer** build is an error, and is never overwritten.
- An older record with no `migrate` declared is an error.
- A record that is valid JSON but not a framework stored record goes to `migrate(parsed, 0)`. That
  covers anything written before this boundary existed.
- A migration converts, validates, then writes, and only while the generation it started in still
  holds. Nothing is written when it throws, returns an invalid value, or the session moved on.

## Size limits and serialization

The framework sets no size limit of its own. The browser's limit reaches you as a quota error
carrying the serialized character count. Values are stored with `JSON.stringify`, so store plain
JSON. A stored value is not screened for non-serializable types first, so a `Date` round-trips as a
string and then fails your own schema.

## The lint rule: `mfe/no-raw-storage`

Replace every `localStorage` and `sessionStorage` call with `useStoredState()` or `useMfeStorage()`.

The rule is on in the `author` preset. It reports a global reference to `localStorage` or
`sessionStorage`, and `window.localStorage`-style member access. A local variable of the same name
and a type position are not runtime access, so neither is reported. The rule is off in test files
alone, because a storage test has to reach the storage it verifies.

<Callout type="error" title="mfe/no-raw-storage">
  `localStorage` bypasses the MFE storage boundary: the key is not namespaced, so another MFE in
  this origin can read or overwrite it, the shell cannot clear it on sign-out, and a quota failure
  escapes as an unhandled exception. Use `useStoredState()` for component state or `useMfeStorage()`
  for imperative access, both from @company/mfe-react. The storage adapter and a documented shell
  override bootstrap opt out through this rule's `allowedScopes` option.

**Fix.** Bind the key with `useStoredState()`, or take the handle with `useMfeStorage()`.

The editor offers a suggestion rather than a fix. It reads: "Read and write through the MFE storage
boundary: replace `localStorage` with `storage` from `const storage = useMfeStorage()`." A fix would
compile only once the file binds `useMfeStorage()`.

</Callout>

## Every storage failure, and its fix

Every one carries `code: 'storage/failure'`. The message composes as
`<id> failed to <verb> the <area> storage key <name>: expected …, received …. <repair>`, for example
`lab failed to write the local storage key draft: …`. The verb is one of `bind`, `read`, `write`,
`remove`, `migrate` or `clear`. Each failure also reaches the diagnostics hub with
`context: { definitionId, area, key }` before it is thrown.

**Binding a key**

| You see: expected / received                                                                  | Do                                             |
| --------------------------------------------------------------------------------------------- | ---------------------------------------------- |
| `a non-empty storage key name`                                                                | Give the key a stable name.                    |
| `a definition id without a colon`                                                             | Use your registry definition id.               |
| `an integer schema version of 1 or more`                                                      | Start at `1`, and raise it with a `migrate()`. |
| `a default matching the declared schema (…)`                                                  | Fix `defaultValue` to match the schema.        |
| `the same schema object every active consumer already declared` / `a different schema object` | Export one schema from one module.             |
| `retention 'user'` / `retention 'browser'`, or a differing `version` or default               | Make both consumers declare the same option.   |

A disagreement is reported to the consumer that disagrees, not to whoever rendered first. The schema
comparison is by reference, and that is what puts the schema at module scope. The `defaultValue`
comparison is structural, so an inline object literal is fine.

<Callout type="error" title="storage/failure, at bind">
  lab failed to bind the local storage key draft: expected the same schema object every active
  consumer already declared, received a different schema object. Declare 'lab:draft' in one shared
  module so every consumer agrees on schema.

**Fix.** Move the `z.object({ … })` out of the component and export it from one module both
consumers import.

</Callout>

**Reading a key**

| You see: expected / received                                                            | Do                                            |
| --------------------------------------------------------------------------------------- | --------------------------------------------- |
| `a record written through the framework storage boundary` / `text that is not JSON (…)` | Remove the key.                               |
| `a framework envelope at version 1` / `an unversioned record (an object)`               | Declare `migrate()`, or remove the key.       |
| `the session generation to be established before a user value is read`                  | Establish the generation before mounting.     |
| `a stored value matching the declared schema (…)`                                       | Raise `version` and declare `migrate()`.      |
| `version 1` / `version 2, written by a newer build`                                     | Reload into the current build.                |
| `version 1` / `version 2 with no migrate() declared`                                    | Declare `migrate()`, or remove the key.       |
| `local storage to be readable`                                                          | Nothing to fix in code: the store is blocked. |

Storage that is blocked stays blocked. Private mode, blocked cookies and a disabled store all read
this way, and the framework never falls back to memory or to your declared default.

**Migrating**

| You see: received                                          | Do                                            |
| ---------------------------------------------------------- | --------------------------------------------- |
| `migrate() threw (…)`                                      | Fix `migrate()`. The old record is preserved. |
| `a migrated value matching the declared schema (…)` failed | Fix `migrate()`. Nothing was overwritten.     |
| `the session moved on while it ran`                        | Nothing was written. Expect the default.      |

**Writing a key**

| You see: expected / received                                                                      | Do                                                       |
| ------------------------------------------------------------------------------------------------- | -------------------------------------------------------- |
| `the session generation to be established before a user value is written` / `no session in force` | Establish the generation, or use `retention: 'browser'`. |
| `a readable current value for the functional update to apply to`                                  | Write an explicit value, or remove the key first.        |
| `a value matching the declared schema (…)`                                                        | Fix the value you pass to `set()`.                       |
| `a JSON-serializable value`                                                                       | Store plain JSON.                                        |
| `local storage to accept 2097152 characters` / `QuotaExceededError`                               | Persist less, or clear this definition.                  |
| `the write to commit in the generation it started in ('…')` / `the session moved on to '…'`       | Drop the result and start again.                         |
| `to remove 'lab:draft'`                                                                           | Retry the removal.                                       |

**Clearing**

| You see: expected                                  | Do                                         |
| -------------------------------------------------- | ------------------------------------------ |
| `to enumerate local storage for keys under 'lab:'` | Check that the store is readable.          |
| `to remove 'draft'`                                | Retry. Nothing outside `lab:` was touched. |

In every write and clear failure above, the stored value is unchanged.

<Callout type="error" title="storage/failure, at write">
  lab failed to write the local storage key draft: expected local storage to accept 2097152
  characters, received QuotaExceededError: The quota has been exceeded. The store is full or
  blocked. Persist less, or clear this definition. The stored value is unchanged.

**Fix.** Persist an identifier and refetch the body, or call `storage.clear()` for this
definition. The previous stored value is untouched.

</Callout>

## Why `localStorage` is off limits

One browser profile carries several people over a day, and one page carries several containers. Web
Storage is a single flat key space, shared by every container and by the shell. Three things follow.

- Keys collide, because two teams pick the same name.
- The shell cannot clear your keys when somebody signs out.
- A quota failure escapes as an unhandled exception, in whichever container wrote last.

The framework's keys carry your definition id and, by default, the session generation. That is what
makes a stored value yours and nobody else's.
