---
title: '6. Lifecycle'
description: 'What happens to your App or Widget between the moment the shell needs it and the moment it is gone.'
---

You export a definition and the framework does the rest, which is comfortable until something goes
wrong and you need to know where. This page follows one <Term>mount</Term> — one live instance of
your App or Widget on the page, with its own abort signal, Query client, storage surfaces and
overlay root — from the fetch that brings your code onto the page to the teardown that removes it.
Everything here is the React adapter's behaviour: `packages/mfe-react`, which is what runs in the
browser.

Three words you will meet throughout. A <Term>definition</Term> is the plain, side-effect-free
descriptor `createApp` or `createWidget` returns; the <Term>shell</Term> is the application that
owns the document and mounts the others into itself; a <Term>container</Term> is your deployable,
loaded at run time through <Term>Module Federation</Term>, the bundler mechanism that lets one page
run code from another build. An App's <Term>boundary</Term> is the stretch of URL the shell assigns
that mount, and everything below it belongs to the App.

<Callout type="info" title="There is no deadline">
  Nothing on this path imposes a time budget. The load suspends until it settles or fails, and there
  is no automatic retry, no backoff and no retry budget. A retry is something a person clicks.
  `createMfeRuntime` takes no option that adds a budget. If you have read about `load/timeout`,
  `mount/timeout` and `dispose/timeout`: those codes belong to `MountController`, a state machine in
  `@company/mfe-host` that the React adapter does not use, and they never fire here.
</Callout>

Five stages run left to right, each an arrow to the next. Below them a band collects the failure

- **the load suspends** — `loadDefinition(runtime, id)`. React Suspense shows the pending slot while
  the container is fetched: the shell's "Loading operations", or the `pending` prop a Widget's
  consumer passed. One load per container per runtime, shared by every waiter and cached, a
  rejection included. There is no time budget; the load suspends until it settles. An arrow goes
  down from this box into the failure band.
- **the definition is checked** — `isMfeDefinition`, then the router. What the container exposed has
  to be a definition made by `createApp` or `createWidget`, and of the kind the registry advertised.
  For an App the router the author's factory returned is checked too: the `basePath` passed through
  unchanged, the supplied history itself, and the supplied context. An arrow goes down from this box
  into the failure band.
- **the mount is created** — `createMount(...)`. An effect creates it and the same effect's cleanup
  destroys it, so one render passes with no mount. It allocates a mount token, the scope root and
  the style root, an overlay root in the document, a tracer, a Query client, the definition's two
  storage areas, and the `AbortSignal` `useMfeSignal` hands the author.
- **rendered, taking input** — `AppMount` / `WidgetMount`. The App routes inside its own boundary. A
  Widget validates every committed input change, and every event it emits. A rejected input keeps
  the last one that passed and reports a diagnostic; it never blanks a Widget already on the page. A
  loop arrow returns to this box, labelled "inputs updated, or an event emitted". An arrow goes down
  from this box into the failure band.
- **disposed** — `dispose()`. Registrations go first, so a disposed mount cannot appear in the
  palette mid-teardown: commands, then the navigator. Then the signal aborts, queries are cancelled
  and cleared, telemetry ends, and the overlay root is removed from the document.
- **Where a failure goes** — six codes in a row: `load/manifest-failure`, `load/entry-failure`,
  `app/invalid-base-path`, `app/invalid-router`, `contract/input-mismatch`,
  `contract/event-mismatch`. The first four are thrown, caught by the `RetryBoundary` and handed to
  the fallback slot as `{ error, retry }`: the shell draws "operations could not be loaded" with the
  message, the code and a Retry button, and `retry()` forgets the cached load so the next attempt is
  a genuinely fresh one. A Widget's first bad input throws the same way; a later one is reported as
  a diagnostic and the last inputs that passed stay on the page. A render error inside a mounted App
  reaches that App's own `defaultErrorComponent`, inside its own boundary, and the host never sees
  it.
- **StrictMode mounts everything twice** — in development React mounts, unmounts and mounts again
  without re-rendering: create, dispose, create. That is why the mount is built by the effect that
  destroys it. A mount built in `useMemo` is not re-evaluated on the second setup, so the second
  setup ran against the object the first cleanup had already disposed — a `CancelledError` in
  development, while production worked.

</Diagram>

## The load suspends

Your code is not in the page's build, so the first thing that has to happen is a fetch — and
something has to fill the space while it runs. A consumer renders `AppHost` (or the component
`lazyWidget` returned). That component calls
`use(loadDefinition(runtime, id, kind))`, so React suspends there while the federation container is
registered and its entry module fetched.

What fills the space is the consumer's: the shell renders a `role="status"` box reading
**Loading operations** / "Fetching the container this application is deployed in. Its code is not
part of the shell's build, so this is the first time this page has asked for it." A Widget's
consumer passes a `pending` prop, and the default is nothing — `lazyWidget` puts its own `Suspense`
around the loader so one Widget's load never suspends the whole consuming page.

The promise is cached per runtime per id, **including a rejection**: React needs the same settled
promise to surface the failure, and a cache that evicted itself would suspend forever and refetch as
fast as the network allows. The failure reaches the diagnostics hub once, off that cached promise,
so one attempt is one diagnostic however many consumers were waiting.

`RetryBoundary` turns a rejection into something a person can act on, and it exists only when the
consumer supplied a `fallback`. It catches the throw, normalizes anything that is not already an
`MfeError` to `code: 'mount/failure'`, and calls `fallback({ error, retry })`. The shell draws that
as the title `operations could not be loaded`, the whole `error.message` below it, a **Retry** button
and the bare `error.code`. Retry drops the cached outcome and remounts the loader — a genuinely
fresh attempt.

## The definition is checked before anything renders

Two checks, in order. First, that the module the container exposed is a framework definition of the
kind the registry advertised.

<Callout type="error" title="load/entry-failure">
  reports@1.2.0 failed to resolve App: expected a definition created with createApp, received a
  module that is not a framework definition. Export the App from src/mfe.ts and rebuild the
  container.

**Fix.** Export the definition from `src/mfe.ts` — discovery reads the entry only — and rebuild.

</Callout>

Then, for an App, the router your factory returned. The factory is called once per mount with
`{ basePath, history, context }`, and all three have to come back through it. The check runs inside
the memo that built the router, so a violation throws during render and lands on the consumer's
`fallback`.

| `…failed to mount App: expected the supplied basePath "/operations" passed through unchanged as createRouter({ basepath }), received "/orders". | `…failed to mount App: expected the exact history instance the framework supplied, received a different history object. | `…failed to mount App: expected the supplied top-level queryClient, forwarded unchanged, received a different Query client. ## The mount is created by the effect that destroys it

`createMount` allocates, in this order: a mount token (`operations#1`), an `AbortController`, a
`QueryClient`, the telemetry surface, and an overlay root appended to `document.body`. `basePath` is
forced to `''` for a Widget, which owns no URL.

It runs inside `useOwnedMount`'s effect, not during render — the mount appends a node to the
document, starts a tracer and allocates a Query client, none of which belong in a render React may
discard. One render therefore passes with no mount and returns `null`.

Around your code the framework then renders the mount provider, the Query provider, the **scope
root** (the element carrying `data-mfe-scope="<id>"` that your container's `@scope` rule selects on)
and the **style root** the build attached, and for an App the `RouterProvider`.

The only handle you are given is the disposal signal:

```tsx title="src/panel.tsx"
import { useMfeSignal } from '@company/mfe-react'
import { useEffect } from 'react'

export function Panel() {
  const signal = useMfeSignal()

  useEffect(() => {
    window.addEventListener('resize', onResize, { signal })
  }, [signal])

  return null
}
```

The same signal reaches route callbacks as `context.mfe.signal`. There is no observable mount state
object: `MountState` is a type in `@company/mfe-core`, `@company/mfe-react` does not re-export it,
and the React adapter never produces one for an author.

**Two mounts of one App, from one route tree.** `router` is a factory called once per mount, not
once per module, so a page showing the same App twice — or an App hosting itself at a splat route —
gets two independent routers over the one generated tree, each with its own mount, its own Query
client and its own storage bindings.

## A Widget's inputs are revalidated on every committed change

The consumer's props are split into inputs and `on…` handlers. On each render the incoming inputs
are compared to the last set checked, first by reference and then shallowly — so replacing only a
handler is not an input change and revalidates nothing.

A genuine change is validated in three steps: serializability first (so the diagnostic names the
real problem), then your `inputs` schema, then the parsed key names against the reserved ones. An
accepted update publishes a snapshot to the mount that is already there; it does not remount your
Widget.

**A rejected update keeps the last inputs that passed on screen.** The error is reported to the
diagnostics hub from an effect, with `context: { widget: 'alert-panel' }`, because an abandoned
render must not reach the sink. Nothing is appended to the message about the previous inputs — the
behaviour is real, the sentence is not.

The exception is the **first** validation: there is nothing to fall back to, so the error is thrown
and reaches the consumer's `fallback` or the nearest error boundary.

<Callout type="error" title="contract/input-mismatch">
  alert-panel@1.4.0 failed to accept input alertId: 7; ✖ Invalid input: expected string, received
  number → at alertId. Check the alertId prop on the Widget.

The framework's own half is the first clause and the last sentence; the part after the semicolon is
Zod's wording and varies with the schema. **Fix.** Pass a string from the consuming component; on a
later update, the last valid inputs are still rendered while you do.

</Callout>

## Events are validated where they are emitted

`emit(name, payload)` checks, in order, that the event is declared, that the payload is
JSON-serializable, and that it matches the declared schema. All three throw at the call site, which
keeps the failure in your own stack rather than in the consumer's.

<Callout type="error" title="contract/event-mismatch">
  alert-panel@1.4.0 failed to emit event 'resolved': expected one of the declared events
  (acknowledged, dismissed), received 'resolved', which this Widget does not declare. Add 'resolved'
  to the events schema, or emit a declared event.

**Fix.** Add the event to the `events` record in your contract and rebuild, or emit one you
already declare.

</Callout>

If the consumer supplied its own runtime contract and declared this event, the payload is validated
a second time against **their** schema. A failure there is reported to diagnostics and the event is
dropped, not thrown: their narrower expectation is not your bug. Handlers are read from a ref
holding the latest committed ones, so the channel is never rebuilt and no callback from an abandoned
render is ever called.

## Holding a navigation

Inside an App, use TanStack's own `useBlocker`; the framework registers one delegate for the mount
and widens your blockers to navigations your router never sees, including those started by the shell
and by sibling containers. `useNavigationBlock` remains for a mount with no router of its own, which
means a Widget.

```tsx title="src/draft.tsx"
import { useNavigationBlock } from '@company/mfe-react'

export function Draft({ isDirty }: { readonly isDirty: boolean }) {
  const { pending, proceed, stay } = useNavigationBlock(isDirty)

  if (pending === null) return null
  return <ConfirmDialog onConfirm={proceed} onCancel={stay} />
}
```

The mount stays mounted for as long as `pending` is set: the host is holding the navigation and
waiting for your answer. You render your own confirmation rather than `window.confirm`. A mount that
disappears mid-negotiation answers `proceed` on the way out, because a host left without an answer
refuses every later navigation as already negotiating.

## Disposal, in order

Disposal runs from the effect cleanup, on every React unmount.

1. Command and navigator registrations are removed first, so a disposed mount cannot appear in the
   palette mid-teardown.
2. The abort signal aborts. Anything you wired with `{ signal }` is torn down for you.
3. In-flight queries are cancelled — signalled, not awaited, because teardown must not block on a
   request — and the mount's Query cache is cleared.
4. Telemetry is disposed; spans still open at that point are reported in development.
5. The overlay root is removed from `document.body`.

Registrations made by a component — `useCommand`, `useBreadcrumbs`, `useNavigationBlock`,
`useStoredState` — clean themselves up in their own effect cleanups, so they go when the component
goes, not only when the mount does.

**What disposal does not touch is the container module cache.** The loaded module and the cached
load promise outlive the mount, so mounting the same App again does not refetch it. That is also why
a development override — the `localStorage` entry that points one definition at your dev server — is
read once at boot and needs a page reload to change: unmounting the container it redirects does not
forget it.

## StrictMode mounts everything twice

In development React mounts, unmounts and mounts again **without re-rendering**: create, dispose,
create. The framework is shaped around it — the mount is built by the effect that destroys it, and
the boundary history subscribes in an effect rather than at construction — so what you write only
has to tolerate running its effects twice. The regression test asserts, from inside the mount, that
after the double-invoke `useMfeSignal().aborted` is still `false`, the overlay root is still
connected and the Query cache is still usable; every one of those is false on the mount React tore
down.

For you this means two things: `src/mfe.ts` must stay side-effect-free, and any effect you write
must be idempotent and clean up after itself.

## When a render throws

Inside an App, your own `defaultErrorComponent` catches route-level throws first, inside your
boundary, and the host never sees them. The examples all set one. The consumer's `fallback` covers
an App that could not load at all, which is a different failure.

Anything that escapes reaches `RetryBoundary`, is wrapped as `mount/failure` with your definition id
and the operation, and is handed to the `fallback` slot. Every framework failure on this page — load,
validation, input, event, storage, disposal — also reaches the diagnostics hub the shell installed,
as a `Diagnostic` carrying the severity, the `MfeError`, a small non-sensitive context object and a
timestamp. A hub with no sinks discards everything, so if you are debugging and seeing nothing,
check that the shell registered one.

## Testing a lifecycle

`@company/mfe-react/testing` runs the real adapter: the same validation, the same mount, the same
disposal, over in-memory storage, navigation and telemetry.

```tsx title="src/mfe.test.tsx"
import { renderWidget } from '@company/mfe-react/testing'
import { screen } from '@testing-library/react'
import userEvent from '@testing-library/user-event'
import { expect, it, vi } from 'vitest'

import { alertPanel } from './mfe.ts'

it('emits a validated acknowledgement', async () => {
  const onAcknowledged = vi.fn()
  const rendered = renderWidget(alertPanel, {
    props: { alertId: 'a-42', severity: 'critical', onAcknowledged },
  })

  await userEvent.click(screen.getByRole('button', { name: 'Acknowledge' }))
  expect(onAcknowledged).toHaveBeenCalledTimes(1)

  await rendered.dispose()
})
```

`renderApp(definition, options)` does the same for an App over a memory history.
`createMfeTestEnvironment()` gives you the pieces directly: `wrapper` for hooks, `routerContext` for
route callbacks, `diagnostics` as an array to assert on, `setShellState` to drive a real identity or
group change, `storageAreas` to inspect what was written, and `dispose()`. `renderSuspending(ui)`
renders a tree that will suspend, inside an awaited `act` scope — what you need when you exercise
the load itself. A first bad input throws, so assert it with `expect(() => renderWidget(…)).toThrowError(…)`.
