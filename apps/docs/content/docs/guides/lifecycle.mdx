A <Term>mount</Term> is one live instance of your App or Widget on the page, with its own abort
signal, Query client, storage and overlay root. This page follows one mount through five stages,
from the fetch that brings your code onto the page to the teardown that removes it. Nothing on that
path runs under a time limit, so a load suspends until it settles or fails, and a retry is a
person's click.

## The five stages

Everything below is the React adapter's behaviour, in `packages/mfe-react`.

<Steps>

<Step>
  **Your container is fetched**. React suspends, and the consumer's pending slot fills the space.
</Step>

<Step>
  **The definition is checked**. It must be a real definition of the declared kind, with a router
  that forwarded what the framework supplied.
</Step>

<Step>
  **The mount is created**. An effect allocates the token, the roots, the tracer, the Query client,
  the storage areas and the abort signal.
</Step>

<Step>
  **Inputs and events are validated**. A Widget checks every committed input change and every event
  it emits.
</Step>

<Step>
  **The mount is disposed**. Registrations go first, then the signal, the queries, telemetry and the
  overlay root.
</Step>

</Steps>

## Stage 1: your container is fetched

Your code is not in the page's build, so the first thing that happens is a fetch. A consumer
renders `AppHost`, or the component `lazyWidget` returned. That component calls
`use(loadDefinition(runtime, id, kind))`, so React suspends while the federation container is
registered and its entry module is fetched.

The consumer decides what fills the space. The shell renders a `role="status"` box:

> **Loading operations** · Fetching the container this application is deployed in. Its code is not
> part of the shell's build, so this is the first time this page has asked for it.

A Widget's consumer passes a `pending` prop, and the default is nothing. `lazyWidget` puts its own
`Suspense` around the loader, so one Widget's load never suspends the whole consuming page.

The promise is cached per runtime per id, **including a rejection**. React needs the same settled
promise to surface the failure, and a cache that evicted itself would refetch as fast as the
network allows. The failure reaches the diagnostics hub once, off that cached promise, so one
attempt is one diagnostic however many consumers were waiting.

## Stage 2: the definition is checked

Two checks run before anything of yours renders. First, the module the container exposed has to be
a framework definition of the kind the registry declared.

<Callout type="error" title="load/entry-failure">
  reports@1.2.0 failed to resolve App: expected a definition created with createApp, received a
  module that is not a framework definition. Export the App from src/mfe.ts and rebuild the
  container.

**Fix.** Export the definition from `src/mfe.ts`, which is the only file discovery reads, and
rebuild.

</Callout>

Then, for an App, the framework checks the router your factory returned. The factory is called once
per mount with `{ basePath, history, context }`, and all three have to come back through it. The
check runs in the memo that built the router, so a violation throws during render.

| You see                                                                                                                                                                                                                                                                       | Do                              |
| ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------- |
| `…failed to mount App: expected the supplied basePath "/operations" passed through unchanged as createRouter({ basepath }), received "/orders". Forward the basePath your factory received: createRouter({ basepath: basePath, … }).`                                         | Pass `basepath: basePath`       |
| `…failed to mount App: expected the exact history instance the framework supplied, received a different history object. Do not create, wrap, replace or mutate the history; forward the one your factory received.`                                                           | Pass `history` straight through |
| `…failed to mount App: expected the supplied context.mfe namespace, spread into the router context unchanged, received a replaced or rebuilt mfe namespace. Spread the supplied context: add your own top-level keys freely, but do not replace mfe or add fields inside it.` | `context: { ...context, mine }` |
| `…failed to mount App: expected the supplied top-level queryClient, forwarded unchanged, received a different Query client. Spread the supplied context rather than constructing your own Query client; the mount owns one.`                                                  | Do not build a `QueryClient`    |

## Stage 3: the mount is created

`createMount` allocates, in this order:

| What                                        | Note                                          |
| ------------------------------------------- | --------------------------------------------- |
| a mount token, `operations#1`               | the internal discriminator between two mounts |
| an `AbortController`                        | its signal is what `useMfeSignal()` returns   |
| a `QueryClient`                             | one per mount, cleared at disposal            |
| the telemetry surface                       | tracer, events, logs and measurements         |
| an overlay root appended to `document.body` | every dialog and popover portals into it      |

`basePath` is forced to `''` for a Widget, which owns no URL. Around your code the framework
renders the mount provider, the Query provider and the scope root carrying `data-mfe-scope="<id>"`.
It also renders the style root the build attached, and the `RouterProvider` for an App.

The only handle you are given is the disposal signal:

```tsx title="src/panel.tsx"
import { useMfeSignal } from '@company/mfe-react'
import { useEffect } from 'react'

export function Panel() {
  const signal = useMfeSignal()

  useEffect(() => {
    window.addEventListener('resize', onResize, { signal })
  }, [signal])

  return null
}
```

The same signal reaches route callbacks as `context.mfe.signal`. There is no observable mount state
object: `MountState` is a type in `@company/mfe-core` that the React adapter never produces.

`router` is a factory called once per mount, not once per module. A page showing the same App twice
gets two independent routers over the one generated tree. So does an App hosting itself at a splat
route. Each router has its own mount, Query client and storage bindings
([decision 2](/docs/decisions#2-one-generated-route-tree-can-back-two-concurrent-mounts)).

## Stage 4: inputs and events are validated

```tsx
<AlertPanel alertId="a-42" severity="critical" onAcknowledged={ack} />
```

The provider splits the consumer's props into inputs and `on…` handlers. On each render it compares
the incoming inputs to the last set it checked, first by reference and then shallowly. Replacing
only a handler is not an input change and revalidates nothing.

A genuine change is validated in three steps:

1. Serializability, checked first so the diagnostic names the real problem.
2. Your `inputs` schema.
3. The parsed key names, against the reserved ones.

An accepted update publishes a snapshot to the mount that is already there. It does not remount
your Widget.

**A rejected update keeps the last inputs that passed on screen**. The framework reports the error
to the diagnostics hub from an effect, with `context: { widget: 'alert-panel' }`. An abandoned
render must not reach the sink. The **first** validation is the exception: there is nothing to fall
back to, so the error is thrown and reaches the consumer's `fallback`.

<Callout type="error" title="contract/input-mismatch">
  alert-panel@1.4.0 failed to accept input alertId: 7; ✖ Invalid input: expected string, received
  number → at alertId. Check the alertId prop on the Widget.

The first clause and the last sentence are the framework's. The part after the semicolon is Zod's
wording and varies with the schema. **Fix.** Pass a string from the consuming component. On a later
update, the last valid inputs stay on screen while you do.

</Callout>

`emit(name, payload)` checks, in order, that the event is declared, that the payload is
JSON-serializable, and that it matches the declared schema. All three throw at the call site, which
keeps the failure in your own stack rather than in the consumer's.

<Callout type="error" title="contract/event-mismatch">
  alert-panel@1.4.0 failed to emit event 'resolved': expected one of the declared events
  (acknowledged, dismissed), received 'resolved', which this Widget does not declare. Add 'resolved'
  to the events schema, or emit a declared event.

**Fix.** Add the event to the `events` record in your contract and rebuild, or emit one you already
declare.

</Callout>

If the consumer supplied its own runtime contract and declared this event, the payload is validated
a second time against **their** schema. A failure there is reported and the event is dropped rather
than thrown, because their narrower expectation is not your bug. Handlers are read from a ref
holding the latest committed ones, so no callback from an abandoned render is ever called.

## Stage 5: disposal, in order

Disposal runs from the effect cleanup, on every React unmount.

1. Command and navigator registrations are removed first, so a disposed mount cannot appear in the
   palette mid-teardown.
2. The abort signal aborts. Anything you wired with `{ signal }` is torn down for you.
3. In-flight queries are cancelled, and the mount's Query cache is cleared. Cancelling signals the
   requests rather than awaiting them, because teardown must not block on a request.
4. Telemetry is disposed. Spans still open at that point are reported in development.
5. The overlay root is removed from `document.body`.

Registrations a component made — `useCommand`, `useBreadcrumbs`, `useNavigationBlock`,
`useStoredState` — clean themselves up in their own effect cleanups. They go when the component
goes, not only when the mount does.

**Disposal does not touch the container module cache**. The loaded module and the cached load
promise outlive the mount, so mounting the same App again does not refetch it. A development
override behaves the same way: that `localStorage` entry is read once at boot, and changing it
needs a page reload.

## Where each failure goes

| Code                                        | Thrown or reported                              | What the consumer sees                                    | Fix                                                  |
| ------------------------------------------- | ----------------------------------------------- | --------------------------------------------------------- | ---------------------------------------------------- |
| `load/manifest-failure`                     | thrown, caught by `RetryBoundary`               | the failure box, with the message, the code and **Retry** | Check the manifest URL on the registry entry         |
| `load/entry-failure`                        | thrown, caught by `RetryBoundary`               | the failure box                                           | Export the definition from `src/mfe.ts`              |
| `app/invalid-base-path`                     | thrown during render                            | the failure box                                           | `createRouter({ basepath: basePath })`               |
| `app/invalid-router`                        | thrown during render                            | the failure box                                           | Forward the history and spread the context           |
| `contract/input-mismatch`, first validation | thrown                                          | the failure box                                           | Fix the prop the message names                       |
| `contract/input-mismatch`, later update     | reported to diagnostics                         | the last inputs that passed, still on screen              | Fix the prop; nothing blanks                         |
| `contract/event-mismatch`                   | thrown at the `emit` call site                  | your own error boundary                                   | Declare the event, or emit a declared one            |
| a render error inside a mounted App         | caught by your `defaultErrorComponent`          | your error component, inside your boundary                | Handle it in your App; the host never sees it        |
| a container that never loads                | nothing is thrown, because there is no deadline | the pending slot, until the load settles or fails         | Retry is the consumer's button, and a person's click |

`RetryBoundary` exists only when the consumer supplied a `fallback`. It catches the throw,
normalizes anything that is not an `MfeError` to `code: 'mount/failure'`, and calls
`fallback({ error, retry })`. The shell draws the title `operations could not be loaded`, the
`error.message`, a **Retry** button and the bare `error.code`. Retry drops the cached outcome, so
the next attempt is a genuinely fresh one.

Every failure on this page also reaches the diagnostics hub the shell installed. The `Diagnostic`
carries the severity, the `MfeError`, a small non-sensitive context object and a timestamp. A hub
with no sinks discards everything, so check that the shell registered one if you are debugging and
seeing nothing ([10. Shipping and failures](/docs/guides/shipping-and-failures)).

## Hold a navigation

```tsx title="src/draft.tsx"
import { useNavigationBlock } from '@company/mfe-react'

export function Draft({ isDirty }: { readonly isDirty: boolean }) {
  const { pending, proceed, stay } = useNavigationBlock(isDirty)

  if (pending === null) return null
  return <ConfirmDialog onConfirm={proceed} onCancel={stay} />
}
```

Inside an App, use TanStack's own `useBlocker`. The framework registers one delegate for the mount
and widens your blockers. They then cover navigations your router never sees, including those the
shell and sibling containers start. `useNavigationBlock` is for a mount with no router of its own,
which means a Widget.

The mount stays mounted for as long as `pending` is set, because the host is holding the navigation
and waiting for your answer. You render your own confirmation rather than `window.confirm`. A mount
that disappears mid-negotiation answers `proceed` on the way out, because a host left without an
answer refuses every later navigation.

## StrictMode mounts everything twice

In development React mounts, unmounts and mounts again **without re-rendering**: create, dispose,
create. The framework is shaped around it, so your code only has to tolerate running its effects
twice.

For you that means two things. `src/mfe.ts` must stay side-effect-free. Any effect you write must
be idempotent and clean up after itself.

## Test a lifecycle

```tsx title="src/mfe.test.tsx"
import { renderWidget } from '@company/mfe-react/testing'
import { screen } from '@testing-library/react'
import userEvent from '@testing-library/user-event'
import { expect, it, vi } from 'vitest'

import { alertPanel } from './mfe.ts'

it('emits a validated acknowledgement', async () => {
  const onAcknowledged = vi.fn()
  const rendered = renderWidget(alertPanel, {
    props: { alertId: 'a-42', severity: 'critical', onAcknowledged },
  })

  await userEvent.click(screen.getByRole('button', { name: 'Acknowledge' }))
  expect(onAcknowledged).toHaveBeenCalledTimes(1)

  await rendered.dispose()
})
```

`@company/mfe-react/testing` runs the real adapter: the same validation, the same mount, the same
disposal, over in-memory storage, navigation and telemetry. `renderApp(definition, options)` does
the same for an App over a memory history.

`createMfeTestEnvironment()` gives you the pieces directly:

| Piece           | For                                     |
| --------------- | --------------------------------------- |
| `wrapper`       | rendering a hook                        |
| `routerContext` | calling a route callback                |
| `diagnostics`   | an array of what the framework reported |
| `setShellState` | driving a real identity or group change |
| `storageAreas`  | inspecting what was written             |
| `dispose()`     | running the real teardown               |

`renderSuspending(ui)` renders a tree that will suspend, inside an awaited `act` scope. That is
what you need to exercise the load itself. A first bad input throws, so assert it with
`expect(() => renderWidget(…)).toThrowError(…)`.

## Why the mount is built by the effect that destroys it

`createMount` appends a node to the document, starts a tracer and allocates a Query client. None of
that belongs in a render React may discard, so it runs inside `useOwnedMount`'s effect. One render
therefore passes with no mount and returns `null`.

StrictMode is the other half of the reason. A mount built in `useMemo` is not re-evaluated on the
second setup. That setup would then run against the object the first cleanup had already disposed,
which produced a `CancelledError` in development while production worked
([decision 14](/docs/decisions#14-a-mount-built-in-usememo-does-not-survive-a-remount-and-strictmode-remounts-everything)).
