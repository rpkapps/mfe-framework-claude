title: '10. Shipping and failures'
description: 'What your container build publishes, how its record reaches the shell, and what each rejection and runtime failure means.'
---

Your build publishes a container on your own origin, and a record in the shell's <Term>registry</Term> points at it. The registry is the JSON array the shell fetches at boot, naming every definition and where its container's manifest lives. This page covers the files you ship, the reasons a record is rejected, and the runtime failures your users can see.

## What your build produces

Run `pnpm run build` in your container. It runs `pnpm run generate && rsbuild build` and writes to Rsbuild's default `dist/`. The shell fetches these files from your origin, so they deploy together.

| File                         | What it is                                                                | Who reads it                   |
| ---------------------------- | ------------------------------------------------------------------------- | ------------------------------ |
| `remoteEntry.js`             | the file a host loads your code from                                      | the shell's loader             |
| `mf-manifest.json`           | the federation manifest, which describes that file                        | the shell's loader             |
| `mfe-registry.json`          | your container's registry descriptor                                      | the registry assembler         |
| `runtime-config.schema.json` | the schema for the deployment's values, when you have `src/mfe.config.ts` | the deployment, before release |
| the exposed chunks           | one per definition, plus the shared chunks                                | the browser                    |
| a CSS asset                  | your stylesheet, scoped to your mount roots                               | every exposed entry            |

The build copies every top-level `.json` from `.mfe/` into the output, so the descriptor and the schema ship beside the bundle. The entries, the contract modules, `.env.example` and `css.d.ts` stay behind. `assetPrefix` is `'auto'` on a build, so your assets resolve against your own deployed location rather than the shell's.

Your contract metadata rides in the manifest under `metaData.mfe`. It carries the contract major, a `buildHash`, a `buildTime`, the descriptor's filename, the definitions and the expose paths.

<Callout type="error" title="No manifest was emitted">
  `MfePlugin: no mf-manifest.json was emitted, so this container advertises no framework contract
  and a shell cannot tell which major it was built against. Check that the Rsbuild config still
  applies pluginMfe() and that nothing replaced the container's moduleFederation options.`

**Fix.** Keep `pluginMfe()` in `plugins`, and do not assign `moduleFederation.options` yourself.
`pluginMfe()` contributes them, and replacing them removes the manifest.

</Callout>

The descriptor is what a host reads without loading you (`packages/mfe-rspack/src/generate/artifacts.ts`):

```ts
export interface ContainerDescriptor {
  readonly manifestUrl: string // container-relative: 'mf-manifest.json'
  readonly container: string // the federation name
  readonly contractMajor: number // 1
  readonly definitions: readonly ExportedDefinitionDescriptor[]
  readonly entries: Readonly<Record<string, string>>
  readonly build?: BuildProvenance // { hash, time }
}
```

`manifestUrl` is container-relative, because a baked-in absolute URL breaks a promotion from one environment to the next. A Widget definition carries `contract` and an App carries `capabilities`. The shell rejects either combination reversed.

`contract.inputs` is absent when the build could not read your schema statically. An unreadable schema does not fail the build, and the Widget still validates its inputs at run time.

## How your record reaches the registry

Nobody hand-writes registry JSON. Your descriptor becomes registry entries in four steps.

<Steps>

<Step>
  Your build writes one descriptor for the container, `.mfe/mfe-registry.json`, listing every
  definition it exports.
</Step>

<Step>
  The assembler reads every container's descriptor and expands it into one entry per definition. In
  this repository that is `tools/dev/build-registry.mjs`. A real deployment does the same job with
  the deployed origins.
</Step>

<Step>
  It resolves each `manifestUrl` against that container's origin, and appends the deliberate
  fixtures.
</Step>

<Step>
  The shell spreads its own `presentation` map of `title` and `icon` per id, last, as its
  per-deployment override of what you declared. Ids, kinds, versions, capabilities, container names
  and expose paths are never written there.
</Step>

</Steps>

One entry looks like this:

```json
{
  "id": "alert-panel",
  "kind": "widget",
  "mfe": { "contractMajor": 1 },
  "manifestUrl": "http://localhost:3003/mf-manifest.json",
  "container": "example_alert_panel",
  "expose": "./widgets/alert-panel",
  "version": "1.4.0",
  "contract": { "events": ["acknowledged", "dismissed"], "inputs": {} },
  "build": { "hash": "…", "time": "…" },
  "title": "Alert panel",
  "tags": ["alerts", "operations", "safety"]
}
```

The `mfe` property is the contract marker. Its presence commits the entry to the React adapter's selection rule.

`build` is one `{ hash, time }` pair, repeated on every entry from one descriptor. A build belongs to the container rather than to any definition it exports. It never gates loading. Its only reader is the bug report, which prints `<id>: <hash> · <time>` per accepted entry, or `<id>: no build published`.

Three failures come from assembly itself:

| What is wrong                           | Fix                                  |
| --------------------------------------- | ------------------------------------ |
| the descriptor names no expose path     | rebuild: the expose map is generated |
| a container has no generated descriptor | run `pnpm run generate` first        |
| a container declares no `mfe.port`      | add the field to its `package.json`  |

<Details summary="The three messages, verbatim">

```text
alert-panel: its container's descriptor names no expose path. Rebuild the container.

No generated descriptor for insights, lab. Run `pnpm run generate` first: the registry is
assembled from what each container generates, never hand-written.

reports: package.json declares no mfe.port, so its dev URL is unknown.
```

</Details>

A registry that will not load at all is a diagnostic, not a crash. The shell still boots, and the bug report gets the failure.

## `runtime-config.json` belongs to the deployment

`runtime-config.json` is never built into the container. The deployment publishes it next to the container's assets, and the generated `#mfe/config` resolves its URL against the container's own public path. In development your dev server publishes the local copy from `public/`:

```json title="examples/operations/public/runtime-config.json"
{
  "apiBaseUrl": "http://localhost:3010/api/",
  "telemetryEnabled": false
}
```

`src/mfe.config.ts` holds declarations only, so no secret belongs in it. The build emits `.env.example`, which lists the names and the expectations and never the values. It also emits `runtime-config.schema.json` with `additionalProperties: false`, so a deployment can validate its file before release.

The snapshot is immutable. Changing a value takes a new deployment and a page reload, and nothing polls. The generated module validates in a top-level `await`. The federation entry imports it before the application entry, so a missing or invalid file fails before any application module evaluates. A container that needs no configuration gets no `#mfe/config` and fetches nothing.

## The three versions

| Version            | Set by                                                  | What it gates                                                          |
| ------------------ | ------------------------------------------------------- | ---------------------------------------------------------------------- |
| definition version | `createApp`/`createWidget({ version })` in `src/mfe.ts` | nothing. It is recorded in diagnostics and printed as `<id>@<version>` |
| package version    | `"version"` in the container's `package.json`           | the federation share scope. It is not carried into the registry        |
| contract major     | `mfe.contractMajor` on the registry entry               | loading. It is `1`, and the shell rejects any other value              |

The build requires the definition version to be a plain string literal:

```text
Write the version inline, for example version: '2.1.0'. It appears in diagnostics, so it has to be
the same string on every machine that builds this container.
```

`examples/operations` keeps both aligned at `2.1.0`. Nothing enforces that.

## Why an entry is rejected, and how to fix it

Every entry is validated on its own, so one bad entry costs only itself. A rejected entry is set aside with a reason and an error rather than dropped, and the registry marks it `quarantined`. `apps/shell/registry.source.json` ships two entries that cannot validate on purpose, because a registry is assembled from builds the shell does not control.

Four rejections come from the registry itself:

| Reason                                       | Fix                                                             |
| -------------------------------------------- | --------------------------------------------------------------- |
| `no adapter recognised this descriptor`      | publish the generated descriptor: the entry has no `mfe` marker |
| `the react adapter rejected this descriptor` | one of the field failures below                                 |
| `invalid definition id`                      | rename the id and rebuild                                       |
| two entries claim one id                     | rename one definition. Duplicates lose **all** copies           |

<Details summary="The four messages, verbatim">

```text
expected a descriptor matching one of the registered adapters (react), received a descriptor that
matched none of them. Check the entry against the generated registry descriptor produced by its
build. Nobody hand-writes registry JSON.

invalid definition id: expected lower-case letters, digits and single hyphens (for example
"alert-panel"), received "Order_Book". Rename the definition id in its createApp/createWidget call
and rebuild.

orders failed to register definition: expected one registry entry per definition id, received 2
entries claiming "orders" (at indexes 0, 4). Rename one of the definitions and rebuild. Duplicate
ids would collide in diagnostics, command attribution and <id>:<key> storage.
```

</Details>

The rule that owns an entry keeps it even when its own validation then fails. An entry that declares the framework contract is never re-read as another adapter's.

The rest come from the React contract rule. Each one is `registry/invalid-descriptor` unless noted, and most carry the same repair sentence: `Rebuild the container; the registry descriptor is generated, never hand-written.`

| What is wrong                                         | Expected / received                                                  | Fix                                                      |
| ----------------------------------------------------- | -------------------------------------------------------------------- | -------------------------------------------------------- |
| no `mfe` object                                       | `an object such as { "contractMajor": 1 }` / `nothing`               | rebuild with a release that emits it                     |
| `mfe.contractMajor` not an integer                    | `an integer` / `nothing`                                             | rebuild with a release that emits `contractMajor 1`      |
| unsupported major (code `contract/unsupported-major`) | `contract major 1` / `contract major 2`                              | upgrade the shell, or rebuild against the shell's major  |
| `id` missing or empty                                 | `a non-empty string` / `nothing`                                     | set a stable id on the definition and rebuild            |
| `manifestUrl` missing or empty                        | `a non-empty URL string` / `nothing`                                 | point the entry at your `mf-manifest.json`               |
| `kind` neither `"app"` nor `"widget"`                 | `"app" or "widget"` / the value                                      | rebuild: the kind comes from `createApp`/`createWidget`  |
| a `contract` on an App                                | `no Widget contract on an App` / `an inputs/events contract`         | drop the contract, or declare the screen as a Widget     |
| `contract.events` not a string array                  | `an array of event names` / what was there                           | rebuild                                                  |
| `contract.inputs` present but not an object           | `a JSON Schema object, or nothing when the build could not read one` | rebuild                                                  |
| `capabilities` on a Widget                            | `no capabilities on a Widget` / `2 capability descriptor(s)`         | move the capability routes into an App                   |
| an unknown capability name                            | `one of settings, help, releaseNotes` / the value                    | correct `staticData.capability` on the route and rebuild |
| a capability without a `label` and `path`             | `a string label and a string route path`                             | add `staticData.label` to the marked route and rebuild   |

Rendered in full, the `legacy-reports` fixture reads:

> `legacy-reports failed to gate the advertised framework contract major: expected contract major 1,
received contract major 2. Upgrade the shell, or redeploy the container against the shell’s major.`

Three fields are read loosely and dropped rather than failing the entry: `build`, `tags` and `icon`. A container that cannot describe its own build still mounts, and a catalogue filter is not worth rejecting an entry over. A malformed hash would otherwise reach a bug report as `[object Object]` and be believed.

## How to read a framework message

Every developer-facing runtime failure goes through `createMfeError` (`packages/mfe-core/src/errors.ts`). Every message is composed from the same five parts:

```text
<id>[@<version>] failed to <operation>[ <path>][: expected <expected>, received <observed>.] <repair>
```

1. **the definition, and its version when one was declared** — `alert-panel@1.4.0`
2. **the operation, and the field or resource** — `failed to accept input alertId`
3. **what was expected** — omitted when the observed value speaks for itself
4. **what was observed**
5. **one concrete repair step** — the last sentence, always an action

<Callout type="info" title="No runtime message names the side that set the expectation">
  `MfeErrorDetails` has no `declaredBy` field. **Build** messages do name that side, in their own
  sentence between the observation and the repair. So does the generated `#mfe/config` module. Read
  a runtime message as the five parts above.
</Callout>

A build message adds the file and position in front:

```text
<file>[:<line>[:<column>]]: '<id>' failed to <operation>: expected <expected>, found <observed>.
This expectation is declared by <declaredBy>. <repair>
```

`<declaredBy>` names the side that set the expectation, read out in lower case: `static discovery`, `the Widget contract`, `the framework identity rules`.

## Runtime failures, in the order they happen

An entry that fails costs the page that one screen. The shell's boundary renders an `Empty` box with the definition id, the whole message, a **Retry** button and the error code. The rest of the page keeps working.

| Failure                                | What the user sees                                         | Where to look                        |
| -------------------------------------- | ---------------------------------------------------------- | ------------------------------------ |
| the container fails to load            | the boundary box, with Retry                               | the developer tools' Registry tab    |
| the definition is invalid at mount     | the boundary box, with Retry                               | your `src/mfe.ts` and router factory |
| a render throws                        | your `defaultErrorComponent`, or the consumer's `fallback` | your own error component             |
| inputs or an event fail validation     | the consumer's `fallback`, or the last valid inputs        | the console diagnostic               |
| a request goes to an undeclared origin | a 401 from the endpoint                                    | `src/mfe.config.ts`                  |

### The container fails to load

You get one diagnostic per attempt. There is no time budget on this path. The load suspends under React `Suspense` until it settles or fails, and retry is explicit.

| Code                          | What went wrong                          |
| ----------------------------- | ---------------------------------------- |
| `load/manifest-failure`       | the manifest was unreachable or invalid  |
| `load/entry-failure`          | a chunk failed after the manifest loaded |
| `load/entry-failure`          | the module exports no definition         |
| `registry/invalid-descriptor` | the kind does not match the registry     |
| `config/missing`              | no runtime configuration was published   |
| `config/invalid`              | a configuration field failed its schema  |

<Details summary="The repairs these messages carry, verbatim and in that order">

```text
Check that http://localhost:3001/mf-manifest.json is reachable and serves a valid manifest.

Check the browser network panel for the failed chunk. A container that resolved its own copy of a
shared singleton fails differently: it loads, and a framework hook inside it then reports being
rendered outside any mount.

Export the definition from src/mfe.ts and rebuild the container.

Rebuild the container so its descriptor matches what src/mfe.ts exports.

Publish the runtime configuration with the container. The generated .env.example lists every value
it has to carry, and the generated JSON Schema validates it before release.

Set API_BASE_URL in the deployment that writes this container's runtime configuration, then reload
the page.
```

</Details>

Look at the developer tools' **Registry** tab first. **Loaded** gives the URL each definition loaded from and marks an overridden entry. **Rejected** names every set-aside entry with its reason. If your id is not listed at all, the message tells you what to do:

```text
Check the id against the generated registry descriptor, or add a localStorage override pointing at
your dev server.
```

### The definition is invalid at mount

An App that does not forward what its factory received fails as the same box.

| What is wrong                       | Fix                                |
| ----------------------------------- | ---------------------------------- |
| the router has no `basepath`        | pass `basepath: basePath`          |
| the history is not the one supplied | forward the history you were given |
| the `mfe` namespace was replaced    | spread the supplied context        |

<Details summary="The three messages, verbatim">

```text
operations@2.1.0 failed to mount App: expected the supplied basePath "/operations" passed through
unchanged as createRouter({ basepath }), received no basepath on the router. Forward the basePath
your factory received: createRouter({ basepath: basePath, … }).

operations@2.1.0 failed to mount App: expected the exact history instance the framework supplied,
received a different history object. Do not create, wrap, replace or mutate the history; forward
the one your factory received.

operations@2.1.0 failed to mount App: expected the supplied context.mfe namespace, spread into the
router context unchanged, received a replaced or rebuilt mfe namespace. Spread the supplied
context: add your own top-level keys freely, but do not replace mfe or add fields inside it.
```

</Details>

### A render throws

Give an App a `defaultErrorComponent`, so a route-level failure stays inside your screen. Without one, the consumer's `fallback` renders and the framework wraps the throw as `mount/failure`, carrying whatever the throw said.

### Inputs or an event fail validation

A Widget validates its inputs against its own schema on every render, and both sides validate events.

| When                                      | What the user sees                                        | What you see                                                     |
| ----------------------------------------- | --------------------------------------------------------- | ---------------------------------------------------------------- |
| the **first** inputs fail                 | the consumer's `fallback`, code `contract/input-mismatch` | one diagnostic with `context: { widget: id }`                    |
| **updated** inputs fail                   | the last valid inputs, still on screen                    | one diagnostic                                                   |
| an undeclared event is emitted            | nothing. The throw lands in the provider's own stack      | `Add 'resolved' to the events schema, or emit a declared event.` |
| a payload fails the **consumer's** schema | nothing. The event is dropped                             | `Check the 'acknowledged' schema this consumer declared.`        |

<Callout type="error" title="An input that does not match the declared schema">
  `alert-panel@1.4.0 failed to accept input alertId: 7; ✖ Invalid input: expected string, received
  number → at alertId. Check the alertId prop on the Widget.`

**Fix.** Pass a string. The wording after the semicolon is Zod's and changes with the schema. The
framework's own half is the first clause and the last sentence.

</Callout>

### A request through `#mfe/fetch` goes wrong

If an origin is your API, declare it with `env(…, { api: true })`. The session bearer token is attached to declared origins only. An undeclared origin gets the request without a token, and the endpoint answers 401. In development you get one warning per origin:

<Callout type="error" title="A request to an origin you did not declare">
  `operations@2.1.0 failed to attach the access token for https://metrics.example.com: expected a
  request to an origin the author declared as an API with { api: true }, received a request to
  https://metrics.example.com, which is not declared. Declare https://metrics.example.com with {
  api: true } if it is your API, or leave it undeclared if it must never receive the session bearer
  token. It was sent without one, so an endpoint that requires it answers 401 — that 401 is this
  missing declaration, not a broken token.`

**Fix.** Add the origin to `src/mfe.config.ts` with `{ api: true }`. If that host must never see
the token, the 401 is correct. There are no wildcards, because a wildcard would hand the session
bearer token to any host the pattern happened to match.

</Callout>

## What you get without writing telemetry code

- Every `MfeError` the framework raises about your definition reaches the shell's diagnostics hub, which forwards it to the shell's telemetry provider.
- Every record carries attribution you cannot override: `mfe.definition.id`, `mfe.definition.kind`, `mfe.definition.version`, `mfe.build.hash`, `mfe.mount.token` and `mfe.trace.id`.
- A production failure therefore arrives labelled with the definition, its version and the build hash. An attribute collision resolves in favour of attribution.
- Use `useTelemetry()`, and ship no telemetry SDK. The `author` lint preset blocks `@opentelemetry/*` and `@grafana/faro-*`, type imports included. Two SDKs in one page mean two trace contexts and twice the bundle.
