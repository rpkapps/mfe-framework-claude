title: 'Configure user context in the shell'
description: 'Persist opaque user documents through an authenticated adapter.'
---

The shell supplies the storage adapter and its authenticated user through the normal shell state. Definitions independently declare their own schemas and cross-owner reads. The runtime registers compiled owner contracts embedded in the generated registry; application code does not aggregate owner schemas or construct a storage scope.

## Configure the adapter

Use your shell framework’s `/host` entry. These examples use the repository’s React shell; an Angular host imports the same factory and adapter types from `@company/mfe-angular/host`.

```ts shared title="src/runtime.ts"
import { createMfeRuntime } from '@company/mfe-react/host'
import { userContextAdapter } from './user-context-adapter'

const { runtime } = createMfeRuntime({
  ...hostOptions,
  shellState: { user: authenticatedUser, groups: authenticatedGroups },
  userContext: {
    adapter: userContextAdapter,
    onError: reportUserContextFailure,
  },
})
```

`hostOptions` contains the host's usual registry entries, framework adapters and container loader. The generated registry embeds each definition's current owner contract. Before mounting a definition, the runtime checks the consumer's declared requirements against those contracts and hydrates the required slices. An unsupported read contract fails before render, loaders or resolvers run. Publish the generated registry with the container; owner contracts remain framework metadata; neither the shell integration nor the persistence adapter imports a schema list.

Each authenticated scope comes from the user's tenant ID, account ID and user ID. No storage calls run while `shellState.user` is `null`. Owners and readers use the same authenticated scope without receiving or assembling an identity key themselves.

The adapter and backend store an opaque document for each authenticated user, keyed by owner ID:

```json shared title="One user's persisted document"
{
  "lab": { "units": "imperial", "well-selection": { "wellId": "well-42", "runId": "run-8" } },
  "well-inspection": { "brief": null },
  "shell": { "preferences": { "theme": "dark" } }
}
```

Changing Lab updates only the `lab` entry. Other owners and fields unknown to an older deployment remain intact. The backend has no domain schemas, field lists or defaults to keep in sync. Revision and retry metadata can be stored alongside this document without becoming application values. The MFE runtime owns schema validation and default materialization.

## Implement persistence

`UserContextAdapter` is exported by the React and Angular `/host` entries. It has `hydrate(ownerIds, signal)` and `write(operation, signal)`. An optional `subscribe(listener, signal)` receives authoritative updates for the authenticated user. None receives a scope string. Each record contains the owner's complete object slice, owner ID and monotonic record revision. `write` resolves only after durable acceptance and returns the authoritative record. The authenticated API identifies the current user independently of request data.

For example, a browser adapter forwards the protocol to your application's authenticated API client:

```ts shared title="src/user-context-adapter.ts"
import type { UserContextAdapter } from '@company/mfe-react/host'
import { api } from './authenticated-api'

export const userContextAdapter: UserContextAdapter = {
  hydrate: (ownerIds, signal) => api.hydrateContext({ ownerIds }, signal),
  write: (operation, signal) => api.writeContext(operation, signal),
}
```

The API client returns authoritative `StateRecord` values, forwards abort signals, and preserves backend failures rather than manufacturing successful records. Its authenticated connection determines the user; the browser submits only owner IDs and values.

An owner write includes `id`, `expectedRevision`, `operationId` and a structural object update. Preserve unknown fields when applying an older writer's update. Deduplicate operation IDs and compare revisions transactionally. Never trust a submitted owner ID as authorization; authorize using the authenticated server session.

For a backend implementation, use `createUserContextBackend` from `@company/mfe-runtime/user-context`. Supply a `UserContextRepository`, authenticated authorization and a `resolveOwner` callback derived from the trusted request identity. There is no schema option. Its transaction checks the record revision, merges opaque JSON objects recursively and saves the result and idempotency receipt together. The repository resolves only after durable commit.

A request-scoped backend binds the authenticated writer independently of the submitted record:

```ts shared title="server/user-context.ts"
import { createUserContextBackend } from '@company/mfe-runtime/user-context'
import { repository } from './context-repository'
import { authenticate, authorizeContext } from './authentication'

export async function contextForRequest(request: Request) {
  const session = await authenticate(request)
  return createUserContextBackend({
    repository,
    resolveOwner: async () => session.authorizedDefinitionId,
    authorize: (scope, ownerId, operation) =>
      authorizeContext(session, { scope, ownerId, operation }),
  })
}
```

`authenticate`, `authorizeContext`, and the durable repository belong to your application. The authenticated definition ID must come from a trusted server policy or credential, not an arbitrary owner header. A write route obtains its backend with `contextForRequest(request)`, derives the internal storage partition from the authenticated session, and adds that partition when calling the low-level `backend.write`. A hydration route supplies the same trusted partition to `backend.hydrate`. Neither route accepts the user partition from the request body. Those low-level storage details remain server-internal; the shell adapter sees only its signed-in user’s requests.

The runtime keeps pending writes invisible. Once storage accepts a write, it publishes the accepted value to subscribers and resolves the caller's success result. Rejected writes return a structured failure without replacing the previous committed value.

## Follow the authenticated user

Update the shell's authenticated user through its normal identity lifecycle:

```ts shared title="src/session.ts"
runtime.shellState.apply({ user: nextAuthenticatedUser, groups: nextGroups })
// Sign-out follows the same path:
runtime.shellState.apply({ user: null, groups: [] })
```

The runtime synchronously invalidates the previous context when the identity changes. It derives the next scope, invalidates old bindings, aborts pending work and removes old subscriptions. Late responses cannot publish into the next user's context. Remount affected Apps and Widgets as part of the host's session transition.

A display-name change does not change the scope. Changing a tenant, account or user ID does. Signing out clears the current context instead of sharing an anonymous persisted slice.

## Give the shell its own preferences

The React shell in this repository hosts both React and Angular definitions. These host snippets apply to either kind of MFE. The shell owns the `shell` slice. Declare its schema next to the adapter in the normal runtime factory call:

```ts shared title="src/boot.tsx"
import { createMfeRuntime } from '@company/mfe-react/host'
import { z } from 'zod'
import { userContextAdapter } from './user-context-adapter'

const { runtime } = createMfeRuntime({
  ...hostOptions,
  shellState: { user: authenticatedUser, groups: authenticatedGroups },
  userContext: {
    adapter: userContextAdapter,
    schema: z.object({
      preferences: z
        .object({
          theme: z.enum(['light', 'dark', 'system']).default('system'),
        })
        .default({ theme: 'system' }),
    }),
    reads: {
      lab: z.object({
        'well-selection': z.object({ wellId: z.string() }).nullable(),
      }),
    },
  },
  theme: {
    select: context => context.preferences.theme,
    cacheKey: 'portal:theme',
  },
})
```

The build discovers this call from the shell entry and compiles the schema out of the runtime bundle. `theme.select` infers the owned shape from `schema`. Run the shell's generation command to generate the typed `#mfe/user-context` hook. The adapter remains a normal local module. `reads` declares only the foreign fields the shell uses; here, it needs Lab's selected well ID without importing Lab's full schema.

A shell setting uses the same owner-inferred binding:

```tsx shared title="React host: src/theme-setting.tsx"
import { useUserContext } from '#mfe/user-context'

export function ThemeSetting() {
  const [theme, set] = useUserContext(context => context.preferences.theme)

  async function chooseDark() {
    const result = await set('preferences', { theme: 'dark' })
    if (!result.ok) console.error(result.error.message)
  }

  return <button onClick={chooseDark}>Dark theme (current: {theme})</button>
}

export function SelectedWell() {
  const [wellId] = useUserContext('lab', context => context['well-selection']?.wellId)
  return <span>{wellId ?? 'No well selected'}</span>
}
```

Mount these components within a Suspense boundary and an error boundary, as their initial reads wait for hydration. The foreign Lab binding returns a one-element tuple with no setter. Each selector subscribes to the fields it accesses and cleans up automatically. Other shell surfaces can keep reading the effective theme while that preference loads. Only accepted writes update the stored preference.

The framework maintains a theme cache partitioned by authenticated tenant, account and user. The shell's prepaint bootstrap must use the same cache key and known identity: `themeCacheKey(cacheKey, user)` from the `/host` entry builds that key, and `readCachedTheme(cacheKey, user)` reads it safely. Before identity is available, use the system theme; do not apply another user's cached preference. A theme correction may be necessary after sign-in when the identity was unknown at first paint.

## Inspect context

The developer tools' **User Context** tab displays each owner contract, committed value, record revision and pending write count. Merely opening the inspector does not hydrate or write context. Scope IDs are excluded from inspection snapshots.
