---
title: 'Build and publish a container'
description: 'What your container build writes, where to publish it, and how its entry reaches the registry.'
---

Build and publish from the container’s own repository. The shell runs in a separate repository and consumes the generated deployment record. Apps and Widgets publish the same way.

## Steps

<Steps>

<Step>
### 1. Build the container

<Tabs items={['React', 'Angular']} defaultIndex={0}>
<Tab value="React">

```sh
pnpm install --frozen-lockfile
pnpm run build
```

Run these commands in your React package directory, such as `apps/field-notes` in the quickstart repository. Its build script runs `mfe-generate` followed by `rsbuild build`.

</Tab>
<Tab value="Angular">

```sh
pnpm install --frozen-lockfile
pnpm exec nx build operations --configuration=production
```

Run this in your container's own Nx workspace. Replace `operations` with its project name. The target depends on generation.

</Tab>
</Tabs>

Install compiled framework releases from your configured package registry. Your repository owns its build configuration and lockfile.

The current React scaffolder writes workspace/catalog references and extends a parent TypeScript configuration. Follow the [independent repository setup](/docs/quickstart) before installing its output. Angular generates a project in your own Nx workspace with published dependency ranges.

</Step>

<Step>
### 2. Check what the build wrote

| File                                        | What it is                                     | Who reads it                    |
| ------------------------------------------- | ---------------------------------------------- | ------------------------------- |
| `remoteEntry.js`                            | the file a host loads your code from           | the shell's loader              |
| `mf-manifest.json`                          | the federation manifest describing that file   | the shell's loader              |
| `mfe-registry.json`                         | your container's description record            | whoever assembles the registry  |
| `runtime-config.json`                       | the declared defaults, and nothing else        | the start-up script, then you   |
| `runtime-config.schema.json`                | the shape of the deployment's values           | your deployment, before release |
| one chunk per definition, and one CSS asset | your code, and the styles scoped to your roots | the browser                     |

The build ships the `.json` files it generates into `.mfe/`, and writes the two configuration files
only for a container that has `src/mfe.config.ts`. It never ships `.mfe/runtime-config.json`, your
local values, because no build copies anything from `.mfe/` that it did not generate for the build output.
Outside the output directory, it also writes `.mfe/runtime-config.sh`, which your image runs at start to write
the environment into `runtime-config.json`.

</Step>

<Step>
### 3. Publish the whole output directory

```text shared
alert-panel.example.com/
  mf-manifest.json
  remoteEntry.js
  mfe-registry.json
  runtime-config.json   (only for a container with src/mfe.config.ts)
```

For React this is usually `dist/` relative to that package directory. For Angular, read `build.options.outputPath` in your project configuration. Publish every built file to the origin your entry will point at, and let the deployment write its
values into `runtime-config.json` beside them. The
[Docker recipe](/docs/supply-values-per-deployment#run-the-artifact-in-a-docker-image) does that from the
container's environment.

</Step>

<Step>
### 4. Hand the description record over

<Tabs items={['React', 'Angular']} defaultIndex={0}>
<Tab value="React">

```json title="dist/mfe-registry.json (trimmed)"
{
  "manifestUrl": "mf-manifest.json",
  "container": "alert_panel",
  "framework": "react",
  "requiresRuntime": ">=1.1.0 <2.0.0",
  "definitions": [{ "id": "alert-panel", "kind": "widget", "version": "1.4.0" }],
  "entries": { "alert-panel": "./widgets/alert-panel" }
}
```

</Tab>
<Tab value="Angular">

```json title="dist/apps/operations/mfe-registry.json (trimmed)"
{
  "manifestUrl": "mf-manifest.json",
  "container": "operations",
  "framework": "angular",
  "requiresRuntime": ">=1.1.0 <2.0.0",
  "definitions": [
    { "id": "operations", "kind": "app", "version": "0.1.0" },
    { "id": "well-inspection", "kind": "widget", "version": "0.1.0" }
  ],
  "entries": { "operations": "./app", "well-inspection": "./widgets/well-inspection" }
}
```

</Tab>
</Tabs>

`manifestUrl` is relative to your container, so whoever assembles the registry resolves it against
the origin you deployed to.

`requiresRuntime` is generated from the build integration's compatibility metadata. One runtime
API version covers this registry format, the mount protocol and shell-owned services. The shell
checks that requirement before selecting an adapter or parsing the registry shape.

</Step>

<Step>
### 5. Update the shell registry

Give the published `mfe-registry.json` and deployment origin to your platform's registry integration. The shell repository or registry service assembles its registry from those records. Resolve relative manifest URLs against the container's deployment origin.

Deploy the resulting registry separately from the container. The framework provides the generated record and registry reader; your platform supplies registration and aggregation.

</Step>

</Steps>

## Check it works

Request `mf-manifest.json` from the origin you published to. It has to answer with JSON, and that
JSON carries your definitions under `metaData.mfe`. Then open the shell and the developer tools'
**Registry** tab. **Loaded** names every accepted entry with the origin it loaded from, and
**Rejected** names the ones the shell set aside.

## Errors

<Tabs items={['React', 'Angular']} defaultIndex={0}>
<Tab value="React">

<Callout type="error" title="MfePlugin: no mf-manifest.json was emitted">

```text
MfePlugin: no mf-manifest.json was emitted, so this container declares no framework contract and
a shell cannot tell which major it was built against.
```

**Fix.** Keep `pluginMfe()` in your Rsbuild configuration. Let the plugin contribute its Module Federation options.

</Callout>

</Tab>
<Tab value="Angular">

If the manifest is missing, check the Nx project's `customWebpackConfig` loads `withMfe()` and build the correct project. Publish its configured output directory.

</Tab>
</Tabs>
